# Faster Letterboxd backfill — 2026-11-01

The owner requested the fastest practical backfill using subagents and scripts. Two agents audited throughput
and implemented bulk identity enrichment while the root agent operated the live pipeline. All source requests
continue through the same globally paced, identifying client; no agent performed independent Letterboxd crawling.

## Running changes

- The initial seed completed successfully: **710,870 source entries** processed in 895 seconds; the queue
  contains about 710,900 distinct movies (710,863 at the acceptance snapshot).
- One first-party Wikidata CSV export joined TMDB movie IDs, Letterboxd slugs and optional IMDb IDs. Its 269,755
  rows produced 266,537 unambiguous URL candidates. The initial plan attached 260,498 hints; a cached reconciliation
  attached three more. The remaining 5,101 unqueued candidates do not currently have an eligible seeded source row;
  deleted/missing movies and IMDb mismatches were also excluded. No second network export was needed.
- The URL hints go into `wikidata_url`, preserving verified source URLs and scores. Every fetched page still
  requires exact external identity. A valid direct URL removes the cold IMDb redirect: one source request instead
  of two. A stale 404/410 or mismatched hint falls back to IMDb and is marked rejected.
- `f/letterboxd/backfill` runs consecutive crawl segments in batches of 100. Its enabled hourly schedule starts
  at :00 UTC and runs for up to 58.8 minutes. This replaces the five-minute idle gaps between ordinary 25-minute
  runs with about 1.2 minutes idle per hour: up to 17.6% more active time before other overhead.
- The shared request spacing remains two seconds per hop, with one active crawler lease, a block check immediately
  before each request, and a stop on rate limits/challenges. More jobs do not multiply source traffic.
- A weekly Monday 03:00 UTC mapping schedule refreshes hints from Wikidata. Manual runs default to a dry run.

The continuous worker uses the ordinary popularity queue, so due retries and recent-release refreshes continue
during the backfill. Existing half-hourly crawl schedules remain enabled; whichever job holds the shared lease
owns fetching. Completed segments immediately continue within the hourly backfill budget. Larger publish batches
reduce database round trips without changing source request spacing.

## Live handoff and validation

The original scheduled crawl was canceled through Windmill and confirmed completed before releasing its exact
owned lease. Its single unfinished queue claim was made due again only if it had not completed. A catch-up
publication republished 140 completed source records so no partial batch was stranded. Source block state was
preserved.

The accelerated manual job `01a195ff-e525-86ef-b164-7f1832e98d67` started at 07:25:37 UTC and is bounded to finish
before the next hourly backfill. It started with the initial cold-only wrapper; the subsequent deployed hourly
version uses the ordinary due queue to maintain refresh/retry fairness. The first 100 movies consumed **169
requests**, versus roughly 200 without URL hints; it published 99 results (84 rated, 15 unrated), with one
temporary error and no source block. Because mappings were being attached during that batch, it is a transition
measurement, not the final sustained rate. At the next queue sample, 81 of the next 100 movies had URL hints.

Mapped movies can approach twice the cold lookup throughput at the same request pace. Actual total throughput
depends on mapping coverage, redirects, latency, errors and source backoff; the entire long-tail catalog still
requires a sustained multi-week crawl at this pace.

All 36 Letterboxd parser, transport, queue, wrapper and mapping tests passed. They cover the post-wait source-block
check, mapped direct fetches, stale-hint fallback, exact identity checks, ordinary due-queue use, lease waits,
block propagation, batch counters, CSV truncation, ambiguity rejection and concurrent URL protection. An
independent agent review found no blocking issue. A mapping redirecting to an unexpected non-movie HTTP 200
page remains a parse error rather than triggering speculative retries through unknown markup.
