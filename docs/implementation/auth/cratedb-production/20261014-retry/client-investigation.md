# Read-only client investigation and retry plan

Investigation started 2026-10-14 20:48 UTC; completed 20:52:48 UTC, within the owner's 20-minute cap. No production mutation was made during this investigation.

All three actual .20 app/search containers have CRATE_HOSTS=10.0.0.11,10.0.0.12,10.0.0.13, CRATE_PORT=4200, and no CRATE_TIMEOUT_MS override (wrapper default 10,000 ms). Installed node-crate is 3.0.0; all inspected connection-pool implementations match. The wrapper constructs URLs in that order and calls crate.connect. Its pool increments lastUsed before selecting; initial selections are .12, .13, .11, repeatedly. This is round robin per SQL statement, not a preferred-first healthy-host list. It has no health eviction or fallback selection, and _executeSql rejects connection/response errors without retrying that statement on another host. Wrapper execute records FAILED and propagates the error; its 10-second cap closes that request. Some specialized write helpers perform read-back/replay, which is not generic query failover and must not be broadened during this window.

Crate-02 was therefore one of the coordinators for these clients, including the first selection after a new pool's initialization. Current socket evidence and an offline pool-selection calculation in a separate read-only process support the routing finding. Historical failed log lines did not identify their destination host, and the original webapp container was removed externally, so individual prior failures cannot be conclusively attributed to a host. The inference is that about one in three statement selections continue targeting a drained node, although request impact is not one in three members: a member request can issue multiple statements. Crate's documented decommission rejects new requests while pending work/relocations finish; distributed requests may also fail even when their coordinator survives. Both explain why healthy surviving endpoints did not prevent application errors.

Expected member impact tonight: pages, discovery/search and member catalog operations that need CrateDB may show errors, take up to the 10-second application cap, or need a member retry during each drain/restart. Affected writes may have ambiguous outcomes; existing read-back safeguards must decide them. Availability of primary data and GREEN recovery gates do not promise error-free member requests. No generic native-client failover is present. No app code, host order, retry policy, container or app configuration will be changed by this operation. The owner explicitly authorized proceeding after the bounded diagnosis despite this known impact; failed-query log lines will be counted per node from before decommission through recovery.

Timeouts: explicitly set cluster.graceful_stop.timeout to 2h (7,200,000 ms), retaining the measured live baseline and documented default, with min_availability=PRIMARIES and force=false unchanged. HTTP decommission read timeout=7,500 seconds, SSH wrapper bound=7,530 seconds. Previous relocation took about 34 minutes, well above 30 seconds and below this server budget; HTTP waits exceed the configured server relocation timeout. Tagged 5.10.9 code then separately waits for active contexts (up to the same 2h), so SQL acknowledgement alone is not an exit gate. Independently inspect the real node/container exit; do not advance on an acknowledgement or force a stop. The settings are dynamic; no static node/app/firewall config is modified. Preserve prior effective timeout and restore/document transient override provenance without RESET GLOBAL erasing persistent settings.
