# Verdict: FEASIBLE-CONDITIONAL

A provisional ranking is feasible only as a narrow local dense shortlist with catalog validation. It will not carry the p95 goal by itself, so the pinned clone diagnosis stays the real fix.

**Source-only review.** I ran nothing and measured nothing, so every latency statement below is a path to measure, not a number. I did not see `ranking.server.ts` (the weights), `search-reblend`/`title-blend`, `RankingProgress`, admission, the Jev runtime, `describeTitles`, the route or `search-client`.

## Check before building (existing data, no code)

- **Upstream floor.** The provisional cannot start before the reading, because the flags come from it. If p95 of `people + language + reading` in existing history rows leaves no headroom under 1500 ms, stop.
- **Translation path.** With `translationEnabled()`, a description search never has an exact title match, so `languagePromise` awaits the full `titlePromise` (page 1 has an 8 s timeout) before the reading starts. No provisional branch fixes that.
- **Coverage.** p95 tolerates 5% slow searches. If the emit-nothing classes below exceed that share of traffic and are slow, the target is missed regardless.

## Signals that exist locally

| Final signal | Local? | Source |
|---|---|---|
| Dense text cosine | Yes, approximately | `prepared.encoded` early vector × `mixVectors[embMain]` (int8) |
| Negated-clause penalty | Yes | negated clauses are in the early encodings |
| Negation labels | Yes | `labelNegation(index, …)` |
| Votes and score priors | Yes | `titleTable` |
| Jev flags, era, type/anime/year/`onlyTitles` | Yes, same decode | the same `searchFilter(...).withEra.rows` |
| Fingerprint (`reading.vector`) | No | no per-title fingerprints |
| BM25 and coverage units | No | no document vectors |
| Facets, English chips | Only after `encodeLate` | not worth waiting for |
| Genre and streaming chips | No | Crate is the authority |

## Usefulness by query type

- **Mood ("tense but not bleak"):** weakest. The fingerprint signal is absent, so expect the largest change when the final list arrives.
- **Concrete ("heist on a train"):** plausible. Without the min-over-units coverage, titles matching only one concept can rank high.
- **Negation:** hard flags are enforced identically. Soft negation is a penalty only, as in the final, so a "without gore" provisional can still show a gory title.

## Local dense shortlist vs expanded literal search

Build the dense shortlist only.

- **Dense shortlist:** it uses no extra encode, Qdrant call or admission slot, and adds one Crate round trip. Its weakness is that it ranks before filtering, so selective genre or streaming chips starve it; then it emits nothing.
- **Expanded literal:** it filters in SQL by construction, which is its one real advantage. But it is a second ranker with its own relevance:
  - `literal(q)` as written matches negated words positively.
  - `toCrateSql` enforces no Jev flags or era.
  - It has nothing for mood queries.
  - A rewritten MATCH text cannot share `basicResults`, so a later fallback would run a second Crate search.

## Emit nothing when

- There is no reading, or `servingFallback` is non-null.
- `lesserKnown` is on: the table holds only indexed titles, so the provisional would show exactly what the toggle is meant to move past.
- `prepared.found` is set: reference ranking is profile-driven.
- The query is non-English (v1): the final dense signal is a two-model mix that needs the late chip vector.
- There is no early dense vector.
- Catalog validation fails or times out; never emit an unvalidated list.
- Fewer than a set minimum of titles survive validation.
- The full ranking has already settled, or the signal is aborted.

## Minimal seams

1. **Preparation.** For streaming callers, if `early.prepared` is undefined after a cached reading, start `prepareSearch` in `combinedSearch` and pass it on. `rankSearch` already consumes `request.prepared`, so there is still one preparation.
2. **Top-K scan.** Add a row-returning variant of `quantizedCosines`. Run it only after round 1 has been dispatched; otherwise its synchronous CPU delays the final ranking on the main thread.
3. **Catalog validation.** One query per type over the local top N: `tmdb_id IN (…)` plus `toCrateSql(policy.filters, type)` plus the eligibility clauses from `literal`. It returns the `Metadata` columns, takes the signal, has a short timeout and is aborted when the ranking wins.
4. **Packet.** Add a distinct `pendingRanking: true` flag. Rows carry no `discovery`, so no reasons render. Metadata must ship, because the client's `matchesRow` reads genres from it.
5. **Deadline.** `RankingDeadlineError` carries the original `ranking` promise. The deadline, `hold(ranking)` and the timeout record stay unchanged.
   - If a provisional was delivered, await that same promise under a separate cap that the signal can abort.
   - On cap or rejection, serve the basic list as today.
   - With no provisional, behaviour is exactly as today.
6. **History.** Record which kind of batch came first, the provisional row count, scan and validation times, and when the ranked list arrived.
   - Set `firstResults` only after the awaited `onProgress` resolves with at least the minimum rows.
   - An abort after a provisional currently records `BASIC_RANKER_VERSION`, which would be wrong; it needs a provisional marker.

## UX warnings

- **Wrong status text.** The client sets `pendingTitleLookup = Boolean(partial)`, so a provisional would say "Still checking title matches". It needs its own wording, such as "Quick matches, refining…".
- **Chips over-claim.** "Looking for" shows the full reading, including avoid chips, while the provisional used only part of it. The status line must carry the uncertainty.
- **Reordering.** The final order must win, so the list swaps wholesale under the pointer.
  - `focusedKey` survives by key, but a title that leaves turns Enter from "open" into "search".
  - With a late title completion there can be three list states.
- **Click continuity.** The search keeps running on the detail page. When the final list drops the opened title, `JourneyNavigation` shows "Outside filters" and "Return to results to choose a matching title", which is false. Previous/Next also change underfoot, and `page` in `detailHref` comes from the provisional position. Disable sequence navigation while provisional.
- **Paging.** Cap the provisional at one page of 20 or fewer and hide the pager, or the page count jumps.
- **Extra requests.** `/api/watchability` is keyed on row keys, so it fires for the provisional and again for the final. With streaming set to "only", that adds another visible row drop.

## Tests that can fail

- **Single delivery:** with the ranking pending, `onProgress` fires once with `pendingRanking`. The final rows deep-equal the non-streaming result.
- **No double work:** `rankSearch`, `encodeQueryTexts` and `queryBatch` call counts are identical with and without the provisional.
- **Filter validity:**
  - Titles failing genre or streaming in the catalog never appear.
  - A validation timeout produces zero progress calls and no `firstResults`.
- **Flags and era:** a title with an excluded flag or outside the era never appears.
- **Emit-nothing cases:** each case above yields no packet and no provisional stage keys. This includes the ranking settling first, tested with fake timers.
- **Deadline:**
  - A late ranking is served after a provisional, with `hold` called once on the same promise.
  - Without a provisional, the basic path is pinned unchanged.
  - A late rejection yields the basic list.
- **Abort:**
  - After a provisional there is one history row with `completionAborted`, no `onComplete`, zero pending timers and an aborted validation signal.
  - Before a provisional there is nothing.
- **Client:**
  - The provisional never enters `sessionStorage`.
  - The status text is distinct.
  - No reasons render.
  - Sequence navigation is disabled.
- **Offline parity (not a unit test):** local cosine against the trace's dense signal, and provisional-versus-final top-20 overlap per query class on the existing evaluation set with cached readings.

## Critical path to measure

`people + language + reading + early-encode wait + scan + one Crate validation + delivery`. Check whether the route's taste lookup sits inside `onProgress`.

## Product decisions

1. **Counting.** Does a list ranked without the fingerprint signal count as "first usable"? I recommend yes, only for classes that pass an overlap bar you set, with provisional-first and ranked-first p95 reported separately.
2. **Late ranking.** After the deadline, should the same late ranking replace the provisional, or the basic list as today? I recommend the late ranking under a hard cap, to avoid two unrelated lists.
3. **Swap timing.** Swap at once, or hold while a card is hovered or focused? I recommend a bounded hold.

A later option outside "existing index" is to add per-title fingerprints to the build, which would restore the missing mood signal locally. It is an index format change.
