# Verdict: ACCEPT

I found no mandatory blocker in the frozen v3 source. This is a paper read of the supplied source and diff only: I ran nothing, and the 139/139 and typecheck results are the author's.

## The seven design blockers

| # | Blocker | Status | Where it is closed |
|---|---|---|---|
| 1 | Named strong matches, filter validity | Covered | `search.server.ts` early batch |
| 2 | Chips, mode, pending flags | Covered | `search-partial.ts`, both controllers |
| 3 | Pre-reading failure and accounting | Covered | hoisted history state, widened `try` |
| 4 | Durable history, delivery acknowledgement | Covered | `BatchDelivery`, route `sendBatch` |
| 5 | Callback failure, admission drain | Covered | `earlyBatch.failure` latch, catch block |
| 6 | `firstResults` preserved | Covered | `??=` at both provisional sites |
| 7 | 1500 ms deadline, same promise, 15 s cap | Covered | `late.resume`, `RankingDeadlineError.ranking` |

1. **Strong matches.**
   - Early rows come only from `matches.allowedTitles`, which has already passed `allowsTitle` and `eligible(..., false)`.
   - They need `lexical >= 0.9`, or the exact title when every query word is in the ranker's `STOPWORDS`.
   - Chip filters are applied where the final's title rows already get them (`matchesRow` in Journey, the results endpoint in Discover), so validity matches the final.

2. **Chips and flags.**
   - `selectReading` binds to the full request key, lets a `pendingRanking` batch fall through to the same-key streamed reading, and rejects other keys.
   - A completed batch's reading still wins, including an empty or missing one.
   - `mode` is `"unknown"` before the language step rather than an invented value; the early packet's `errors` is a fresh `[]`.

3. **Pre-reading failure.**
   - `read`, `fallback`, `served` and `languageMode` are hoisted, so `queueHistory` no longer closes over an unassigned binding.
   - A failure before any reading records `basic` with the charge accumulated so far.
   - The early path never touches `basicList`, `literal()` or `lap()`.

4. **Delivery acknowledgement.**
   - `sendBatch` returns `sent`. An early batch counts only when `delivered !== false && !signal.aborted`.
   - A declined final throws, so no success row is written.
   - Without callbacks, `delivered` is `undefined` and the path is as before.

5. **Admission drain.**
   - A rejected early callback is latched and rethrown only after the ranking and `await earlyBatch.sending`.
   - The catch holds `lateWork` and a running people step before the route can release, then awaits `sending`, `early.titles` and `early.prepared`.
   - The "early batch after ranked results" race is closed by reaction order on `shownPeople`: the main path's continuation runs before the `Promise.all` callback, which then sees `closed`.

6. **`firstResults`.** It is also set only after an accepted, un-aborted delivery, so it stays a valid "delivered" latch for the catch.

7. **Late window.**
   - `resume` returns the original promise only when the early batch was delivered, the signal is live and no window exists.
   - There is exactly one `rankForServing` call per search; reblend goes through `reuse`.
   - The cap is cleared after the final is built and before `onComplete`.
   - A declined or still-sending early batch keeps today's basic fallback.

## Other dispositions I checked

- **No duplicate queries:** hoisting `titleMatches` above the language await adds no catalog read, and the late path adds no reading, ranking or `literal()`.
- **Sibling ownership:** `metadataFor`'s `track` registers each per-table query, and `describeTitles` is owned separately. Before a miss, `own`, `bounded`, `signal` and `budget` are identity or `undefined`, so non-late reads keep their own limits.
- **No new unhandled rejections:** every owned promise gets a `then(ended, ended)`, and `expired` and the title-match promise are pre-caught.
- **Timings:** `Object.assign(stageMs, served.stageMs, deadlineStageMs)` keeps completed `ranking*` values and the frozen `rankingDeadline*` snapshot under separate names. A successful late final sets neither `fallback` nor `completionFailed`.
- **People-only partials:**
  - `SearchPeople` renders in both pages from the partial batch.
  - Journey suppresses the empty cue through `showsNoResults`.
  - Discover suppresses it through `!(search.partial && first.total === 0)`.
  - The failure text is honest in both.

## Scoped limitations (not blockers)

- **Discover empty-list request:** a people-only partial sends `ranked=` empty to `/api/discover/results`. That endpoint (`discover-results.server.ts`) is not in the packet, so I could not confirm how it answers. The same request already occurs today for a final with no titles, so this is not a new path.
- **Files not in the packet:** `ranking-progress.server.ts`, `title-prefix.server.ts` and `search-test-answers.ts` were not supplied.
- **History diagnostics on a late failure:**
  - The row carries `rankerVersion: "essence-text-v1"` although no basic search served.
  - A user abort inside the window records `rankerFallback: "timeout"`.
  - `completionFailed` / `completionAborted` disambiguate both.
- **Rejection delay:** the catch awaits `early.titles` before rethrowing, so the error packet can lag by up to the title lookup's and catalog read's own limits. It errs toward holding admission.
- **Abort during the reading:** `basicList` still starts `literal()` before its abort check. This is unchanged from base and is awaited.
- **Early versus final order:** early rows use the UI `blend` and the final uses the server blend, so rows can reorder, and an alternate cut can show early and then fold away.
- **Taste on the early packet:** `moved` is computed over the title-only list, and a member's first paint waits on the taste load.
- **Extra client fetches:** each partial can trigger another `/api/watchability` call (Journey with a streaming filter) and a Discover results fetch.
- **Naming nit:** in `SearchJourney.tsx`, `pendingTitleLookup = Boolean(partial)` now means "any partial". Behaviour is correct.
- **Declared limitations stand as written:** the pre-late catalog sibling gap, shared `creditCache` siblings, remote SQL after HTTP abort, old-tab mixed-version masking, and no production latency evidence. I do not treat any of them as closed.
