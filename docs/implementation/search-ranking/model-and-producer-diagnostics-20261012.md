# Model parity and historical producer diagnostics

Six existing model files matched in full between the October 12 page container and the pinned diagnostic producer image. Separately, both active search roles matched that producer's model layer, file sizes and markers. The private producer was staged, but its first two comparisons stopped at producer exit before clone queries. These are preparation and diagnostic results for [task406](https://github.com/alp82/goodwatch-monorepo/issues/406), not a latency remedy or a started seven-day acceptance window.

The earlier [initial clone pinning proof](clone-pin-feasibility-20261012.md), published by PR459, remains separate. This document adds model, producer and index evidence; it does not repeat that initial pinning result.

## Model and source comparisons

The [full-byte parity result](model-byte-parity-20261012.json) completed at 2026-10-12 06:41:16.849945 UTC. It read six files totaling **923,875,007 bytes from each source**, or **1,847,750,014 bytes overall**. Both sources matched all six frozen SHA256 values and their markers. One source was the running page container at commit `5dd25de1e48d09bc154340b31be595a2ffd31632`; the other was a retained, never-started container with producer image `sha256:3d698950ee07437a64d9bbc8eaafe2d4638a7f90dde0e57aee133d51b6653a7f`. Stable file identities and page process identity were fenced. The verifier records no container starts, downloads or source-host writes during its own check. These operation counts do not describe all earlier preparation or whole-system activity.

The [active search metadata result](active-search-model-metadata-20261012.json) checks the two actual search roles at commit `927d38b2cca815f02a0b1636ec06f63c24603396`, with their distinct running image. Their model layer matched the pinned producer, no mount covered the model directory, six file sizes matched per role, and all markers matched. It read **768 marker bytes and zero model-content bytes**. Process start ticks and container/root identities were fenced. This establishes layer/metadata/marker parity at those observations; it does **not** establish full-byte equality of the active search files.

The [active-search source comparison](diagnostic-active-search-source-parity-20261012.json) proves all 60 scoped Git mode/blob/path rows equal between diagnostic bundle source `2eb889b4d7ab998f012cda8aadbc2afc8d9dd8ff` and active search source `927d38b2cca815f02a0b1636ec06f63c24603396`. The [page-source comparison](diagnostic-page-source-parity-20261012.json) separately checks those scoped application sources against page commit `5dd25de1e48d09bc154340b31be595a2ffd31632`. Source equality is scoped to the listed ranking, combined-search, runtime, role/lifecycle, encoder-entry helper and dependency files. Neither comparison proves equality of independently compiled artifacts. The pinned producer image supplies external dependencies/models; the separately frozen bundle supplies diagnostic application code.

The staging operation did not repeat the full model-byte reads.

They did not read the producer modules, models, index or private environment. A corrected diagnostic used a separate file bind under writable tmpfs.

The [corrected index/history probe](private-producer-index-history-probe-20261012.json) reached Crate through the unchanged diagnostic boundary. This identifies an index-pointer mismatch independently of the original failure; it does not prove the original producer's exact failing phase or interpretation-cache readiness.

## Retained historical index and preload correction

The [retained manifest probe](private-producer-retained-manifest-20261012.json) found one exact build row for `20261011T041503Z`, with ten file entries totaling **63,078,980 manifest-declared bytes**. Its raw JSON-string SHA256 was `000b58ebaf48d6f51d3298665918e1fefd68985226678a1a00f3e1db1b26e8a0`. The current manifest's `previous_build_id` matched that build, and there was no literal `previous` alias row. This probe verified manifest metadata, not blob presence or content. The publisher [keeps current and previous build rows and their blob digests](../../../goodwatch-flows/windmill/f/search/build_indexes.py), rather than maintaining a `previous` alias.

A separate historical preload leaves the frozen453 ranker, stage and consumer unchanged. It redirects only the exact current-manifest SELECT to a parameterized lookup of the retained October 11 row, then verifies its raw manifest SHA and build ID before releasing response bytes to the loader. Other SQL/blob traffic continues through the original read-only boundary. This prepares **historical clone mechanism evidence**, not current-index production acceptance.

The [first historical comparison result](private-producer-historical-v2-failure-20261012.json) again stopped at producer exit before clone queries, with all owned lifecycle exits proven and the clone still running. Its precise failing phase was not captured. A [local real-HTTP fixture](historical-index-content-length-fixture-20261012.json) then reproduced a concrete preload defect: rewriting the SQL body preserved the caller's old Content-Length, truncating the body at the fake server. The old guard failed; the new guard updates that header only for the exact rewrite and passed. Fixtures cover explicit headers, split writes, both callback overloads, raw-SHA response gating, unchanged unrelated SQL/blob headers and forbidden INSERT bodies. This fixture establishes the defect and fix locally, without retrospectively proving the actual producer failure's cause.

The [completed subsequent historical comparison](private-producer-historical-v3-cap-refusal-20261012.json) passed the producer EOF/exit0 fence: the frozen consumer progressed into the candidate control. At 2026-10-12 08:03:51.366480 UTC that phase refused with `initial_cap_fit_inconclusive`, controller exit1 observed and null server/wall timings. Its failure and release records each report zero queries in that candidate phase. The complete result retains no paired latency frame, so it does not establish a numeric red baseline, candidate latency or parity result, nor does that absence prove zero queries in earlier phases. Cleanup recorded released, pin child exited, producer absent, no remaining owned controllers/holders and the clone still running. No cap or guard was relaxed. The preparation from [PR455](../../../goodwatch-qdrant/diagnostics/clone-preparation/README.md) had not been executed as part of this attempt. No query latency or parity outcome is claimed here. All artifact hashes and byte sizes are pinned in the [evidence audit](model-producer-diagnostic-evidence-audit-20261012.json). Production deployment, organic first-result latency/error coverage and the fresh seven-day acceptance window remain outstanding.
