## Code blocker

**`consumer_cpu0.mjs` `main()` `paired-batch` emit vs `audit_cpu0.mjs` `auditConsumer`: `baselineControllerExit` is missing from the paired row.**

- **Consumer:** the `baseline-batch` emit includes `baselineControllerExit:baseline.controllerExit`. The `paired-batch` emit carries only `candidateControllerExit`.
- **Auditor:** the `cpu0_audit_baseline_changed` gate requires `same(pending.baselineControllerExit,row.baselineControllerExit)`.
- **Effect:** on real output the right side is `undefined`, so `canonicalHash` hashes `"undefined\n"` against the hash of `{code:0,observed:true,signal:null}`. Every real nine-slot run ends `consumerPass:false`.
- **Why tests miss it:** `test_audit_cpu0.mjs` `fixture()` builds both rows from one `base` object that already contains `baselineControllerExit`. No test feeds rows emitted by `main()` into `auditConsumer`.
- **Fix:** add `baselineControllerExit:baseline.controllerExit` to the `paired-batch` emit. Add a test that builds both row kinds through one emit helper shared with `main()`, so the two shapes cannot drift again.

## Fix in the same respin (not independently blocking)

1. **Pre-query contract reasons are erased.** In `controlledBatch`, `readinessEvidence(...)` runs inside the reader's `try`. Its bare `catch` replaces any `ContractFailure` with `cpu0_control_frame_failed`. Reasons such as `cpu0_cold_birth_not_fresh`, `cpu0_clean_stop_unproven` and `negative_insufficient_missing_pages` all surface as a frame error with `failureKind:'readiness'`. The behaviour is fail-closed and terminal, but the pre-query validation becomes undiagnosable. Preserve `ContractFailure` instances in that catch.

2. **The controller's allowlisted `reason` is dropped.** `failureEvidence()` never projects `frame.reason` from `phase-failed`/`failed` frames. `host_cpu_busy`, `negative_missing_pages_inconclusive` and `pin_child_timeout` therefore all read `cpu0_control_phase_failed`. The backend already restricts these to `CONTROL_REASONS`, so a consumer-side allowlist would be safe. `hostCpuEvidence` and `pressureFinalizationFailure` are also not projected.

3. **`resource_metrics_unavailable` evidence is misreported.** `cpu0_guards.resource_limits` emits `{schema,scope,measurementsAvailable:false,overlappingNonAdditive:true}` for that case. `failureEvidence` requires `checkedAt`, `failedChecks` and both deltas, so it sets `evidenceRejected:true` on a legitimate backend shape.

4. **Preflight failure facts are discarded.** `runEntryPreflight` throws `cpu0_preflight_refused` on a non-zero exit without projecting the failure JSON (lifecycle, CPU and host-CPU evidence).

5. **Minor mismatches:**
   - `hierarchyEvidence` caps rows at 32, while `source_cpu` can return 33 when the root is the 33rd row.
   - An oversize response in `transport_cpu0.mjs` surfaces as `cpu0_query_transport_failure`, not `cpu0_query_response_invalid`.
   - If `process.argv[1]` differs from the realpath of the module, `main()` never runs and the process exits 0 with no output.

## Integration dependencies

In that window the controller makes roughly 21 docker CLI calls on baseline and about 45 on candidate (5 s timeout each). It also runs a full `measure_source`, the candidate `manager.request()` (30 s budget), `PinChild.close` (5 s + 5 s) and `commit_handoff`. The backend's own budgets exceed 15 s, and a timeout sends SIGTERM that can land mid-commit.
