M1–M6 are closed in the code paths the original report named, but two narrow evidence-retention and labelling defects remain in the JS. Both fail closed; neither lets a bad run reach `consumerPass`.

## Mandatory findings

### N1. Refusals between a successful preflight and the admission row drop the validated enrolment and exit facts
- **Where:** `source/consumer_cpu0.mjs:219-221`.
- **Trigger:** run with `--raise-own-nofile` while the preflight enrols `raiseOwnNofile:false` (the new M3 gate).
- **Same window:** `consumerBirth()` throwing at `:219`, or `validateAdmissionFrameV2` refusing at `:221`.
- **Effect:** the preflight has already written its handoff and enrolment (`handoffWrites:1`, `enrolmentWrites:1`) and exited cleanly. The only public output is `{kind:'failed',variant,reason,failureKind}`: no `preflightExit`, no receipt or enrolment hash, no successor handoff hash.
- **Fix:** wrap `:219-221` in a try/catch that attaches the same `publicEvidence` shape `runEntryPreflightV2:190` uses: `variant`, `preflightExit`, `preflightReceipt:receipt`, `handoffAccepted:false`.
- **Same class, recommended:** `:226` (`cpu0_client_retained`) and `:228` (`pairedEvidence` refusal) discard a completed phase whose handoff has already advanced. Attaching `previousHandoffSha256` and `controllerExit` there would close it. Leave the identical v1 behaviour alone.

### N2. Audit mode is selected after the output is parsed, so some refusals are unlabelled and the v1 refusal shape changed
- **Where:** `source/audit_cpu0.mjs:96-98`, `:102`.
- **Trigger A (v2):** a valid v7 manifest with an empty or truncated output file. `JSON.parse` throws at `:97` before `selectedAuditMode` is set at `:98`, so the refusal has no `schema` or `variant`. This partly reopens M6.
- **Trigger B (legacy):** the same with a valid v6 manifest. The old source printed `schema:'cpu0-consumer-audit.v1'` and `variant`; this one prints neither. That is a change to legacy v1 output.
- **Fix:** read the manifest, apply the size bound and set `selectedAuditMode` before reading or parsing the output and context files. Unknown or unparseable manifests stay unlabelled, as the existing test intends.

## Non-blocking tightenings

- **Late birth refusal.** An unreadable controller birth is refused only at `query-ready`, after the cold stop and pressure. Refuse on spawn instead.
- **Distinct births.** The audit accepts the same `{pid,startTicks}` for all 18 phases. Require 18 distinct births, none equal to the enrolled preflight identity.
- **Monotonic order across ledgers.** Nothing orders the entry ledger's monotonic time against the cache baseline, or the cache baseline against the working-set sample. The distinct-time fixture itself has entry at 25 and cache baseline at 10 and passes.
- **Failure-path binding.** `overheadFailureEvidence` is not checked against `controllerBirth`; the birth is only carried alongside it.
- **Node provenance in the audit.** The audit CLI takes `nodeProvenanceSha256` from the context file rather than hashing the staged `node-provenance.json`.

## Test coverage versus protocol assumptions

- **Composed audit.** The nine-pair fixture reuses one controller birth (303/99/301) and one instant for every phase, so chain-wide ordering and birth uniqueness are untested.
- **Pipe tests.** They now cover candidate, wrong birth, null before and after ready, and backend failure, but with a Node stand-in, a fake `queryBatch` and only the `control-native-title` tag.
- **`mainV2`.** It is never run end to end; only the two extracted helpers are tested, which is why N1 was not caught.
- **Registration digest.** `consumerRegistrationSha256` is still accepted from the first entry ledger and then pinned.

## Unresolved backend and external integration (not JS defects)

- **Backend mode selection.** The v2 consumer still launches the preflight and controller with v1-identical argv; ABI2 selection on the backend must be confirmed at combined closure.
- **Entry baseline inspector.** The JS now requires the entry-ledger baseline inspector to be this phase's controller; the backend must emit it that way.
- **Lock arithmetic.** `lockedBytes` must equal the sum of `dataPages × pageBytes` over the four classes, and each class must have at least one page.
- **Opaque values.** The `consumerArgvHash` recipe, the registration digest definition and `sharedControlIdentity` are shape-checked only.
- **Byte-for-byte recipes.** The handoff file, exe hash and cgroup hash encodings must match Python exactly.
- **Stopped headroom.** The schema has no timestamp or source binding.
