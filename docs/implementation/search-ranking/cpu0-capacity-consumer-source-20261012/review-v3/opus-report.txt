## Limitations

These are not blockers.

**New observations on the two corrections**
- The refusal label comes from the manifest's `schema` field before its SHA is checked. A wrong-hash file claiming v7 produces a v2-labelled refusal.
- `completeEntryAdmissionV2` is exported and does not revalidate the receipt before retaining it; it relies on its only caller having done so.
- The admission-refusal fixture injects `readBirth` and does not assert the specific reason per case. The default `/proc` birth read is not exercised in the v2 path.
- The manifest and output files are read whole before their size bounds apply (unchanged behaviour).
- A legacy refusal with an unknown or unparseable manifest is unlabelled, as intended.

**Carried over from the V2 report, still not implemented**
- **Later phase refusals:** `cpu0_client_retained` (`consumer_cpu0.mjs:229`) and a `pairedEvidence` refusal (`:231`) still discard a completed phase whose handoff has advanced.
- **Late birth refusal:** an unreadable controller birth is refused only at `query-ready`, not on spawn.
- **Distinct births:** the audit does not require 18 distinct controller births, nor that they differ from the enrolled preflight.
- **Monotonic order across ledgers:** entry ledger, cache baseline and working-set sample are not ordered against each other.
- **Failure-path binding:** `overheadFailureEvidence` is not checked against `controllerBirth`.
- **Node provenance in the audit:** `nodeProvenanceSha256` is taken from the context file, not hashed from the staged file.
- **Registration digest:** `consumerRegistrationSha256` is accepted from the first entry ledger and then pinned.
- **Coverage:** `mainV2` is never run end to end, and the composed nine-pair audit fixture reuses one controller birth and one instant.
