# Prepared read-only BM25F acquisition

This standalone reader is prepared for root review. No Qdrant host or production endpoint has been contacted. Fourteen local fixtures passed; their HTTP requests were confined to loopback. The original plan and source bindings remain in `../offline-bm25-retrieval-plan-20261013`.

`PLAN-v2.json` corrects the original arithmetic: 42,934 unchanged IDs require 85 batches of 500 plus one batch of 434, hence 86 point reads plus two collection metadata reads (88 requests). The original plan incorrectly said 87 plus two; the full-population local fixture caught this before execution. The successor records the original SHA and preserves all ID ordering and safety limits.

The only HTTP operations are GET `/collections/media_fingerprint_v1` before/after, and POST `/collections/media_fingerprint_v1/points?timeout=8` with exact public batch IDs, `with_payload:false`, and `with_vector:["terms_bm25f_v1"]`. This is point retrieval, without query/search/upsert/update/delete. No retries, redirects, SDK inference, app imports, embeddings, JeV, user data or history calls occur. `QDRANT_URL` must already be configured; no default endpoint is used. The deployed source's 6334-to-6333 REST port mapping is retained. Credentials from `QDRANT_API_KEY` remain in memory and headers only; no addresses, credentials, raw server bodies or errors are emitted.

A request has a wall timer over headers and the entire body, at most 10 seconds and clamped to the original 600-second global remainder. The global deadline starts before stdin. Each response is bounded to 16 MiB and aggregate response bytes to 1 GiB. Only one response is buffered at a time; the corpus is not accumulated in RAM. Sparse entry bounds are 32,768 per point and 134,217,728 total. These are refusal limits, not observed sparsity or fit claims.

Output has a separate 2 GiB cap because row output includes both observed numeric decimals and reconstructed float32 values. `writeFrame` awaits the actual Writable callback and, on backpressure, drain. It retains a sanitized listener on terminal failure to catch the subsequent asynchronous error event. A true-return asynchronous write failure is tested. The request/body, output backpressure and publication checkpoints all consume the same global budget. A terminal line alone never suffices: actual CLI exit zero, physical EOF, zero stderr and strict complete-stream validation are required. Any refusal leaves a consumed partial output; it is not retried or treated as complete.

Each row is aligned to the exact title-table ID order, including explicitly missing points. Present sparse vectors require strictly increasing unique uint32 indices, equal array lengths and finite nonnegative values at most one. Parsed short Rust float32 decimals such as `0.33333334` are retained in `observedValues`; `float32Values` explicitly records `Math.fround` reconstruction. Exact equality between these two representations is not required. A positive value that underflows binary32 is invalid; exact stored zero is valid. The original document builder ordinarily produces positive saturated weights, but Qdrant's valid sparse numerical representation permits zero. Present empty arrays are valid empty documents. Missing/null/omitted/malformed vectors are separately invalid or missing; they never become valid zero documents. There is no L2 normalization. Unexpected IDs, duplicate points, unrequested vector names and nonnull payloads cause fixed-category refusal without publishing their contents.

The collection observations expose only an explicitly public projection (modifier, count, status, shard/replication counts and its hash). The requested sparse vector must exist with absent/null/none IDF modifier. Unequal projections refuse. Equal observations do not prove a transactional snapshot or equality with the earlier index build. Current sparse values may have drifted; pinned index term IDs/IDF and current document weights therefore form a qualified mixed-snapshot study input. Unknown stored term IDs must be retained and reported by the subsequent validator; they receive no invented vocabulary mapping.

Production BM25 and per-unit BM25 contribute their top-300 hit maps, not exact dots of every union candidate. Absent top-list hits become zero in `fromMap`. A later offline study must reconstruct the original top-list gates, join membership and population normalization separately from any all-pool sparse-dot alternative. The pinned 42,934 rows omit other live collection candidates, so cohort-local top lists are not live production candidate parity. No quality or production latency conclusion follows from this acquisition.

## Review and reproducibility

Run only the local fixtures:

```sh
node --test test-reader.mjs test-driver.mjs
```

The exact output is retained as `tests.stdout`/`tests.stderr` with the receipt and source manifest. The full 42,934-ID tests enforce serial request ordering and the exact REST body; a real subprocess DataURL driver test proves 88 requests, complete row output, actual CLI zero/EOF and the embedded reader SHA. Physical services, current server API compatibility and production vector contents are not tested.

`build-driver.mjs` generated `eval-driver.mjs` once with O_EXCL. The driver authenticates its embedded reader bytes before DataURL import and delegates to the same `runCli` input/hash/deadline/endpoint implementation. Its expected reader SHA is frozen in the artifact. It does not require a source file on a host or container. A modified reader SHA is tested to refuse before input or requests. Root can place this public driver text in the argv of Node inside an already running search-role container, with the exact plan on stdin and existing environment credentials in RAM; root owns any SSH/Docker invocation, outer watchdog and O_EXCL output/hash collection. Nothing here authorizes host execution before root's concrete source review.
