I found no concrete operational, safety or spec blocker in the frozen recovery source. This is a read-only review: I executed no tests, computed no hashes, and make no runtime, latency or owner-approval claim. The 100/19 test counts are the author's.

## Findings (all non-blocking)

**N1. The live binding to the config-proof hashes cannot be confirmed from the packet.**
- `recovery.py:121` requires `sha(canonical(non_cpu(old)))` to equal `OLD_HOST_SHA` (and likewise for NEW). The read-only script that produced `root-readonly-created-config-public.json` is not in the packet.
- The proof's scalar hashes do look like SHA256 of JSON `null` and `false` (recognised from memory, not computed), but that says nothing about the separators or excluded fields used for the whole-dict hash.
- If the generator differed, the first root run refuses with `recovery_config_proof_changed` at the first parity check. That is before the attempt receipt and before any mutation, so it fails closed.
- Minimal fix: none in source. Root should confirm the generator used compact sorted JSON over HostConfig minus exactly `NanoCpus`, `CpuQuota`, `CpuPeriod` before invoking.

**N2. DESIGN-v2's test gate is only partly met by `test_recovery.py`.**
- Not exercised:
  - `proofs()` on the real frozen bytes or a modified proof (it is always patched, `test_recovery.py:201`);
  - a mismatched OLD receipt hash;
  - a symlink or inode change in the admission directory;
  - the inverse null pair or a non-null OLD value;
  - a primary refusal combined with a lock-close failure (only the success path is tested, `:291`).
- The composed fixture also mocks `prior_census`, `port_closed`, `own_stopped_placement`, `admission.host`, `collection_shape`, `StartEngine`, `attest`, `pair_snapshot` and `read_handoff`. "Composed" therefore covers ordering and ledger shape, not those boundaries.
- I traced `proofs()` by hand against both real blobs and it accepts them; the packet also carries `initialMode`, and `build_packet.py:64` runs `proofs()` when it sets that.
- Minimal fix: add those five cases in a successor, or have root accept the gap explicitly.

**N3. A pre-publication `/version` transport failure is labelled `recovery_start_unknown`.**
- `recovery.py:272-310` uses that reason for every transport or framing failure, including the GET.
- The typed ledger stays correct (`actionState: not-issued`, `attemptObserved: false`), but the top-level `reason` reads as if a start may have been issued.
- Also unverified: the parser refuses chunked responses (`:299`). My recollection is that dockerd sends `Content-Length` for a `/version` body of this size, but I could not check that here.
- Minimal fix: have `version()` re-raise transport failures as `recovery_normalization_refused`.

**N4. A failure after the handoff is committed does not carry the completed result.**
- If `read_handoff` or `publish(SUCCESS_NAME)` fails (`recovery.py:496`, `:508`), the reason is `recovery_attempt_publish_failed` and `recoveryCompletedReceipt` is not attached. That attribute is only set on lock-close failure (`:523`).
- The executor still reports `observedCommittedHandoffSha256` (`executor.py:236-238`) and continuation stays false, so this is not unsafe.
- I estimate the result at well under the 64 KiB cap, from reading `birth_admission`.
- Minimal fix: attach `result` to the error when `publish(SUCCESS_NAME, …)` fails.

**N5. Small deltas from the hash-bound DESIGN-v2 text.**
- Two reason codes are not in the v2 list: `recovery_closure_unproven` and `recovery_mode_mismatch` (`reason_codes.py:6,27`).
- `recoveryCompletedReceipt` is an extra entry in `FAILURE_FIELDS` (`executor.py:247`).
- Both are additive and stay closed. Root should acknowledge them, since the acceptance is bound to the v2 hash.

**N6. Operational notes, all failing closed before publication unless stated.**
- **Cgroup walk:** `own_stopped_placement` walks all of `/sys/fs/cgroup` (`recovery.py:171`). A scope that vanishes mid-walk gives `recovery_placement_unknown`. All three calls are before publication.
- **Post-publication re-inspect:** two docker CLI inspects run between the attempt receipt and the POST (`:442`). A transient failure there spends the one attempt without a start. This matches the design.
- **Admission staleness:** nothing bounds the time between the last `admission.host` (`:425`) and the POST. It is realistically under two seconds; the worst case is roughly a minute of inspect timeouts.
- **Strict POST parsing:** a 304 or oddly framed reply after the POST becomes `issued-unknown`. That is conservative, but it happens after the action.
- **Cosmetic:**
  - `http.client` and `stat` are unused imports (`:8,14`).
  - A receipt-identity mismatch is labelled `recovery_placement_unknown` (`:422-423`).
  - A 204 with a non-empty body would be labelled `issued-nonzero`.
  - On a failed first call, the cleanup RPC arguments still carry `recoveryProof`, which the executor ignores (`outer_local.py:173`).
