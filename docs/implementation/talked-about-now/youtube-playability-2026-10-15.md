## Size of the problem

The starting production snapshot had **30 kept YouTube associations, representing 30 unique videos**. All 30 were checked from Germany. **One of 30 (3.3%)** was unplayable and country-excluded: Narnia's `O8hR2dQGv0k`. The remaining 29 returned `OK`, allowed embedding and included DE/US/GB in their explicit country list. The same one of 30 excludes the US and UK; this is country-metadata evidence, not a claim that browsers in those countries were used. The captured JSON records each video's HTTP/player verdict, country count and DE/US/GB membership.

## Method and tradeoffs

The supported [YouTube Data API video resource](https://developers.google.com/youtube/data/reference/rest/v3/videos) is the best ongoing method: `videos.list(part=contentDetails,status)` returns region restrictions and embedding/privacy/upload status, independent of the worker's country. The [list method costs one quota unit](https://developers.google.com/youtube/data/reference/rest/v3/videos/list); batching 50 IDs takes two calls for the current 82 unique matched videos, before caching. Google's [getting-started guide](https://developers.google.com/youtube/data/getting-started) documents the default free quota. No billing, paid inference or OpenRouter call is added. No API key was created or changed.

The implementation supports that method immediately if the owner supplies the existing optional `YOUTUBE_API_KEY`. Without it, the public watch page supplies a useful free fallback:

- Require the response's video identity to match the requested ID.
- Require explicit `availableCountries` metadata containing DE, player status `OK`, and `playableInEmbed=true`.
- Reject an explicit region exclusion as `youtube_region_blocked_DE`.
- Reject unavailable/private/deleted, non-embeddable and age-restricted responses. A missing API item is `private_deleted_or_missing`; watch-page error responses without identity are `private_deleted_or_unavailable`.
- Treat consent, bot/sign-in challenges, absent/malformed metadata, oversized pages, timeouts and HTTP failures as unknown and **drop**, without misreporting them as confirmed geo-blocks.
- Do not use `gl=DE` or language preferences as a substitute for country metadata. Do not use oEmbed as positive evidence. No video files are downloaded.

Watch pages are undocumented and datacenter requests can be challenged; that can hide otherwise good videos. **The production worker preview returned 1 playable, 3 region-blocked and 78 unknown among all 82 videos. Consequently the no-key fallback currently suppresses every YouTube item under the editorial gate on that worker, including 29 previously kept videos verified as playable from residential Germany. The API key is needed for reliable positive checks on the actual worker fleet.** The fallback prioritizes quality over quantity. A worker outside Germany can also produce conservative false negatives, but cannot approve a country-excluded video because DE membership remains mandatory. Sampled workers' German egress was checked during diagnosis; it is not assumed from a language/location query parameter.

Observations use at most four concurrent requests, 4 MB per watch response, a 1,000-video corpus cap, and bounded HTTP timeouts. Cache successful/definitively blocked observations for one hour and unknown observations for five minutes. Cache identity includes post ID, content hash and video ID. Future/stale observations cannot pass the pure judge. Each normal discovery re-judge refreshes expired observations, including ingestion's `hydrate=False` path. `force_playability=true` (CLI `--force-playability`) bypasses the cache for immediate rechecks. A video changing just after a successful check can remain visible until the next re-judge after expiry, plus the webapp's existing cache lifetime; this is periodic validation, not continuous playback monitoring.

All persisted observations are structured `playability:` entries in `doc.social_relevance.reasons`; the existing `relevance-1` version and schema are unchanged. No other table, Valkey, flag, secret or schedule is written by this rollout. The existing restricted re-judge writer and stale-upsert protection remain intact.

## Verification

The production Narnia pattern was first reproduced as a failing relevance-judge test (`keep != drop`), then passed with the fix. New tests cover real AU/NZ metadata, allowed/blocked/empty country lists, successful and malformed player responses, missing/changed identity, private/deleted, embedding/age restrictions, API batch boundaries/fallback, transport errors, response size/closure, cached/future/expired evidence, and duplicate selection that promotes a playable video or news article. The ingestion `hydrate=False` call path is tested through restricted re-judge persistence.

The original 632-row editorial regression remains an editorial evaluation: its old corpus did not measure playability. Its offline harness explicitly assumes availability only for that evaluation, labels the assumption in its output and leaves the captured fixture unchanged. Production has no default assumption. Separate playability tests use captured or controlled responses.

With isolated localhost CrateDB 5.10.16: **60 existing social tests passed, 12 skipped; 12 new playability tests passed**. The 12 pre-existing tests that require mutations to existing social tables were not enabled. Real-database coverage includes typed reason arrays, all 632 decisions, BIGINT keys and stale-write protection. Python compilation and `git diff --check` pass. Windmill metadata/locks were regenerated with the same CLI version as deployment (1.803.0).

## Owner-provided key (recommended for reliability)

Create or select a Google Cloud project, enable **YouTube Data API v3**, and create an **API key** under APIs & Services → Credentials. Restrict the key's APIs to YouTube Data API v3; do not use browser/referrer restrictions for this server workload. Optional IP restrictions must cover every Windmill worker's public egress. Do not enable billing or buy quota for this feature. Store the key as a **secret Windmill variable `u/Alp/YOUTUBE_API_KEY` in workspace `goodwatch`**, then run `f/social/rejudge` with `{"apply":false,"force_playability":true}`, inspect its counts, and run with `apply=true`. The existing settings loader already reads that exact variable; no code change is required.
