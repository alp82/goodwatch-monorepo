The sections below retain the original diagnosis, causal probes, actual implementation and verification limits.

The deployed homepage at the start of this investigation had two reproducible interaction costs: page-wide style invalidation from the opening's boot-gate selectors, and React work in the unchanged Browse subtree while the visitor types. Address both first. A browser-only probe combining those changes reduced the slowest observed interaction from 296–312 ms to 168–192 ms under the same 6× CPU emulation. Nothing was deployed, and these lab results do not establish that Google's historical mobile INP of 432 ms is fixed.

Desktop LCP has a separate delivery bottleneck on a limited connection: the large room AVIF finishes immediately before LCP. Optimizing that image's bytes and responsive selection is the next loading improvement; it already has early discovery and high fetch priority.

## Mobile: first focus invalidates most of the page

The tight reproduction is a fresh mobile browser, 6× CPU slowdown, wait for hydration, tap `#start-search-input`, and type `funny sci-fi`. The check exits 1 when the maximum observed Event Timing duration exceeds 200 ms. It does not calculate Google's field p75 or every detail of the `web-vitals` INP selection algorithm.

Unmodified runs:

| Run | Search tap | Worst keyboard event | Long tasks after beginning interaction |
|---|---:|---:|---:|
| `input-only-6x` (trace) | 312 ms | 208 ms | 21 |
| `baseline-6x` | 296 ms | 200 ms | 23 |
| `baseline-final2` (trace) | 312 ms | 224 ms | 23 |

At 4× slowdown, the mood-then-typing sequence reached only 160–184 ms. The evidence is a reproducible slower-device failure, not a claim that all mobile visits exceed 200 ms.

The first focus is dominated by browser style work, not a long `click` handler. In the `input-only-6x` trace, the click's Event Timing duration is 312 ms: 288 ms input delay, 3.3 ms handler processing, and about 21 ms presentation. The style tasks before that click contribute to the reported delay. Its interval contains 204 ms of style recalculation and a pass affecting 1729 elements. The second baseline trace shows 212 ms and the same element count.

The opening stylesheet has page-wide selectors such as `html:has(#start-boot-gate:not(:checked)) [data-site-header]`. The selector-stats trace identifies these rules as expensive. That trace deliberately enables costly selector instrumentation and is used only for diagnosis, not the timing comparison. [Opening selectors](../../goodwatch-webapp/app/ui/start/opening/opening.css), [Chrome selector profiling](https://developer.chrome.com/docs/devtools/performance/selector-stats).

To test causality, a response interceptor changed only the opening stylesheet **in the test browser**: for the known fresh guest with the unchecked gate, the matching `html:has(...)` condition became `html`, and the checked-gate condition became an impossible selector. It leaves the truth values of those conditions unchanged for this test visit while eliminating the relational lookup. This is an isolation probe, **not a valid production replacement for all visitor states**.

In the traced selector-only probe, the first tap fell to 160 ms; style work in its interval fell to 23 ms, with at most 21 elements in a pass. Other selector-only runs had whole-visit maxima of 216–256 ms. A later keyboard interaction still reached 288 ms: fixing the first focus alone is insufficient.

Recommended change: remove the root-level relational boot-gate dependency from the header/cover's interaction-sensitive style path, retaining the correct first-visit, returning-visit and reduced-motion behavior. Do not blindly switch to an inline `<html>` attribute: [boot-gate.ts](../../goodwatch-webapp/app/ui/start/opening/boot-gate.ts) documents an earlier hydration problem with that approach. Keep SSR and hydration consistent and test those states explicitly.

## Mobile: each draft update reaches unchanged Browse cards

The field calls `setDraft` on every `onChange` in [StartSearchBar.tsx](../../goodwatch-webapp/app/ui/start/search/StartSearchBar.tsx). That changes the `query` state held by [useStartQuery.ts](../../goodwatch-webapp/app/ui/start/stage/useStartQuery.ts), whose owner is the entire `GuestStart` tree in [_index.tsx](../../goodwatch-webapp/app/routes/_index.tsx). Its siblings include `<StartBrowse data={browse} />`, even though typing does not change `browse`.

The trace shows Browse work during typing, including `MoodRail`, `ArrivalsRail`, `GenreCloud`, poster-card marks and repeated user-data hooks. The 800 ms search debounce limits network requests; it does not prevent these synchronous draft renders. The first keypress in one trace spent about 70 ms in the input event and about 91 ms recalculating styles during that event's broader native text-input path.

A second browser-only probe cached `StartBrowse`'s returned element while its `data` reference was unchanged. Its descendants could still process their own updates. This reduced post-action long tasks from 23 to 9 in the isolated run. It did not fix the first focus (360 ms), which agrees with the separate boot-selector problem.

Recommended change: keep the live typing draft within the search control, committing to the page's query state only when searching/clearing, and/or memoize the unchanged Browse subtree with stable inputs. Preserve URL commits, clearing, preset selection, blur/submit behavior, and child control updates. Validate the change against the same touch and typing sequence rather than only a load audit.

## Implementation

Implemented in an isolated worktree based on `884dbdcc5a1abe72e0f731e1d3e6cc4b8277af4c`; the retained checkout's existing local changes were preserved.

- **Boot selectors:** moved the pre-paint checkbox and its session script before `SiteChrome`'s header and main. Opening styles use scoped sibling selectors instead of root `:has` conditions. Server rendering and hydration retain the checkbox-property contract; fresh, returning, reduced-motion, member and client-navigation states have regression coverage.
- **Typing:** the live draft stays in `StartSearchBar`. Search, clear and URL navigation commit/reset through an explicit revision; mood picks preserve the draft. The heavy Browse contents have an SSR Suspense boundary: server links remain in place, while an early search event can hydrate the stage without synchronously walking every Browse card. `StartBrowse` skips unchanged parent renders while its own controls still update. Debounce, submit, preset, blur, history and privacy behavior remain covered.
- **Search URL updates:** the router snapshots `window.scrollY` even with `preventScrollReset`. The new clear trace exposed about 113 ms of forced style/layout when navigating immediately after the query DOM commit. URL replacements now run after a rendering opportunity, with cancellation/coalescing and a history-generation guard. Input/query clearing stays immediate; hidden tabs write via a task without waiting for a paused animation frame. Tests cover rapid edits, Back/Forward, unmount and hidden-tab commits.
- **Room delivery:** landscape AVIFs are 36,344 bytes at 800px, 73,994 at 1280px and 97,278 at 1536px, replacing the single 157,342-byte landscape file. The phone file is unchanged. Picture and HTML-head preload share the exact media, sizes, candidates and CORS mode. Removed the guessed 103 hero preload that could fetch the wrong orientation/resolution; stylesheet, font and mark hints remain. See the [encoding and quality notes](../../goodwatch-webapp/app/img/start-room/README.md).
- **Shared loading:** notification code, container and CSS now load on demand. Pending notifications preserve rich Undo callbacks through an offline load and retry on reconnect or the next notification. Swiper styles belong to the two carousel wrappers; its unused icon font remains stripped. No performance caps were raised.
- **Mood panel:** placement reads are batched after a rendering opportunity; resize bursts coalesce and await the block's motion with a bounded fallback. The panel no longer polls geometry each animation frame. Focus follows placement and respects a visitor who already entered the choices; Escape and outside-click behavior remain covered.
- **Existing field events:** adapt PostHog's existing INP capture before SDK 1.295 copies native prototype getters into empty objects. Only fixed target categories and numeric timings are added; search text, DOM IDs, raw selectors, labels and script URLs are excluded. Per-entry presentation estimates are named as estimates. No duplicate observer, event stream or SDK upgrade.
- **Regression command:** `./bench.sh cwv` exercises trusted touch/keyboard interactions and desktop loading in the pinned browser, records each action and fails on the explicit lab thresholds. It blocks requests that could write to production. This is an Event Timing regression proxy, not Google's field p75.

### Root scroll-style invalidation

The wider selector probes did not consistently remove clear/mood latency. The diagnostic selector-stat run is
excluded from timing comparisons: instrumentation increased clear's measured duration to 4096 ms. It was used to
identify invalidation sources, not as a threshold pass. Its debug trace directly attributes root inline-style
mutations to `InstantRouteScroll.tsx` (set `scrollBehavior = "auto"`, force `getComputedStyle`, then remove it two
frames later). Debug stack-frame line numbers are **one-based**, unlike CPU Profile call-frame line numbers; the
mapped `shell-DY573wMK.js` line 10 columns 26799/26902 identify those two source statements.

That helper keys page changes by `pathname + search`, so search-state URL replacements with
`preventScrollReset: true` still trigger document-wide style work. The trace contains repeated passes over
1430–1746 elements; generic universal, pseudo-element and divide/space selectors become expensive because the
whole tree is being recalculated. Their presence in the cost table is not proof that they caused invalidation.
The hypotheses about remaining legacy root, stage and focus `:has` rules are therefore not implemented as CSS
changes. The narrow fix uses the committed router scroll-restoration flags to skip the root override when a
same-path query update explicitly preserves scroll, retaining real page changes, saved history offsets and hash
behavior.

A separate Done trace identified a forced shelf geometry read from its existing observers. Subsequent shelf
measurements now coalesce after paint, while the initial placement remains synchronous so covers never flash over
controls. The existing observation sources and cover visibility/flip rules are retained.


### Status and tooltip selector invalidation

After the scroll fix, the residual clear trace has **zero HTML style mutations**. It instead records a BODY and
stage invalidation immediately after React removes the reading content. Blink's invalidation set lists **52
selectors**: 50 utilities generated by the `stacked` variant's `&:is(owner:has(face), owner:has(face) *)` shape and
two tooltip `group-has-[:focus-visible]` descendant rules. This is direct invalidation evidence, distinct from the
incidental expensive selector rows in the earlier whole-tree cost table.

Two controlled browser-only checks on the same generator, with unchanged markup and no page errors, confirm the
family's effect: removing only those 52 nonmatching homepage rules gives a 184 ms whole-flow maximum (176 ms clear),
and reshaping the 50 status selectors plus removing the two tooltip rules gives a 192 ms maximum (192 ms clear).
The latter preserves the status predicate and specificity exactly. Neither probe is used as the final production
measurement.

The implementation splits `stacked` into explicit owner-self and owner-descendant selectors, keeping the same
`:has([data-status-face])` predicate, container thresholds and media conditions. A static `hasStatus` flag was
rejected because a status component can fall back to a Seen face as tracking state changes. Installed Tailwind
4.1.5, its optimizer and Vite's final esbuild CSS minifier retain the narrow form. Native Chromium compared
**148 computed-style states** from actual SplitFrame SSR, covering viewport/container widths, compact/big frames,
status/Seen faces, dynamic status removal/restoration and hover: every old/new result matches.

The Ready switch's button and tooltip are already direct siblings. A named `peer/ready` and
`peer-focus-visible/ready` replace its two broad focus selectors while preserving the wrapper's hover behavior,
touch peek and ARIA link. QuickTable's self-only `:has` rule and the unrelated legacy root/stage selectors are
unchanged. The actual-component tests cover guest/member, phone/desktop placement, on/off, keyboard focus, toggle
and touch peek expiry; a final native browser check additionally exercises the compiled page stylesheet.
