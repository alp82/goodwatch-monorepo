# Better Auth adapter and secondary-storage inventory

Research date: 2026-10-14. Resolves the research questions in [#531](https://github.com/alp82/goodwatch-monorepo/issues/531), using [#528](https://github.com/alp82/goodwatch-monorepo/issues/528) and [the map #529](https://github.com/alp82/goodwatch-monorepo/issues/529) as the design baseline. This is a source inventory and design correction, not an implemented CrateDB adapter.

## One-paragraph answer

Better Auth 1.7.7 can use durable CrateDB sessions with Valkey secondary storage: an individual session lookup falls back on a missing key when `storeSessionInDatabase: true` and `preserveSessionInDatabase` is off, and the OAuth provider **requires** that database copy. It does not fall back on a thrown storage error, malformed entry, session-list lookup or batch lookup, and it does not warm a missing session entry. The strict adapter needs key reads, id reads, `in` batches, explicit list plans, hook reads and native conditional atomic operations; the tables below inventory those shapes. Applied CAS writes can return zero after failover (#530), so recover ownership from an atomic receipt/tombstone or throw and fail closed; Better Auth cannot infer the winner itself. Provider tokens support hashes, but core session tokens have no hash-storage option, Google tokens need reversible encryption, and MCP's default 30-second refresh retry window stores an encrypted token response. The stock Redis package's five required operations are single-key and compatible with Cluster routing at runtime, but its declared client type is standalone Redis and its `listKeys`/`clear` helpers are not Cluster-safe; implement the small five-method `SecondaryStorage` contract against the existing Cluster. These findings refine the key map and remove Valkey-only sessions from #528's choices. [Session source][session-read], [provider requirement][provider-init], [hash options][provider-hash], [Redis source][redis-source], [Cluster routing][cluster-routing], [#530 evidence](https://github.com/alp82/goodwatch-monorepo/blob/research/cratedb-cas-proof/docs/research/auth-on-cratedb-verification.md).

## Reading the allowlist

Tables use logical model and field names before factory renaming. Bare fields mean `eq`; all simultaneous predicates use `AND`; brackets mean a predicate may be absent. `in` is an operator, not a SQL scan requirement: implement it as key fan-out where possible. `eq null` must match a null value, not the string `"null"`. Missing optional fields are **not** implicit null predicates. At the custom adapter boundary the factory normalizes omitted operator/connector/mode to `eq`/`AND`/`sensitive`, transforms field names and adds default dates/ids. Match normalized shapes and validate every predicate; preserve explicit limits, offset, sort, projection and update/set fields. [Where normalization](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/factory.ts#L485-L631), [adapter contracts](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/types.ts).

Use native `consumeOne` and `incrementOne`; do not rely on the generic snapshot fallbacks on CrateDB. `consumeOne` returns the deleted row or null. `incrementOne` returns the post-write row or null and **must support `increment: {}` with nonempty `set`**: OAuth rotation/revocation uses it as a conditional-set primitive. Without a transaction implementation the factory invokes the callback sequentially without rollback. This inventory does not re-prove the CrateDB guarantees from #528. [Atomic contracts/fallbacks](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/atomic-fallback.ts), [transaction fallback](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/factory.ts#L850-L895).

### Factory and hook expansion

- With joins disabled, `session → user` and `account → user` add **`user.findOne(id)`**; `user → accounts` adds **`account.findMany(userId, limit:100)`** by default. A limit in the join options overrides 100. The factory calls the **custom adapter directly** for these extra queries. [Join fallback][factory-joins].
- Every `deleteWithHooks(where, model)` adds **`findMany(same model, same where, limit:1)`** before `delete`; `deleteManyWithHooks` adds **`findMany(same model, same where)`** before `deleteMany`. This happens even without application delete hooks. `consumeOneWithHooks` can add `findMany(hookWhere,limit:1)` when before-hooks exist and no snapshot was supplied. Verification consumption passes its latest-row snapshot. Missing these reads can suppress deletes/hooks: the helpers catch pre-read errors. [Hook implementation][hooks].
- `findMany` without an explicit limit is normalized to **100**, or `advanced.database.defaultFindManyLimit`. This applies to delete-hook snapshots and refresh-family enumeration too: a safety-critical sweep must not assume it has enumerated every row when there are >100. An adapter must not silently ignore the requested limit; the build needs pagination/bounded populations or an upstream change for complete hook planning. [Factory default](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/factory.ts#L1199-L1226), [family enumeration][family-revoke].

## Atomic outcomes, CrateDB failover and consumed tombstones

The [#530 primary-failover experiment](https://github.com/alp82/goodwatch-monorepo/blob/research/cratedb-cas-proof/docs/research/auth-on-cratedb-verification.md) reproduced applied CAS UPDATE/DELETE returning **rowcount 0 to their original caller**, without another consumer. Its [committed observations](https://github.com/alp82/goodwatch-monorepo/blob/research/cratedb-cas-proof/docs/research/cratedb-cas-proof/observed-results.json) are primary experimental evidence, incorporated here without rerunning that cluster. Therefore #528's **“gone means another caller consumed” is false**. Business predicates must be checked before a narrow key/seq/term write; adding them to that CAS write was rejected in #530. Atomic application and knowledge of ownership are separate requirements.

Better Auth does not accept SQL rowcount as the native primitive's result: **return a row on known success, null on a known guard miss, or throw on indeterminate/error outcomes**. Returning numeric 0 is outside the contract (although provider `if (!won)` would treat it as failure); returning numeric 1 is not a row either. It has no first-class indeterminate result and no automatic operation-ownership recovery. [Atomic API contract](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/index.ts#L463-L508), [factory native dispatch](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/factory.ts#L1382-L1549).

| Primitive/caller | Null (or incorrectly returned numeric 0) | Thrown error |
| --- | --- | --- |
| DB `consumeVerificationValue` | Latest-row `consumeOne` null stops the path; does not delete older identifier rows or fire delete.after; caller receives null | Propagates from consume; expiry checks and caller work do not run. A later `deleteMany(identifier)` error also aborts even after successful consume. [core consumption][verification-consume], [consume hooks][hooks] |
| OAuth auth-code exchange | Tries to delete tokens bearing that authorizationCodeId, then returns **400 invalid_grant**; no token issuance | Escapes the await, so no issuance and no null-branch replay cleanup; outer error handling reports failure. | Password reset / account-delete link | Invalid token response; no password change/account deletion | Escapes before the mutation. Generic fallbacks are a different layer: `consumeOne` checks `deleteMany` rowcount, maps 0 to null without retry, and rejects counts other than 0/1. `incrementOne` retries from a newly read snapshot on rowcount 0 (up to five attempts), returns null if a later read misses the guard, can return a no-op snapshot without writing, and throws after retry exhaustion; DB errors propagate. Those retries are unsafe for an ambiguous already-applied logical increment unless the native adapter adds ownership recovery. OAuth's revoked=null gate prevents a second rotation of the same parent, but cannot tell the original writer it won. Use native methods. [Fallback source](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/atomic-fallback.ts#L130-L249).

After an ambiguous parent rotation, a later HTTP refresh sees `revoked`: within MCP's reuse interval it can only replay a **stored encrypted complete response**. If the first attempt stopped before child creation/replay storage, no response exists and it returns invalid_grant. Outside the window it invalidates the client+user family. Thus the 30-second retry mechanism cannot repair an interrupted mint chain by itself. Throwing on indeterminate ownership fails closed but may strand that refresh grant and require reauthorization. [Revoked-token branch](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/oauth-provider/src/token.ts#L1899-L1928), [replay storage][rotation-replay].

A **consumed-tombstone CAS UPDATE can satisfy the logical `consumeOne` contract**, provided the custom adapter makes the row behave as deleted everywhere: atomically gate on unconsumed state using the read version, retain a unique operation id and the original logical row, return that original row only to the winning invocation, hide tombstones from all finds/counts/joins/updates, and return null to different consumers. Physically deleting later is an implementation detail. After zero/error, a same-invocation receipt proves ownership; mere absence, a changed version or a generic consumed flag does not. An HTTP replay is a different consumer and must not regain the single-use credential. This is an adapter design inference from the observable contract, not an upstream tombstone feature.

Two further obligations make a bare `SET consumed=true` insufficient. Core DB consumption follows the winning consume with **`deleteMany(identifier)`**, so that deletion must not destroy the recovery receipt prematurely, and older verification rows must remain invalidated. Also, a receipt written to a separate table is not atomic with consumption; for increments a single last-operation marker may be overwritten before recovery. Retain receipts for a defined recovery window, distinguish safe contention retries from unknown outcomes, and throw a monitored indeterminate error if ownership cannot be established. Do not blind-retry using a fresh tuple. Tombstones/receipt fields can be adapter-private but must not leak through Better Auth's schema output. [Core sequence][verification-consume], [#530 recovery requirements](https://github.com/alp82/goodwatch-monorepo/blob/research/cratedb-cas-proof/docs/research/auth-on-cratedb-verification.md#changes-required-in-the-adapter-design).

With the selected verification-in-Valkey mode, codes/reset/deletion consumption uses atomic `getAndDelete`, not CrateDB `consumeOne`; DB ambiguity still matters immediately for **refresh rotation/revocation**, and for verification if DB mode/DPoP is enabled. Valkey timeout after GETDEL is likewise an unknown outcome, not permission to reconstruct a credential. No end-to-end transaction or durable mint-result recovery is implemented by this research.

## Sessions: missing key, outage, lists and revocation

`findSession(token)` awaits secondary `get(token)` first. On a **missing/falsy value** it reads the DB session by token and joins the user only when `storeSessionInDatabase` is true and preservation is false. A truthy malformed cached entry returns null; a thrown `get` error escapes; neither triggers a DB read. The fallback returns the DB result without writing secondary storage. `/get-session` checks expiry after the internal read. The option's inline comment still says reads are always secondary, but the implementation is more specific and is the authority here. [Read implementation][session-read], [public expiry check](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/better-auth/src/api/routes/session.ts#L287-L301), [stale option comment](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/types/init-options.ts#L1075-L1101).

`listSessions(userId)` reads `active-sessions-<userId>` and each cached token; a missing index yields `[]`. `findSessions(tokens)` reads only the supplied cached entries. Both ignore the DB copy whenever secondary storage is configured. `updateSession` updates the DB but its cache callback returns early on a missing entry, so even a refresh does not reconstruct that entry/index. [Lists][session-list], [batch reads][session-read], [refresh][session-update].

Revoking a token/user still deletes DB rows with the selected mode. However, user-wide cache deletion obtains tokens from the **secondary active-session index**, while valid cache hits bypass the DB. If that index is evicted separately, surviving token entries can escape cache deletion. The index is also a get/modify/set JSON list, not an atomic Redis set. Merely adding a read fallback does not make session discovery/revocation complete. [Cache deletion helpers](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/better-auth/src/db/internal-adapter.ts#L109-L205), [bulk deletion][core-delete].

Design implication: **no adapter-side DB fallback is needed for a normal individual cache miss**, but storage failure policy, cache reconstruction and durable session-list/revocation policy still need implementation. A Cluster wrapper may deliberately translate session-read transport errors into monitored misses, allowing the existing DB fallback; this is application policy, not stock behavior. Do not turn errors from `increment`/`getAndDelete` into success. Restore indexes from durable session rows or use durable revocation checks/epochs so eviction cannot conceal sessions during revoke-all; handle storage failure on create/update/delete too. Database-only core sessions with a separate application cache are another option to evaluate. These are design inferences from the read/write paths, not claims of an upstream guarantee.

For MCP, `requireMcpAuth` performs local signature/issuer/audience/expiry/scope checks through JWKS (plus DPoP when applicable), **not a database session/client-revocation lookup**. Provider introspection does query the client/session. Immediate Connected apps revocation of already issued JWTs therefore requires an application policy/introspection/revocation check or acceptance of access-token expiry latency; do not assume deleting a refresh token immediately invalidates a locally verified JWT. [Guard](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/mcp/src/require-mcp-auth.ts#L103-L136), [introspection](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/oauth-provider/src/introspect.ts#L200-L248).

## Redis/Valkey Cluster and the custom storage contract

`@better-auth/redis-storage` accepts `client: Redis`, not `Redis | Cluster`. A real type probe with ioredis 5.11.1 and TypeScript 5.9.3 using bundler resolution produces **TS2740** for `redisStorage({client:cluster})`. This is a declared API limitation; it does not mean the required operations cannot run on Cluster. `get`, `set`, `delete`, `GETDEL` and the one-key Lua scripts all name exactly one key, so ioredis can route each to that key's slot; no cross-key transaction or universal hash tag is needed. This conclusion is source-based plus command recording, **not a live Cluster test**. [Redis implementation][redis-source], [ioredis key extraction](https://github.com/redis/ioredis/blob/fb224a7609b6d25959e06e31fdab2460d1f75691/lib/Command.ts#L275-L289), [routing][cluster-routing].

The extra `listKeys()`/`clear()` helpers use a single `client.scan` cursor sequence. In Cluster a keyless command selects a sample node, so that sequence is not a scan of every master (and is not pinned to one master across iterations). `clear()` also sends `del(...batch)`, which can cross hash slots. Never use those helpers to revoke all sessions in GoodWatch's shared Cluster. If administration needs enumeration, iterate `cluster.nodes('master')`, SCAN each node separately and delete each key individually or group by slot; enumeration is still best effort under concurrent writes. These helpers are **not required** by `SecondaryStorage`. [Redis helper source][redis-source], [ioredis routing][cluster-routing], [official Cluster node enumeration](https://github.com/redis/ioredis/blob/fb224a7609b6d25959e06e31fdab2460d1f75691/README.md#running-commands-to-multiple-nodes).

Implement these five methods against the existing ioredis Cluster, with an auth-specific prefix and closure-bound client functions (the limiter extracts `increment` and calls it without a receiver). [Required interface][secondary-contract], [rate-limit caller][rate-limiter].

| Method | Required semantics | Cluster implementation |
| --- | --- | --- |
| `get(key)` | return stored string/unknown or null on a missing key | `cluster.get(prefix+key)`; outage policy is explicitly ours |
| `set(key,value,ttl?)` | TTL is in **seconds**; value is a string | `SETEX` for positive TTL; stock falls back to unexpired `SET` for absent/nonpositive TTL |
| `delete(key)` | remove one key | `DEL prefix+key` |
| `getAndDelete(key)` | **atomic** read-and-remove | `GETDEL prefix+key` (Valkey 8.1); stock falls back to one-key Lua GET/DEL only for an unknown-command error |
| `increment(key,ttl)` | atomic +1, return new count; absent counter starts at 1; apply TTL **only on creation**, never extend it | one-key Lua `INCR`; `if count==1 then EXPIRE key ttl end`; reject noninteger/nonpositive TTL |

The session-token key stores JSON `{session,user}` with TTL until session expiry. `active-sessions-<userId>` stores JSON token/expiry references with TTL until the latest session expiry. `verification:<storedIdentifier>` stores verification JSON with its expiry. Rate limiting calls `increment` with a key generated from request/path/rule identity and TTL=window. **Auth codes, reset-password tokens and deletion links** use required atomic `getAndDelete` when DB storage is off. Google OAuth state is an exception: `parseGenericState` uses `findVerificationValue`, validates the signed state cookie, then separately calls `deleteVerificationByIdentifier` (GET followed by DEL in secondary storage). #528 overstates atomic consumption for all OAuth state. Preserve the cookie check and account for this distinct path in callback race tests; a GETDEL implementation alone does not change its caller. [Session writes][core-session-create], [consumption][verification-consume], [Google state retrieval/deletion](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/better-auth/src/state.ts#L228-L303), [limiter][rate-limiter].

GoodWatch's [ADR 0003](../adr/0003-redis-cluster-of-masters-with-volatile-lfu.md) requires TTLs on new Cluster keys because volatile-lfu evicts expiring keys and capacity can otherwise be exhausted by immortal data. Stock `set` accepts missing/nonpositive TTL and then writes without expiry. The custom wrapper should refuse/skip already expired writes and enforce positive TTLs for auth data; the selected callers already avoid most zero-TTL writes. Account for expiry during user-session cache refresh, which can reach `set(...,0)`. Keep this enforcement in the auth wrapper rather than changing the shared cache configuration. [Stock set][redis-source], [user-session cache refresh](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/better-auth/src/db/internal-adapter.ts#L109-L136).

## What changes relative to #528

| Assumed / unresolved in #528 | Found at the pin | Design change |
| --- | --- | --- |
| DB session fallback needed verification | Individual missing-key fallback exists, with the qualifications above | Keep storeSessionInDatabase=true and preservation off; spend work on outages/listing/revocation instead of duplicating the normal fallback |
| Valkey-only sessions were an open option | Provider refuses that setup | Database sessions are required for this plugin set |
| Tokens stored only as hashes | Core sessions have no hash option; Google/JWKS must be recoverable; refresh replay response is encrypted token material | Specify storage per column, not a blanket hash claim |
| Keyed tables suffice for lookup plan | Core and provider also read/write logical ids, batches, client/session/code indexes, unfiltered small lists | Make returned logical ids equal deterministic physical keys where valid, **or** maintain strong reverse indexes; retain raw-compatible session output and explicit list plans |
| Consent PK hash(clientId,userId,referenceId) | With absent referenceId, upstream lookup matches client+user **without** testing referenceId=null | Fix a no-referenceId policy for launch or implement the broader lookup; an invented null predicate would change semantics |
| Refresh family invalidation needs repair | It targets **all client+user refresh rows**, with no familyId column; list default is 100 and multi-step race remains | Explicitly handle complete enumeration and the documented revocation race; double sweeps alone are not a proof |
| 30-second reuse window | Correct for mcp(), not bare oauthProvider() | Keep MCP composition and encrypted replay column |
| On zero, missing consumed row identifies another winner | #530 demonstrated this request's own DELETE can survive while returning 0; Better Auth has no indeterminate result | Retain atomic ownership receipts/logically deleted tombstones or throw and fail closed; distinguish applied state from a confirmed caller |
| All single-use OAuth state uses getAndDelete | Google state uses separate get/delete after cookie validation | Keep signed-cookie check and test this specific callback path |
| CIMD has hardened fetching/MCP profile | Both are available but require explicit configuration | Pass transport/profile; per-process quotas need deployment-aware limits if required |

The logical-id issue is not proof the deterministic-key plan is impossible: #528 already suggests setting ids inside the adapter. If `session.id` equals the physical hash key, OAuth's id lookup is a direct read. Likewise deterministic account/consent/token ids can serve both their tuple/token and id shapes. The build must demonstrate that returned ids, passed ids (`forceAllowId`), foreign references, and core outputs stay compatible, rather than blindly preserving generated random ids in a token-keyed table. User ids remain the migrated UUIDs. [Factory create/output](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/adapter/factory.ts#L885-L970), [core identity patterns][core-identities], [provider schema](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/oauth-provider/src/schema.ts).

Foreign-key behavior remains a separate adapter obligation: OAuth client-resource links have cascades; token sessionId references specify set-null; token/user/client/refresh references and user-account/session relationships also exist. Do not assume CrateDB enforces Better Auth's schema relationships. This research inventories explicit calls and flags those requirements; it does not implement delete cascade policy or change the accepted infrastructure ADRs. [Provider schema](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/oauth-provider/src/schema.ts), [core schema](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/core/src/db/get-tables.ts).
