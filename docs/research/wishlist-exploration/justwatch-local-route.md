# JustWatch: local wishlist extraction route

Research date: **2026-10-18**. Decision evidence for [Can a local JustWatch export preserve a complete wishlist and its identities?](https://github.com/alp82/goodwatch-monorepo/issues/704), within [Map: streaming wishlist imports](https://github.com/alp82/goodwatch-monorepo/issues/702).

## Finding and route recommendation

**A local, independently implementable route is specific enough to prototype:** read the signed-in person's **`WATCHLIST`** through JustWatch's browser GraphQL endpoint, exhaust its cursor connection, and download a local JSON file retaining native identities and movie/show scope. JustWatch's own distributed application contains this list query and membership fields. A currently distributed independent exporter implements this route and requests IMDb/TMDB IDs. This establishes implementation evidence, **not a successful authenticated extraction or a completeness benchmark**. No source account or real export was available in this investigation.

Prefer this wishlist-only experiment over introducing Simkl as a destination. **Defer adopting Simkl's file dialect** until its actual bookmarklet and local output can be inspected. The earlier inability to retrieve its JavaScript persists. Its publisher additionally describes an import policy that combines explicit wishes with unstarted tracked shows, which must not silently become GoodWatch Want to See. These are research recommendations; they do not accept a prototype, authorize a production release, or close a dependent decision.

## Simkl bookmarklet: unresolved implementation, newly explicit semantic risk

**Publisher documentation.** [Simkl's instructions](https://simkl.com/apps/import/justwatch/) describe a browser bookmarklet that reads a signed-in JustWatch session and downloads JSON before any Simkl sign-in/upload. They claim watchlist, seen movies/shows, episode dates and IMDb/TMDB IDs. That sequence supports an accountless *destination* handoff; the source still needs the person's JustWatch session. The web reader exposed the instructions, but omitted the bookmark URL and copy-button handler. Direct unauthenticated requests to the canonical page, `www`, HTTP and simple mobile/output query variants returned HTTP 403 challenge HTML. No challenge-solving or signed-in workaround was attempted. **Actual Simkl JavaScript, endpoint destinations, output keys, native IDs, cursor termination and reuse licensing remain unobserved.** Do not interpret the page's privacy claim as a completed code audit.

**Publisher announcement, not observed JSON.** [Simkl's feature announcement](https://www.reddit.com/r/Simkl/comments/1x2o1l2/new_import_your_justwatch_watch_history_and/) explicitly says its Plan to Watch import includes the JustWatch watchlist **plus tracked shows not started**; partway-through shows become Watching and finished shows Completed. Custom lists and likes/dislikes are excluded. Whole-season marks use the marking date. This describes importer policy; it does **not** prove the downloaded file already merges those categories. A raw export might still preserve them separately. GoodWatch must inspect that boundary before accepting this dialect, retain independent membership and seen evidence, and never interpret tracking progress zero alone as an explicit wish.

There is no verified Simkl sample in this report. Neither an output schema nor a working Simkl extractor is invented to fill that gap.

## Independent route: what the code actually does

**Observed first-party application.** The [distributed list component](https://www.justwatch.com/appassets/BV5hFCnc.js) includes `GetTitleListV2` and `WatchlistTitleGraphql`. It requests `titleListV2(country, titleListType, sortBy, first, after, filter)` with `totalCount`, `pageInfo.endCursor`, `hasNextPage` and edges. Its component supplies `first: 20` and `includeTitlesWithoutUrl: true`. Edges retain `id`, `objectId`, `objectType`, localized title/year/path, and separate `watchlistEntryV2.createdAt`, movie `seenlistEntry`, show `tvShowTrackingEntry` and `seenState`. Its UI selects Watchlist, Seenlist or Likelist explicitly and fetches subsequent pages using the returned cursor. The website's normal query also inherits display filters; copying a filtered UI view would not establish complete membership.

**Observed independent implementation.** The [exporter's query and pager](https://github.com/max-arias/justwatch-csv-exporter/blob/f82272838260ac83ff4a193939fd8280538a9c21/src/lib/justwatch-api.ts) independently select `WATCHLIST` or `SEENLIST`, use `LAST_ADDED`, 20-item pages, and request only `includeTitlesWithoutUrl` as the title filter. Each node supplies opaque `id`, explicit `MOVIE`/`SHOW`, title/year/path, `externalIds { imdbId tmdbId }`, wishlist-added time and separate show progress. It retains native `id` in memory and deduplicates on it. These external-ID fields are requested by distributed third-party code; their actual availability, nullability and correctness on a person's account remain unverified here. They are provider-returned IDs, not title-search guesses. Numeric native `objectId` must never be relabeled TMDB.

**Observed session/network behavior.** [Session code](https://github.com/max-arias/justwatch-csv-exporter/blob/f82272838260ac83ff4a193939fd8280538a9c21/src/lib/justwatch-session.ts) injects into a JustWatch tab's main world, reads the person's own `jw/user` access token and device ID, and sends GraphQL query POSTs to `https://apis.justwatch.com/graphql` with bearer authorization and optional `device-id`. A POST here contains a read query, not a membership mutation. The code detects sign-in through `jwLoginId`; it can open a temporary JustWatch tab to refresh the site's session. There is no bundled API key, middle-tracker login or Simkl transmission in this path. The [manifest configuration](https://github.com/max-arias/justwatch-csv-exporter/blob/f82272838260ac83ff4a193939fd8280538a9c21/wxt.config.ts) requests downloads, scripting, storage and the JustWatch website host. The popup can load JustWatch poster URLs; the intended independent wishlist prototype needs no posters. Account state must stay in the source browser, outside the downloaded file and GoodWatch servers.

**Observed output loss.** [CSV generation](https://github.com/max-arias/justwatch-csv-exporter/blob/f82272838260ac83ff4a193939fd8280538a9c21/src/lib/csv.ts) drops every show from Letterboxd output. Trakt output drops items lacking external IDs and omits native IDs, titles and year; for missing wishlist-added dates it substitutes export time. Neither CSV retains coverage or the original account/list provenance. Consequently, copying this CSV journey is inferior to producing the existing [shared wishlist JSON v1](../../implementation/shared-wishlist-format.md) directly. Keep unknown added dates absent. A Seen export is never a wishlist.

**Licensing boundary.** [AMO](https://addons.mozilla.org/en-US/firefox/addon/justwatch-csv-exporter/) advertises MIT for the package, but the inspected repository root has no `LICENSE` and `package.json` has no `license` field. Record that discrepancy before copying source; an independent implementation can use the observed protocol without importing this code. No open reuse license was found for the Simkl bookmarklet or DOM gist. JustWatch's website code is first-party protocol evidence, not licensed GoodWatch source. None of this establishes production API access terms or a supported third-party integration contract.

## Synthetic checks: the pager does not certify completeness

Executed the pinned exporter's actual `fetchTitleList` and `classifyResponse` functions with Node 24.15.0 type stripping and synthetic responses. Network and sleep were injected stubs; no account API calls occurred. Inputs used synthetic movie nodes, explicit `WATCHLIST`, and declared totals. The results below are **synthetic executions, not provider benchmarks**.

| Input response sequence | Requests | Returned items / reported total | Observed outcome |
| --- | ---: | ---: | --- |
| Two unique nodes; second page `hasNextPage: false` | 2 | 2 / 2 | Normal return. |
| Two pages repeat cursor `a`, both still `hasNextPage: true` | 2 | 2 / 50 | Normal return with no partial flag. |
| First page has no end cursor, `hasNextPage: true` | 1 | 1 / 50 | Normal return with no partial flag. |
| HTTP 200 has valid list data plus a non-auth GraphQL field error | 1 response classified | 1 / 1 | Classified as a usable page; field error not surfaced. |

The return shape is only `titles`, `total`, `skipped`. [Background handling](https://github.com/max-arias/justwatch-csv-exporter/blob/f82272838260ac83ff4a193939fd8280538a9c21/entrypoints/background.ts) records any normal return as `complete`. Code inspection additionally found stops for empty pages and a calculated/hard page ceiling; these are loop protections, not cursor exhaustion proofs. Its transient retry/backoff, one-time auth renewal and deduplication are useful mechanisms, but no experiment here establishes list snapshot stability during edits.

**Prototype requirement:** store terminal reason, pages/requests, reported totals over time, unique native identities, skipped/invalid entries, duplicates/conflicts and GraphQL errors. Only a clean terminal `hasNextPage: false`, consistent counts and accounted-for entries can be candidate evidence for `complete`. Missing/repeated cursors, limits, interrupted requests, resolver errors or list changes require `partial`/`unknown`, with actionable retry. An equal count alone is insufficient. Where the API has no snapshot guarantee, report that limitation and test repeatability with no concurrent list edits.

## Alternatives and semantic guardrails

The [DOM gist](https://gist.github.com/rvighne/cb12f4d57ebb5a739ed5017021e8f85f/3f37c1ef31c5fea7de600e6d2b6f9af4b03018ed) returns `Title,Year` from visible headings after `console.assert` against `.titles-count`. An assertion failure does not stop export. Its example URLs distinguish movies and watchlist/seen/liked tabs, but output itself has no type, ID or membership label. Manual scroll/rendering and active filters can omit titles. It is a partial manual fallback, not proof of complete mixed wishlist capture.

[JustWatch custom-list documentation](https://support.justwatch.com/article/what-are-custom-lists) distinguishes those lists from Watchlist and says provider filters apply. [Hide Seen/Disliked documentation](https://support.justwatch.com/article/how-to-use-the-hide-seen-disliked-function-on-just-watch) says those settings can hide titles even in Watchlist. Thus neither rendered presence nor progress establishes the entire explicit wish set. Preserve a seen title's explicit wish membership for GoodWatch's existing rewatch confirmation; never turn history into wishes automatically. Custom-list capture would require an explicitly selected list and purpose, a separate question from this route.

[JustWatch's partner data export](https://apis.justwatch.com/docs/data_export/) is a contracted S3 catalog/offer feed, not the person's wishlist. It does not solve migration. [The privacy policy](https://support.justwatch.com/article/privacy-policy) gives a data-rights contact and portability language, but publishes no personal wishlist export schema here. A voluntarily obtained account archive remains an alternative to inspect; no support email was sent, and no legal entitlement/timing conclusion is needed for this experiment.

## Minimal next experiment and access request

The now-specifiable follow-up is a **read-only browser-session to local wishlist JSON prototype**, followed by owner review. Its required access is one willing person's existing JustWatch browser session, used locally; no cookies/password/token need to be shared. Before running, audit the exact prototype script and its complete network destinations. If that is unavailable, defer authenticated validation rather than claiming a working exporter.

1. In a stable, unfiltered existing account, locally identify explicit Watchlist movies and shows, a seen-only title, an unstarted tracked show not explicitly wishlisted, and an explicit seen-plus-wishlist overlap **where those cases already exist**. Do not create or change provider memberships for this research. Missing cases remain untested.
2. Run the independent query capture with no third-party credentials and no middle-service upload. Compare each source category to its returned membership fields. Retain opaque native IDs, actual object type, returned external IDs and their provenance; preserve unknown IDs without guessing. Restrict exported candidates to explicit wishes. Check localized/unavailable-title behavior and missing external IDs.
3. To test paging rather than merely schema, use an existing list longer than 20 items. Record reference count, every cursor, terminal state, duplicate/skipped counts, total requests, duration and interruption recovery. A smaller list can validate shape only. Compare two stable runs and reviewed native identity sets; publish denominators and unsupported cases, not a population accuracy percentage.
4. Proposed gates, to be accepted by the owner later: zero seen-only/tracked-only contamination; correct movie/show scope and no invented catalog IDs in every reviewed case; every reference wish accounted for or explicitly reported unresolved; clean cursor exhaustion and reconciled counts for a complete claim; any interruption/mismatch visibly partial. Benchmark capture separately from downstream GoodWatch matching.
5. To reconsider the Simkl dialect, obtain **the public bookmark's complete JavaScript URL and every loaded script**, plus a local redacted JSON preserving key names, types and distinct source-set membership. A structural sample needs only one available movie and show and the above negative-control cases if already present; replace private account identifiers and omit tokens. A separate >20-item run is needed for pagination. Do not upload to Simkl. A schema sample cannot establish destinations or completeness without script/network evidence.

Use private local storage for raw responses and account exports; publish only reviewed structural/synthetic fixtures and aggregates. The shared contract can carry one source/list's native ID, type and coverage; richer raw category/progress evidence belongs in the private experiment record and must not be silently discarded before eligibility is established. Its ignored extra fields are not durable provenance storage.

The research decision is therefore **prototype the independent explicit-Watchlist route; defer Simkl-specific compatibility and all completeness/support promises pending the exact local experiment above**. This establishes a route and a bounded missing-access request without supplying the owner's prototype verdict.
