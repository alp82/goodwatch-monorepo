# Next native wishlist adapters: evidence and shortlist

Checked **2026-10-18** for [Which native wishlist exports should be the next adapters?](https://github.com/alp82/goodwatch-monorepo/issues/703), within [Map: streaming wishlist imports](https://github.com/alp82/goodwatch-monorepo/issues/702).

**Recommendation:** preserve the existing IMDb and Simkl work. Among genuinely new routes, validate **MDBList personal Watchlist first**, then **Seerr's local Watchlist** for existing users. Both justify a narrowly scoped reader/adapter experiment, not a support announcement. Google Saved, Serializd and Sofa/Listy need the specific samples below before implementation is selected. No new native adapter has met a live release gate in this investigation.

This follows [alternative routes](alternative-routes.md) and [tracker routes](tracker-routes.md), rather than repeating their surveys. The material additions are current MDBList OpenAPI inspection, a deeper Seerr serializer/Plex coverage audit, failed public Serializd probes, current entitlement checks, and precise validation boundaries. Recommendations are research judgments; they do not supply the owner's acceptance of a prototype or authorize new tickets.

## Evidence and scope

- **Inspected producer code:** pinned Seerr and Serializd exporter sources. Code shows attempted behavior, not successful current remote responses.
- **Official documentation/schema:** current provider pages and MDBList's machine-readable API schema. Its example objects are documentation examples, not account exports.
- **Actual HTTP observations:** MDBList unauthenticated reads were rejected with 401; Serializd public show probes were rejected with 403. These establish no successful membership or identity mapping.
- **Existing runtime evidence:** shipped Watcharr's unmodified backend was previously exercised with synthetic accounts. This report did not repeat it; [Watcharr validation](watcharr-validation.md) remains the evidence owner.
- **No new account export or synthetic runtime fixture:** none was obtained or generated here. No private archive, credential, profile, provider mutation or member mutation was used. No extraction/matching recall or accuracy percentage can be computed.

The glossary and [tracking ADR](../../adr/0009-tracking-is-a-state-machine.md) apply: Want to See is independent of a show's status, and an explicit rewatch wish must survive. Custom-list membership requires the member's explicit choice of intent. None of these routes should infer watches, union unrelated lists, or delete wishes absent from a partial capture. Implementation should enter the [existing shared contract](../../implementation/shared-wishlist-format.md), retaining source evidence independently of a matched catalog identity.

It supplies a stronger evidence bar than an export button or documentation example. ## MDBList: strongest new documented reader

**Route/account:** `GET https://api.mdblist.com/watchlist/items`; personal API key or bearer authentication. The free key is documented at Preferences; basic daily quota is 1,000 requests, shared with the account's other clients. Paid rating filters are unnecessary for full membership. Prefer a local, one-shot reader over making users create another tracker account. [API guide](https://docs.mdblist.com/docs/api), [API landing page](https://api.mdblist.com/).

**Inspected contract:** downloaded `https://api.mdblist.com/schema/?format=json`, reached through the Swagger page's actual `/schema/` configuration. The schema identifies itself as MDBList API 1.0.0; SHA-256 of downloaded bytes: `12a16e8b83e2f17886fd714d97f2465482ce582ae54041640b3ec54a98964f6e`. It declares `/watchlist/items`, `/watchlist/items/{mediatype}` and `/lists/{listid}/items`. Personal wishes and arbitrary lists are separate routes. [Machine-readable schema](https://api.mdblist.com/schema/?format=json), [Swagger UI](https://api.mdblist.com/docs/).

The schema prefers `cursor`/`next_cursor`, deprecates `offset`, describes default cursor page size 100 and maximum 1,000, and documents `X-Has-More`. It offers movie/show/season/episode filters and `movies`, `shows`, `seasons`, `episodes`, `pagination` response buckets. Movie fields include `ids.tmdb`, `ids.imdb`, `ids.mdblist`, title, year and media type. The show's declared shape/example lacks that same nested `ids` object, though the general landing page describes provider IDs. A reader must inspect actual movie **and** show rows rather than requiring identical shapes. `sort=added` does not establish that a per-item added timestamp is returned: the inspected item properties do not declare one. Leave source-added time unknown unless the response proves it. [Schema](https://api.mdblist.com/schema/?format=json).

**Important change from earlier assumptions:** generic API landing material still describes offset endpoints, while this route's current machine-readable contract prefers cursors. The schema declares only an unconstrained object for `pagination`; its example does not demonstrate the cursor's exact location. Do not build a guessed pagination envelope from an example. Fetch first/middle/final pages and record actual cursor placement and headers. The unauthenticated route returned 401, so no actual membership envelope was observed. [Route](https://api.mdblist.com/watchlist/items), [schema](https://api.mdblist.com/schema/?format=json).

**Intent/scope:** use personal Watchlist only. Dynamic, official, external and shared lists do not intrinsically express the member's Want to See. Season/episode entries must remain unsupported or explicitly resolved at their actual scope, never silently promoted to a show. Anime has no separate proven wishlist contract here; require a verified TMDB movie/show identity for any anime title. [User-list semantics and media filters](https://api.mdblist.com/schema/?format=json).

**Permissions/reuse:** API access is offered, but this is not an open-source implementation licence or blanket metadata redistribution permission. Current OAuth documentation grants only `write` scope, including broad library/playback access; a GET-only reader is therefore not a provider-enforced read-only token. No OAuth app was registered. Prefer testing an existing user's local key, retaining only selected fields; check applicable terms before distributing a client. [Official authentication/scopes](https://api.mdblist.com/docs/authentication/).

**Smallest experiment:** existing consenting user, selected Watchlist, `limit=2` to force pagination; include a movie, show, duplicate title, explicit rewatch wish, unsupported season/episode if available, and missing ID. Inspect only sanitized response structure and aggregate counts. Pass when every selected movie/show is accounted for once, cursor exhaustion and counts agree, unsupported scopes remain visible, and 401/429 or a missing cursor cannot become a successful empty/complete export. Measure request count, retries, time and operational steps. Do not enable filters that hide wishes.

## Seerr: local intentions are better established than Plex completeness

Inspected [`seerr-team/seerr` at `63705622eac5dd4e1006775e9fc43215c3ea0c88`](https://github.com/seerr-team/seerr/tree/63705622eac5dd4e1006775e9fc43215c3ea0c88), snapshot dated 2026-10-17.

**Route/account/tier:** existing self-hosted Seerr installation/user; `GET /api/v1/user/:id/watchlist?page=N`, 20 items/page. Own-user reads pass; reading another user requires `MANAGE_REQUESTS` or `WATCHLIST_VIEW`. Cookie/API-key mechanisms appear in the API contract; this does not imply an arbitrary key is narrowly scoped to one member. No additional provider subscription requirement is established for reading the local list. [Handler](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/server/routes/user/index.ts), [API contract](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/seerr-api.yml).

**Format/identity/dates:** JSON envelope `page`, `totalPages`, `totalResults`, `results`. Local rows carry record `id`, `tmdbId`, `mediaType`, title, `ratingKey`, `createdAt`/`updatedAt`, plus eager related entities. The adapter must project minimal fields locally; avoid uploading whole ORM records. Identity uniqueness is `(tmdbId, mediaType, requestedBy)`, so use TMDB plus movie/TV type. Creation/update dates are local Seerr record timestamps, not proved original Plex added dates. Anime is only a movie/TV catalog case; no dedicated anime/episode mapping is established. [Entity](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/server/entity/Watchlist.ts).

**Coverage trap, inspected:** any nonempty local list wins. Only zero local rows triggers Plex fallback; there is no local+Plex union. Plex returns a different projection (`id` is set to `tmdbId`, no local timestamps). The route does not return a discriminator establishing which backend supplied results. A zero local list without a Plex token returns empty, whereas zero local rows with a token invokes Plex. Label source scope as the effective Seerr route unless separately established; do not promise an explicitly selected Plex export from this endpoint. [Handler](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/server/routes/user/index.ts).

**Additional completeness limits:** `getWatchlist` resolves metadata then filters out rows without a truthy TMDB ID, while retaining upstream `totalSize`. Its exception path returns `totalSize:0, items:[]`. Thus count mismatch and a failed upstream read can be hidden behind an ordinary route response. Its cache is keyed by token, while requests carry page offsets: page/ETag behavior deserves a targeted regression test, not an unsupported claim that paging currently fails. No Plex request was made here. [Plex reader](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/server/api/plextv.ts).

**Intent/reuse:** local Watchlist membership is distinct from acquisition requests, availability, or a Plex library. Read only the intended Watchlist. Seerr source is MIT; retain notices if reusing code. That licence does not settle Plex/TMDB service terms or metadata redistribution. [Entity](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/server/entity/Watchlist.ts), [MIT licence](https://github.com/seerr-team/seerr/blob/63705622eac5dd4e1006775e9fc43215c3ea0c88/LICENSE).

**Smallest experiment:** disposable local Seerr fixture or existing consenting user, 21+ local rows, mixed movie/TV and same numeric TMDB ID in both namespaces. Exhaust pages and reconcile unique identities with the chosen local list; test zero rows separately with and without Plex configured. Treat Plex-derived captures as unknown coverage until raw source count, metadata exclusions and upstream failure handling can be explained. No acquisition request should become a wish. This is a validation follow-up, not approval to write to any existing installation.

## Google Saved / Takeout: defined CSV, unverified film-list parity

Google documents CSV fields `title`, `item_content_url`, `note`, `tags`, `comment`; an optional collection description precedes a blank line and header. Fields vary by service/action. There is no guaranteed year, movie/show type, catalog ID or added date. Preserve original URL; do not assume a Google knowledge/search URL is TMDB/IMDb identity. [Saved schema](https://developers.google.com/data-portability/schema-reference/save).

Google TV's Watchlist is account-associated, supports movies/shows, and the web route is Interests → Watchlist; Google warns some service content cannot be added. This establishes intent and a UI reference, not parity with every old/new Saved export. A mixed collection also holds non-media URLs; anime is not separately guaranteed. [Google TV help](https://support.google.com/googletv/answer/10059391?hl=en).

**Account/tier/pagination/coverage:** a Google account and a user-requested export; no paid tier is established for Takeout. CSV pagination is not relevant once downloaded, but completeness against the selected Watchlist is unknown. Takeout warns changes between request and archive creation may be absent. Do not make a transient in-flight discrepancy proof of permanent omission. A direct Data Portability API integration adds app verification and potentially a security assessment; it is unnecessary for a local file adapter. [Takeout help](https://support.google.com/accounts/answer/3024190), [Portability overview](https://developers.google.com/data-portability).

**Reuse:** official documentation describes data export; it does not license third-party scraper code. Earlier CineHarvest code had no inspected licence and guessed first-search metadata; keep it a reference, not a dependency. Google's API policies require a separate review if an authenticated connector is selected. [Existing inspection](alternative-routes.md#3-google-saved-takeout-and-shareable-collections), [API policy](https://developers.google.com/data-portability/policy).

**Smallest sample:** the selected Watchlist CSV only, plus aggregate reference count and a sanitized field manifest; old/new Google TV and Search saves, movie/show, same-name works, removed item and more than one UI page. Unknown type/ID rows remain unresolved, not guessed first results. Pass when collection intent is explicit, inclusion/omission is explained, and a source URL survives review. Defer automatic matching claims until separately benchmarked. No whole Takeout upload is necessary.

## Serializd: code lead, not an authenticated contract

Serializd says its current features are free, TV-focused and sourced from TMDB. That does not prove that every numeric `showId` is a public TMDB ID. Movies are outside this route; animated/anime shows require demonstrated catalog identity. [Provider FAQ](https://www.serializd.com/).

The MIT exporter at `c34102e55e514ee841123f638596cce64dd8ed88` logs in locally, reads `/api/user_information?shouldGetUserContext=true`, iterates `context.watchlist`, groups by `showId` and chooses the earliest `dateAdded`. It then sends that ID to Trakt's TMDB search. There is no pagination/count check in that context reader. Date strings/precision and season-to-whole-show promotion remain sample questions; the exporter choosing `min()` is not a documented provider date rule. [Inspected code](https://github.com/mwsmws22/serializd_to_trakt/blob/c34102e55e514ee841123f638596cce64dd8ed88/serializd_to_trakt.py), [MIT licence](https://github.com/mwsmws22/serializd_to_trakt/blob/c34102e55e514ee841123f638596cce64dd8ed88/LICENSE).

**Actual probes:** unauthenticated GETs to `/api/show/1399` and `/api/show/1396`, using the reader's JSON accept and `x-requested-with` header, both returned HTTP 403 from this environment. No bypass, login or retry escalation was attempted. Therefore these probes did not validate numeric identity or current API viability. A newer `belepod/serializd-export` at `b5816616d74ef6bc515c1b5a2de5dec29284cda9` was also inspected: it reads watched shows and diary, not Watchlist. An export tool's name is insufficient evidence of wish coverage. [API client](https://github.com/belepod/serializd-export/blob/b5816616d74ef6bc515c1b5a2de5dec29284cda9/src/api.js), [Orchestrator](https://github.com/belepod/serializd-export/blob/b5816616d74ef6bc515c1b5a2de5dec29284cda9/src/exporter.js).

**Smallest sample/reuse:** selected redacted `context.watchlist` with two known show IDs, one season-specific membership and repeated seasons/dates, plus visible count. Verify IDs against the source show's TMDB attribution and establish whether whole-show Want to See is intended. Keep `showId` source-scoped until proven. No server-held email/password integration; no requirement to publish a private list. Existing MIT extraction code can be independently adapted with notices; no stable first-party API/export guarantee or reuse permission for the service itself was established. Defer live reader implementation until that sample/access boundary is resolved.

## Sofa / Listy: request bytes, not a migration through another app

**Sofa:** publisher now places Backups & Export in its Free section and says Standard needs no account. This resolves the earlier survey's entitlement ambiguity at the documentation level, not runtime. It handles movies/TV and many unrelated categories. The publisher's 2019 export announcement proves an export feature, not today's backup contract. [Pricing/features](https://www.sofahq.com/pricing), [Publisher announcement](https://www.sofahq.com/blog/making-it-easy-to-leave-sofa).

**Listy:** official guide offers Export all to `.listy` files; its product page says use without registration and local storage. The export guide does not specify a paid requirement, and runtime entitlement remains untested. Neither a `.listy` container/schema nor catalog IDs, completion flags, dates or pagination/completeness were inspected. Its movies/TV lists coexist with other categories. [Export guide](https://listy.is/help/how-to-export-lists/), [Product](https://listy.is/).

Listy's own Sofa importer describes `.sofa3bk` and preserving lists, notes, completed items and Pile. This is primary evidence of **Listy's importer claim**, not a Sofa-owned schema specification. A list/Pile is not necessarily a wish, and completed membership must not be discarded if an explicit rewatch intention also exists. No separate anime contract is established. [Importer guide](https://listy.is/import/sofa/).

**Smallest sample:** one original current backup from each app built from synthetic content: one pending movie, pending show, completed title, explicit rewatch if supported, same title in two lists, Pile/unfiled entry, custom non-media item and an unknown/custom title. Record app/version/platform, file suffix, archive manifest, field names and ID namespaces; share only sanitized structure and counts. A complete tiny export can establish a parser contract, but large-list completeness remains a later test. Identify selected-list membership separately from completion and tracking states. Implement no guessed ZIP/JSON decoder before seeing bytes.

No open-source producer licence or redistribution licence was established for either app. Independently parsing a user-directed local export is the proposed boundary; do not copy proprietary app/importer code or treat an export help page as a metadata licence. This is an explicit unresolved constraint, not a legal conclusion.

## Preserve canonical IMDb / Simkl work

Read full issues and comments on 2026-10-18. [Build the IMDb import: ratings, watchlist, lists and check-ins](https://github.com/alp82/goodwatch-monorepo/issues/618) already specifies Watchlist → Want to See, IMDb matching and `Created` as added date; arbitrary custom lists are not applied. [Collect real export files](https://github.com/alp82/goodwatch-monorepo/issues/372) still records missing IMDb files. No later samples are recorded in those comments. IMDb's current FAQ confirms movie/TV wish intent and explicitly says IMDb and Prime Video watchlists are separate. Do not market this as a Prime adapter. [IMDb FAQ](https://help.imdb.com/article/imdb/track-movies-tv/watchlist-faq/G9PA556494DM8YBA).

[A real Simkl backup](https://github.com/alp82/goodwatch-monorepo/issues/641) remains the sample task. [Build the Simkl backup import](https://github.com/alp82/goodwatch-monorepo/issues/621) already specifies `plantowatch` → Want to See, TMDB then IMDb identity, and show-level-only anime status/wishes/ratings until mapping licensing is settled; anime episode rows remain unmatched. The official backup page offers ZIP/JSON and CSV and describes CSV as lacking episode detail; it does not settle the original file's planned-list shape, pagination, timestamps or every ID namespace. [Backup page](https://simkl.com/apps/backup/).

The current page marks CSV free for everyone and presents ZIP as VIP or free monthly; those are documented offers, not an authenticated entitlement test. Reuse the existing owner checklist and inspect the original bytes when available. Preserve source dates only when explicit, never substitute export time. IMDb/Simkl completeness and native-file compatibility remain sample-limited; their existing work was neither duplicated nor closed here.

## Follow-ups now precise enough to consider

These are proposed breakdown inputs for the map owner, **not newly created or accepted tickets**:

1. Validate MDBList personal Watchlist cursor/identity contract using the bounded experiment above; decide whether a local producer is useful to existing users. No OAuth connector is prerequisite.
2. Validate Seerr local-list pagination/projection separately from Plex fallback; require visible evidence of backend scope and metadata exclusions before a Plex completeness claim.
3. Collect only selected Google Watchlist CSV and sanitized Sofa/Listy synthetic backup shapes. These three sample questions are independent; no full private archive is needed.
4. Obtain Serializd selected-context evidence and verify season/ID semantics before choosing extraction implementation. Public probes failing does not require an owner to surrender credentials.

A later accepted adapter needs parser/intent tests, native format recognition without accidental cross-source detection, preview/receipt integration, idempotent additive behavior and Undo validation, then deployment verification. That execution belongs to scoped build/release tickets after acceptance. UX integration follows the separately owned design; this report changes no UX. Research resolution is complete because the ranked shortlist and explicit sample/defer limits answer the question; the overall map remains open.
