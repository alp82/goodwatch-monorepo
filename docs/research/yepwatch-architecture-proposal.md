# YepWatch: API, Crate and realtime architecture proposal

Checked **2026-10-20**, updated after explicit user choices. **User-confirmed choices are identified below; transport/storage mechanics remain proposals, not an accepted ADR or implementation approval.** YepWatch is the working name; yepwatch.com ownership is user-reported. No application, DNS or infrastructure changes were made.

## Direction and revised stack

**Build the Expo matcher over a namespaced GoodWatch API, keep durable room state in Crate, and deliver a realtime multiplayer experience through WebSockets.** Recommend **HTTP commands plus server-pushed room views/revisions**, with a small Node WebSocket gateway alongside the existing Remix service. Reuse Valkey Pub/Sub for revision-only invalidations; Crate remains authoritative. This supersedes the earlier PostgreSQL and polling-first recommendations.

| Boundary | Choice / status | Reason and consequence |
|---|---|---|
| Durable room state | **Crate — user-confirmed**; one bounded aggregate per room proposed | Single-document CAS keeps votes, roster, consent and receipts atomic within that document. No assumed multi-row transactions. |
| Client data access | **API only — user-confirmed** | No native/browser database/cache credentials or direct connections. All YepWatch-owned HTTP/WS routes use **/api/yepwatch/v1**. |
| Reuse boundary | **Thin adapters — user-confirmed** | Authorize, validate and project over existing domain methods. Rooms/votes/decisions are new domain logic, not a giant route or copied catalog implementation. |
| Live behavior | **Realtime multiplayer — user-confirmed**; WebSocket push + HTTP commands proposed | Prompt join/ready/progress/shortlist/consent updates. No normal client polling. |
| UI | Expo + React Native + TypeScript, Expo Router and Expo Web — recommendation retained | Share the matcher journey with platform-specific accessible controls. Existing GoodWatch webapp need not migrate. |
| Server | Existing Remix page service for HTTP/domain logic; small Node/ws gateway proposed | Own the upgrade/socket lifecycle without rewriting remix-serve. Gateway calls private API adapters, not catalog/database code. |
| Fanout | Existing Valkey Pub/Sub — proposed | Revision hints only; missed events and outages require repair. No exactly-once claim. |
| Client state/auth | TanStack Query, local React state, Zod, SecureStore; GoodWatch OAuth + PKCE — proposed | Existing accounts, separate room credentials, private member prefilling. OAuth compatibility still needs proof. |

Also confirmed: native iPhone/Android first, couch/remote/mixed rooms immediately, all existing GoodWatch catalog/country/service coverage, optional initial GoodWatch login and guests, later a simplified companion experience. **Still proposals:** browser guests, per-viewing-screen contexts, movies-first, short decks, size/expiry limits and detailed protocols. Coverage intent proves neither every current offer/entitlement nor movie-versus-show scope. Playback synchronization/chat are not included. [Product research](goodwatch-mobile-group-matcher.md), [naming context](goodwatch-matcher-naming.md).

The **GoodWatch central login/issuer at goodwatch.app**, its existing /api/auth/OAuth routes, and required **/.well-known/apple-app-site-association** and **/.well-known/assetlinks.json** are existing/standards routes, not misplaced new YepWatch APIs. Invitation pages /r/INVITE are UI URLs. Do not move/duplicate central auth or association files to force the API prefix.

Guests receive unguessable room-scoped credentials: HttpOnly, Secure, SameSite=Lax cookies in browsers; bearer credentials stored in [SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/) on native. The authoritative room stores verifiers/capabilities, never raw guest secrets in projections. A code/nickname/invite proves neither identity nor room-read permission. Host rights are separate. Validate credentials, membership generation, expiry and authorization on each operation; CSRF/Origin protection applies to cookie-authenticated writes.

Keep GoodWatch accounts/Crate auth as the single member authority ([config](../../goodwatch-webapp/app/server/auth/auth.server.ts#L94), [runtime](../../goodwatch-webapp/app/server/auth/runtime.server.ts#L42)). Recommend system-browser authorization code + PKCE through Expo AuthSession and a web server callback. GoodWatch cookies cannot span unrelated domains ([cookie domain rules](https://httpwg.org/specs/rfc6265.html#section-5.2.3)); YepWatch has its own session. Browser tokens remain encrypted server-side, native refresh tokens in secure storage; no embedded client secret. Bind state, PKCE, exact callback and invitation context. Validate issuer/audience/scope/expiry/client and active grants before private reads. [Expo OAuth](https://docs.expo.dev/guides/authentication/), [Better Auth provider](https://better-auth.com/docs/plugins/oauth-provider).

The current provider/consent/verifier are **MCP-specific** ([provider](../../goodwatch-webapp/app/server/auth/auth.server.ts#L107), [consent](../../goodwatch-webapp/app/server/auth/mcp-flow.server.ts#L10), [verifier](../../goodwatch-webapp/app/server/mcp/authorization.server.ts#L7)). Extend that provider with a registered YepWatch resource/read scope and callbacks, preserving adapter [call-shape constraints](../../goodwatch-webapp/app/server/auth/call-shapes.server.ts#L50); do not install a second OAuth provider alongside mcp() ([composition](https://better-auth.com/docs/plugins/mcp)). This remains a compatibility spike. Existing [origin guards](../../goodwatch-webapp/app/server/site-origin.server.ts#L14) need explicit namespace-aware policy, not native header spoofing.

Linking proves both account grant and current participant credential, retaining votes/participant identity; duplicate account membership needs explicit resolution. Member Seen/taste/preferences stay private. Saved services only prefill a screen suggestion. Session votes do not write ratings, Seen, Want to See or permanent settings ([tracking ADR](../adr/0009-tracking-is-a-state-machine.md#L5)). Account revocation stops private prefilling; room access follows the separate room credential/leave policy, rather than silently confusing account logout with group departure.

## Crate aggregate: correctness before throughput

**One room aggregate is the atomic boundary**, including phase/expiry/generation, roster and capability epochs/verifiers, screens/constraints, immutable deck versions, private votes, consent/proposal versions, chosen result, command receipts/high-water marks and a pending-notification revision. Optional account links reference GoodWatch IDs/grants, not duplicated account records. Separate session/invite lookup rows may help discovery but cannot decide membership or finalization; authority is reread from the room.

Keep the semantic room revision separate from Crate storage sequence/term: ticket consumption and marker housekeeping change storage versions without inventing public room events. Use an opaque encoded/encrypted payload with bounded indexed metadata for cleanup/notification discovery, plus a safe whitelist projection. Existing auth uses **INDEX OFF, columnstore=false** for large encrypted payloads, authenticated envelopes and receipt recovery ([implementation](../../goodwatch-webapp/app/server/auth/IMPLEMENTATION.md#L34)); reuse suitable codec/transport techniques with separate room keys, not auth tables or its adapter wholesale. Private credential verifiers/votes/receipts never serialize into shared room DTOs.

**Verified semantics:** Crate offers document-level atomicity, full-primary-key Get visibility versus refresh-dependent search, and outage caveats ([5.10 consistency](https://cratedb.com/docs/crate/reference/en/5.10/concepts/storage-consistency.html)). OCC requires equality on the full primary key, **_seq_no and _primary_term together**; stale versions affect zero rows ([5.10 OCC](https://cratedb.com/docs/crate/reference/en/5.10/general/occ.html)). There are no ordinary multi-row SQL transactions or PostgreSQL locks. Use simple PK queries; test EXPLAIN/Get plans. Search/large IN queries are not authoritative immediate state reads. Use a room-specific least-privilege DQL/DML role and separate privileged migrations; do not reuse unrestricted catalog credentials.

Proposed command algorithm:

1. **Read and validate:** full-PK read; authenticate; reject tombstone/expired room; check phase, roster/context/deck/proposal versions and expected own-vote revision. Derive a pure transition. Slow candidate generation/watchability runs outside this read/CAS section and must be version-checked again.
2. **Identify and order:** command ID binds room generation, actor and monotonically increasing actor sequence, with a payload hash. Keep one in-flight command per actor; UI animations can queue locally. Store the accepted sequence/high-water mark and receipt/outcome in the same aggregate mutation. Duplicate ID/different payload is refused; old sequences never become new commands after receipt pruning.
3. **Commit:** replace the aggregate using exact PK/sequence/term CAS, including new semantic room revision, receipt, vote revision and pending-notification marker. Zero affected rows means re-read/revalidate, not an assumed applied vote. Bound conflict retries with jitter and a request deadline; begin testing at roughly five retries, then report busy/conflict and reconcile the same command.
4. **Resolve uncertainty:** a timeout after sending is **indeterminate**, not permission to replay as a new action. Re-read by PK and inspect this command's receipt/high-water mark. An unchanged/older read proves nothing; the existing adapter explicitly handles lagging read-back ([source](../../goodwatch-webapp/app/server/auth/crate-adapter.server.ts#L270)). Retry only the same logical ID/base CAS or a newly fenced/revalidated transition. If needed, an acknowledged CAS verification fence preserving the command outcome confirms it on the current writable lineage before publication; prove this recovery on 5.10.16. Receipt absence outside the retained window cannot establish non-application: return outcome-unknown and current authorized state, never reapply.
5. **Read/project after commit:** retain the applied receipt revision R. Read the authoritative aggregate until at least R is visible, within a bound; return the command receipt separately from a possibly newer current view. Do not present a cached/proposed payload as current state. If confirmation is unavailable, keep the command resolving and do not broadcast an unconfirmed match. Clients discard older snapshots/events. Partition/dirty-read caveats prevent claiming universal linearizability merely from CAS or any one receipt read.

**Final consent is one CAS**, binding title, roster/context/proposal versions and all included participants' consents. A competing veto, undo or roster edit changes that aggregate and forces re-evaluation. Only one current proposal can become chosen. After finalization, stale votes cannot reopen it; reopen is explicit. Viewing availability is evidence, not an atomic reservation of a provider entitlement.

**Bounds — proposed, to measure:** up to 8 participants/screens, four short rounds of about 20 candidates, a 256 KiB encoded-payload ceiling, two outstanding live tickets per participant, and at most 64 recent receipts per actor with a declared retry window (initially test 15 minutes). Keep actor high-water marks for the room lifetime. Do not evict receipts promised within that window to accept more traffic: throttle/reject safely at a bound. Full aggregate replacement amplifies writes and per-room contention; independent rooms distribute across shards, but one large/hot room does not scale through more API instances. Start with a small shard count and measure before changing allocation; no copied auth-table shard layout is automatically correct.

**Expiry/deletion:** enforce immutable expiry on every API read/mutation and socket view/lease. Cleanup CAS-replaces the exact live generation with a minimal tombstone, clearing votes/secrets and retaining enough nonsecret fencing metadata. A stale mutation loses to that version; updates never upsert missing rooms. Only creation inserts, using a server-issued short creation lease/immutable ID and a database-time insert deadline. The existing auth [insert guard](../../goodwatch-webapp/app/server/auth/crate-adapter.server.ts#L349) and [tombstone policy](../../goodwatch-webapp/app/server/auth/IMPLEMENTATION.md#L67) are precedent, not room compatibility proof. **Initially keep the minimal nonsecret closed-generation tombstone; do not automatically purge it.** That prevents a delayed insert from finding the ID absent. Finite retention alone cannot fence an arbitrarily delayed already-accepted write: physical purge needs a proved in-flight lifetime/fencing protocol, not just a wall-clock lease. Never reuse IDs. Monitor tombstone growth and rate-limit room creation; this storage cost is an explicit tradeoff, while private votes/credentials still expire.

A pre-expiry command may be in flight when the deadline passes. CAS alone is not a wall-clock expiry fence: reject post-expiry projection/acknowledgement, close subscriptions, and let tombstoning fence outstanding writes. If strict “no storage mutation after deadline” is wanted, prove a database-time mutation guard separately; do not imply it is already achieved. Backups/old storage versions need retention independently of logical deletion.

**Durability:** propose two replicas and REQUEST translog durability, initially waiting for **two active copies**, rather than silently copying auth's wait-for-one policy. These are table settings to validate, not deployed facts. [5.10 table docs](https://cratedb.com/docs/crate/reference/en/5.10/sql/statements/create-table.html) explain request flushing and that active-shard checks occur before writes and do not eliminate every failure. One lost node should be exercised with this policy; loss of sufficient copies blocks writes. Do not force-promote stale replicas to keep choosing live. Restore/partition tests must establish actual recovery behavior; do not promise zero-loss or availability under arbitrary partitions. Existing [snapshot/retention operations](../../goodwatch-crate/README.md#L5) need explicit room coverage and restore proof.

## Realtime transport and safe subscriptions

**Recommend HTTP commands + WebSocket pushes, not commands over sockets initially.** HTTP preserves current Remix routing, validation, idempotent retries and own-command responses; WS supplies prompt server updates. A unified socket protocol would still need acknowledgements, deduplication and recovery while duplicating transport handling. No normal client polling.

Use a **small Node + ws gateway** behind the exact **wss://yepwatch.com/api/yepwatch/v1/realtime** route. It owns upgrades, connection admission/backpressure/heartbeat and shutdown; it does not implement voting or query Crate/catalog. It calls private namespaced API projection/ticket adapters with a server-only service credential and participant-scoped subscription lease. Thus HTTP instances keep domain logic/storage, gateway instances keep only reconstructible connection maps.

This is an initial process addition justified by the current host: [remix-serve entry](../../goodwatch-webapp/Dockerfile#L66) owns HTTP and [custom shutdown](../../goodwatch-webapp/app/server/lifecycle.server.ts#L228) closes HTTP requests/connections. Node explicitly says [closeAllConnections does not close upgraded sockets](https://nodejs.org/docs/latest-v24.x/api/http.html#servercloseallconnections). The [ws source/docs](https://github.com/websockets/ws#client-authentication) demonstrate explicit upgrade/auth handling. Embedding a gateway later in a controlled HTTP entrypoint is possible; discovering/patching remix-serve's server is not the proposed starting design.

**Subscription protocol:**

1. Obtain a fresh initial HTTP snapshot and **POST /realtime/tickets** with actual room credential/cookie, CSRF protection and current room/participant generation. Issue a short-lived single-use random ticket (propose 30 seconds), stored as a verifier in the aggregate and bound to room, participant, capability epoch and read scope.
2. Browser WebSocket construction does not offer arbitrary Authorization headers ([WHATWG interface](https://websockets.spec.whatwg.org/)). Open the fixed WSS URL; send the ticket in the **first application frame**, never URL/query/subprotocol. Browser Origin must match the configured YepWatch allowlist; missing native Origin still requires the same ticket. Do not use Origin as identity.
3. Allow only a tiny unauthenticated frame budget and short authentication timeout; subscribe/send no room data yet. The gateway redeems via gateway-authenticated **/realtime/internal/attach**. The API verifies/consumes the ticket by CAS and issues a short scoped subscription lease. Replay/expired ticket fails; a room code is insufficient.
4. Establish bus subscription before reading the current authorized shared view; buffer/coalesce revision hints during attachment, then fetch at least the highest observed revision. Initial shared snapshot plus client's private HTTP snapshot closes the subscribe/snapshot race. A lease proves access, not the right to request another room or other members' data.
5. The gateway sends committed **room.snapshot / room.updated** with generation/revision and a safe shared view: joins/leaves, ready states, aggregate deck progress, round/shortlist/consent/chosen changes. Own private vote state comes only from authenticated HTTP snapshot/command responses. Do not broadcast voter/title/like/pass pairs or raw account inputs.
6. HTTP response and push may arrive in either order; revisions/command receipts reconcile them. Animate one's own swipe immediately as pending. Announce a shared match/choice only after confirmed server state. “Multiplayer” does not authorize speculative all-like results.
7. On disconnect/gap/background resume, reconnect with backoff/jitter, a new ticket and last seen generation/revision. **Resnapshot is the initial recovery contract**; no durable event replay is promised. Coalesced full shared views can skip revisions; deltas, if later introduced, require contiguous versions or reset. Fetch own pending operation outcomes over HTTP before replaying.

Check membership/epoch/expiry in API projections before forwarding; leases expire/renew on a bounded heartbeat. Invalidation triggers revocation checks; expiry has an explicit close timer. If authority cannot be checked, stop sending room data and signal reconnecting. A coalesced server-side audit catches lost revocations too; do not promise instant revocation under a network partition. Already delivered data cannot be recalled.

Aggregate progress/shortlist can imply a partner's preference; explain that unavoidable small-room inference. Promise that individual votes are not exposed in shared payloads, not secrecy of unanimous outcomes. Presence (“connected/reconnecting”) is nonauthoritative, in gateway memory or short-lived Valkey TTL hints. It never removes a voter, grants membership, supplies readiness or changes consensus.

## Multi-instance fanout, repair and hosting

Each confirmed mutation sets a **pending notification revision in the same room CAS**. After acknowledgement, publish only room ID/generation/revision through a prefixed **Valkey Pub/Sub channel**. Gateways coalesce hints and request authorized shared projections through the API; no client/gateway receives a raw database aggregate. Publisher/subscriber connections are separate. [Valkey](https://valkey.io/topics/pubsub/) documents at-most-once delivery; [ioredis](https://github.com/redis/ioredis#pubsub-1) documents cluster propagation. Verify the installed client version's reconnect/resubscribe behavior; library wording is not an exactly-once application guarantee.

| Failure/race | Proposed repair |
|---|---|
| Commit succeeds, process crashes before publish | A server-side recovery worker discovers indexed pending markers, rereads each by PK and republishes. Search refresh can delay discovery; it does not decide current state. Do not use refresh_interval=-1 as auth does without another complete discovery mechanism. |
| Publish succeeds, process dies before clearing marker | Duplicate invalidation is harmless; deduplicate by generation/revision. Clear only the published pending revision with CAS, preserving any newer pending revision. Housekeeping must not increment semantic room revision or trigger a loop. |
| Publish acknowledgement but subscriber misses delivery | Successful publish is not receipt by every gateway/client. Periodically audit **active rooms server-side** by authoritative revision, propose every 10 seconds; push repair snapshots and revalidate leases. This is an integrity audit, not the normal client live transport. |
| Valkey/node outage or subscriber reconnect | Retain pending markers; retry with bounded backoff. Gateway marks live transport degraded, resubscribes then resnapshots; server audit repairs missed state. HTTP commands may commit while updates are degraded, so UI must say so. No hidden polling-first mode. |
| Out-of-order/duplicate hints, version gap, gateway restart | Ignore older revisions; rebuild connection state from fresh credentials and snapshots. No in-memory event log is authoritative. |
| Expiry/revocation races | Enforce current room capability/epoch/expiry in projections, close local subscriptions, and send no stale cached view while authorization is unavailable. Tombstone/expiry timers and audit cover missed bus hints. |

A marker is an **outbox-like latest-state repair**, not a durable event history: transitions may coalesce and unseen cosmetic animations may be skipped. It guarantees neither exactly-once delivery nor completeness after destructive data loss. Keep terminal/expired state long enough to notify/close subscriptions, while deleting private fields. Shared worker duplication is acceptable with CAS; no cluster-wide in-process lock or Kafka is needed.

Existing [Valkey ADR](../adr/0003-redis-cluster-of-masters-with-volatile-lfu.md#L10)/[config](../../goodwatch-cache/valkey.conf#L15) intentionally allow cache loss/no replicas. That remains compatible because neither room truth nor the only notification-repair record is there. Normal delivery needs working Pub/Sub; a bus outage is a visible degraded condition, not successful realtime.

[Traefik documents WS/WSS upgrades through HTTP routing](https://doc.traefik.io/traefik/master/user-guides/websocket/); the repo describes v2.10/multiple proxy hops ([routing](../../goodwatch-proxy/traefik/goodwatch-balance.yaml#L20)). The newer guide is capability context, **not proof of this deployment's timeout/upgrade configuration**. Prove upgrade, Origin preservation, idle timeouts and health routing through the actual version/hops. Match the exact WS path separately from HTTP ticket/internal paths; do not cache upgraded traffic or retry established socket streams.

No sticky-session correctness requirement: a socket naturally stays on its gateway, while commands can reach any API instance. Existing GoodWatch member stickiness is incidental. Start with one gateway if an acknowledged reconnect gap during restart is acceptable; two allow rolling replacement, and the multi-instance proof must use two. On SIGTERM stop readiness/new upgrades, notify restarting, close clients (1012), drain with a bound, then terminate remaining sockets before the container stop deadline. Ping/pong detects dead connections; cap message/frame size, per-IP/participant connections, send buffers and unauthenticated dwell time. Slow clients get a resync/close, not unlimited queues. No database credentials in the gateway; protect its private API service credential/leases and never log ticket frames.

## Product, UI and deployment boundaries retained

Screen eligibility remains proposed: couch participants share one confirmed country/usable-service context; remote screens each supply theirs, possibly using different providers. Personal saved subscriptions are editable suggestions, not automatically available on a couch. Use all database choices. Coarse indexes generate candidates, country-qualified evidence verifies watchability, and candidate search widens beyond a fixed popular first-N before claiming no intersection. Unknown/stale coverage is not verified no-match; offer context correction/new round/explicit unverified discovery without silently relaxing vetoes.

Preference ranking is per person with equal weight, Seen/duplicate exclusions and neutral options for guests lacking taste. Freeze roster/context/deck per round; late join waits for a new round, edits invalidate proposals/consent, disconnect does not silently exclude. A bounded unanimous shortlist plus final consent goes beyond the first overlapping like; compromise requires explicit agreement. Movies-first remains a recommendation.

Retain **Expo Router + Expo Web** for matcher/browser guests ([routing](https://docs.expo.dev/router/introduction/), [web](https://docs.expo.dev/workflow/web/)); replace the guest UI with a small DOM client only if measured loading/accessibility/link reliability warrants it. Flutter/Capacitor remain alternatives with different language/UI/bundling costs, not reasons to migrate GoodWatch. Use Gesture Handler/Reanimated plus equivalent labelled buttons/undo, keyboard, reduced-motion/VoiceOver/TalkBack checks ([gestures](https://docs.expo.dev/tutorial/gestures/), [accessibility](https://reactnative.dev/docs/accessibility)). Query stores authoritative HTTP/pushed snapshots; local React state owns pending animation/forms. Wire [foreground/network state](https://tanstack.com/query/latest/docs/framework/react/react-native); WS replaces normal refetch intervals.

Keep **yepwatch-app/** isolated with its own npm lockfile; **goodwatch-webapp/packages/yepwatch-contracts/** contains portable DTO/schema/transition types only; **app/server/yepwatch/** owns domain/storage/adapters; a sibling **yepwatch-realtime/** owns the small gateway and consumes contracts/API. Add local package copies deliberately to the existing webapp Docker build context. No React/server/DB imports in contracts or native bundles; no catalog duplication in the gateway. [Dependency isolation constraints](https://docs.expo.dev/guides/monorepos/). Future companion can share contracts/identity primitives, without deciding its store packaging.

Use yepwatch.com for UI/API/WSS and goodwatch.app for issuer. Required [Apple association](https://developer.apple.com/documentation/xcode/supporting-associated-domains)/[Android App Links](https://developer.android.com/training/app-links) stay at standard paths. Distinguish browser/native callbacks; preserve browser guests and a visible code/reopen-original-link path after installation rather than assuming deferred invite recovery. Stage with separate origins, app IDs, OAuth clients, secrets and data; test real installed builds. EAS remains optional ([local builds](https://docs.expo.dev/build-reference/local-builds/)); OTA must respect [runtime compatibility](https://docs.expo.dev/eas-update/runtime-versions/). Optional Google login needs actual [Apple 4.8](https://developer.apple.com/app-store/review/guidelines/#login-services) assessment.

Keep attribution/link-kind metadata and honest provider handoff: [TMDB FAQ](https://developer.themoviedb.org/docs/faq), [watch-provider requirements](https://developer.themoviedb.org/reference/movie-watch-providers). Existing new-product licenses/entitlements remain unverified. Log allowlisted latency/conflict/reconnect/repair/degradation/lifecycle metrics, not votes, emails, taste vectors, credentials, ticket frames or invite URL values; disable replay capture on private room surfaces. **Proposed UX targets:** local swipe feedback within one frame; p95 commit-to-other-foreground-screen update below 300 ms in a stated staging network test; reconnect to current state within two seconds after connectivity/auth recover. These are targets to validate, not throughput/latency promises.
