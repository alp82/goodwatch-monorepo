1. The plan in short

  • Two jobs, two sources. The free TMDB API keeps the provider lists of every title fresh every day. TMDB watch pages are fetched only for the links, and only where something changed or a tier says it's due.
  • Fetch less, not faster. The API diff tells us which (title, country) pairs changed. Pairs with no offers, countries the page can't show (Niger), and deleted titles are never fetched.
  • Tiers. Opened titles and everything that changed: daily. Top ~950 titles: daily. The next ~3,800: every 3 days. The rest: a rolling sweep, oldest first.
  • One global pace. A shared token bucket in Valkey paces all 12 random workers together. A controlled ramp finds the safe rate: test up to 4 req/s and run at 3 req/s (about 2.2× today).
  • Recovery stays honest. The existing gate backs off and probes on its own. During a block, the last verified links stay up and new offers fall back to TMDB's "where to watch" link. No proxy is needed to keep links on the site.
  • Ask before routing around. Email JustWatch for free non-commercial access. Optionally tell TMDB who we are before ramping. Keep the paid proxy (DataImpulse first, Geonode backup) designed but unbought.
  • Cost: $0/day as recommended. Worst case with every optional item turned on: about $0.37/day.

5. Refresh planning

How a pair gets fetched

Daily: TMDB API watch/providers for all 361k titles→ Per country: hash of sorted (type, provider id)→ Compare with the hash at the last verified page fetch→ Changed, new, or due by tier → page queue
  • Detector cost. 361k calls a day is 4.2 req/s, about 10% of TMDB's stated API ceiling, and 1–2 GB a day. It is a separate upstream (api.themoviedb.org) with its own gate, so a page block never stops the lists.
  • Daily is the useful maximum. TMDB builds provider data from one daily JustWatch export, 8–32 h behind, so polling more often finds nothing new.

Pairs that never need a page fetch

  • Countries with no offers. Documents are created only where the API lists a country, but they're never removed when a country drops out. Mongo holds 9.3 M documents and Crate 8.27 M pairs, so up to about 1 M documents may be such leftovers estimate. When the API drops a country, write an empty offer list and stop. Don't fetch the page to confirm.
  • Countries the page can't show. Niger today (section 9). Keep the API list, store no links, and check once a month with one canary page.
  • Unchanged pairs between tier dates. If the API hash is the same as at the last page fetch, the links are very likely still valid. Only prices and quality can drift, which the tier dates cover.
  • Deleted titles. Already excluded by tmdb_deleted. Section 9 adds the 404 path.

6. Throughput and politeness

One global pace, random workers unchanged

  • Token bucket in Valkey. A GCRA limiter keyed per upstream (tmdb:web, tmdb:api). Every fetch takes a token right before its request, whichever of the 12 workers Windmill picked. The bucket holds the rate; the workers don't need to know about each other.
  • Pace per worker follows from it. At 3 req/s, each worker averages 0.25 req/s. Per egress IP it's 3 req/s divided by the number of worker hosts, about 0.75 req/s across four hosts.
  • Bigger jobs, kept-alive connections. Each job claims up to 20 due pairs in tier order and works through them on one HTTP/2 connection, instead of one job and one Mongo connection per pair. That is where the speed-up comes from; TMDB sees fewer TLS handshakes, not more requests.
  • Concurrency. With requests under a second, 3 req/s needs only 2–3 requests in flight. Cap in-flight requests at 6 globally (a Valkey counter with lease expiry).

Adaptive rate (AIMD)

  • Add 0.1 req/s after every clean 10 minutes, up to the operating rate.
  • Halve the rate on a 429, on more than 1% 5xx in a minute, or when p50 latency doubles against the 24-hour baseline.
  • After the gate reopens, restart at 25% of the operating rate and climb again.

7. Blocks and recovery

What already works (commits c12d9dae, dffc5e98)

  • One gate per upstream (tmdb_streaming_upstream/tmdb_watch) shared by all workers. It classifies responses as challenge, 429, other 403, or 5xx.
  • Backoff runs 30, 60, 120 … up to 1,440 minutes, and a longer Retry-After wins. A fenced single probe reopens the gate only after a fully validated 200.
  • A block releases the pair without touching its links, failure counter or schedule. A Discord alert goes out after 2 hours blocked, with one recovery message.

What to add

  • Soft and hard limits. A single 429 with Retry-After under a minute halves the rate (AIMD) instead of closing the gate for 30 minutes. Challenges, repeated 429s and 403s still close it.
  • Slow start after reopening (section 6).
  • Graceful degradation. While the gate is closed, the API detector keeps running, so provider lists stay daily. Pages keep their last verified links. New offers show TMDB's "where to watch" link, which the site already uses as a fallback. Users keep a working link either way.
  • Freshness alert. Warn when T0 or T2 falls behind its cadence by 24 h, not only on gate state.

9. Data quality

Niger: TMDB's page can't show it

  • What happens. /movie/603-the-matrix/watch?locale=NE returns HTTP 200 with the country selector set to DE and every clickout tagged uct_country=de. The page fell back to the visitor's country (Germany for both this machine and Hetzner). locale=NG works. Checked 2026-10-17.
  • Why it matters. validate_selected_country correctly refuses the page, so no wrong data is saved. But 46.8k titles (104k rows) have Niger offers, and they took 11% of all fetches in the observation window.
  • Fix. A small list of page-unsupported countries, starting with NE. Those pairs keep the API provider list with no links and are never fetched. A monthly canary on one Niger page removes the country from the list as soon as TMDB renders it. Why TMDB fails on NE is unknown; it may read it as a language code.

404s and deleted titles

  • Today a 404 (5 of 2,420 fetches) climbs the failure ladder up to 7 days and repeats forever.
  • Fix. On a 404, call the TMDB API for the title. If the API also answers 404, set tmdb_deleted (the flag already exists and stops all crawling). If the API answers 200, refresh the watch URL from its link (a changed slug or a merge) and retry once. Also apply /changes deletions directly.
