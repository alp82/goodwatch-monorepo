Summary and recommendation

The block is not on the IP. TMDB challenges any request that sends the User-Agent Mozilla/5.0 over HTTP/1.1, which is exactly what fetch.py sends through requests. From the "blocked" IP 78.46.209.172, HTTP/2 or an honest User-Agent gets a 200 right now. Changing that one header would let the current crawler run again today.

  • No paid API with deep links fits $1/day. The cheapest is Movie of the Night at $299/month for 1 M requests. Watchmode starts at $349/month. JustWatch, Reelgood and Gracenote sell only through sales contracts.
  • TMDB's watch data is JustWatch data. Every TMDB clickout is a click.justwatch.com redirect tagged clickoutType: jw-content-partner-export-api. JustWatch's own GraphQL API returns the same offers with direct service URLs, availability dates and quality. It returns many countries and many titles in one request, at about 200 times fewer bytes per (title, country) than TMDB's watch page.
  • We already hold the JustWatch id for 278k titles. It sits inside the stored clickouts (title_context.jwEntityId, e.g. tm10 for The Matrix), so mapping TMDB ids to JustWatch ids is mostly done.
  • Our own Hetzner IPs fit the budget at $0. Every architecture below runs on them. Residential proxies are affordable only for the small JustWatch payloads, and only as a capped emergency path.
  • Recommendation: architecture C, built in steps.
    • Fix the client fingerprint and put a single upstream circuit breaker in place. That alone restarts the crawler.
    • Then make JustWatch GraphQL the main source of links, batched, with the full catalog refreshed daily (about 36k requests and 2 GB a day).
    • Keep TMDB's free API as an independent check and the fixed TMDB page crawler as the fallback.
    • Cost about $0/day, with an optional $5 one-off proxy credit capped at 0.3 GB/day.
    The catch is the terms: JustWatch forbids scraping and commercial use, so that choice is the owner's (Q2).

Crawling methods

Request volume

  • Batch per request. The TMDB page covers one country per request, TMDB's API all countries, and JustWatch GraphQL several titles × all countries in one document. Going from page to JustWatch cuts requests about 250× and bytes about 200×.
  • Change detection.
    • TMDB /changes doesn't carry provider changes (TMDB staff, 2024). The working detector is to poll watch/providers per title, which is free, all countries per call and about 2 KB, and diff the provider set for each country. All 361k titles take about 0.7 GB and 10 hours a day at 10 req/s.
    • JustWatch has a per-country daily feed. newTitles(country, date, pageType: NEW) listed 600 US titles with new offers for 2026-10-16. It covers additions only, so removals and price changes still need a sweep. JustWatch's maxOfferUpdatedAt(country) per title also shows whether anything changed.
  • Priority order, each from its own budget:
    1. Titles a member opens (the existing f/priority/crawl_all).
    2. Countries the detector flags as changed.
    3. The JustWatch new-offer feed.
    4. Popular titles.
    5. A rolling sweep, oldest first.

Conditional requests and caching

  • The TMDB page ETag changes on every response, so revalidation is useless there.
  • GraphQL POSTs aren't cacheable.
  • The useful "cache" is our own: hash each country's offer set, skip the write and the Crate copy when the hash is unchanged, and keep maxOfferUpdatedAt to skip fetching.

Client fingerprint

  • What is needed: HTTP/2 (httpx with http2=True), or an honest User-Agent that doesn't pretend to be a browser. Either passes TMDB's present rule.
  • curl_cffi copies a real browser's TLS and HTTP/2 fingerprint. It helps against fingerprint rules but runs no JavaScript, so it can't pass a real JavaScript challenge or an IP block. It's worth keeping as a second client profile.
  • FlareSolverr and reusing clearance cookies is browser automation to get around a challenge. Not recommended; see legal.

Polite pacing (AIMD)

  • One token bucket per upstream (TMDB page, TMDB API, JustWatch) and egress path, shared by every worker. Keep it in Valkey or the existing tmdb_streaming_upstream Mongo document.
  • Additive increase: +0.1 req/s per clean minute, up to a ceiling.
  • Multiplicative decrease: halve the rate on a 429, a challenge page or a latency spike.
  • Start at 1 req/s per path.
  • Keep connections alive, with 2–4 concurrent streams on HTTP/2.

Automatic recovery

  • Back off the upstream, not the document. A 403 challenge or a 429 opens that upstream's circuit. Documents are released with no failure count, which differs from today, where every probe writes a failure and re-blocks for 30 minutes.
  • Half-open with a canary. After an exponential, jittered wait (1 → 2 → 4 … up to 60 minutes), send one request for a known-good URL (The Matrix, US). Close the circuit only when it parses.
  • Classify responses: challenge page, 429 with Retry-After, 5xx, parse failure (a markup change, which should alert and not back off), or a genuine empty result.
  • Fail over through a chain: client profile (honest User-Agent → HTTP/2 → curl_cffi), then egress path (host A → host B → IPv6 for TMDB → capped proxy), then source (JustWatch ↔ TMDB page).
  • Health: a Windmill monitor that alerts when a circuit stays open more than 2 hours, or when the hourly success count falls below a floor.

Three architectures within $1/day

A. Fix the TMDB page crawler and drive it by changes

  • How it works.
    • Keep TMDB's watch page as the only source of links, with an honest User-Agent and HTTP/2.
    • One long-running fetch job per egress path replaces 10-document flow runs, with a shared AIMD token bucket.
    • The free TMDB API detector polls watch/providers daily per title and moves changed countries to the front.
    • The rest is a rolling sweep, oldest first.
    • Egress is 2–3 of our hosts plus IPv6.
  • Throughput: 5 req/s per path. With one path that is about 430k pages/day (18 GB, free); with three paths, 1.3 M/day.
  • Time to full freshness: changed pairs within about 1–2 days, bounded by TMDB's own 8–32 h lag. A full sweep takes about 22 days on one path, or 7 days on three.
  • Recovery: a circuit breaker per path with a canary and no per-document failures. On a challenge it switches client profile, then path. It alerts after 2 hours open.
  • Code changes:
    • fetch.py: an httpx HTTP/2 session and honest User-Agent; classify challenge, 429 and parse errors.
    • country_state.save_failure: a rate-limit path that doesn't touch the document.
    • upstream_deadline becomes a breaker with a canary.
    • next.py and the flow become a loop job that runs for 55 minutes.
    • New: f/tmdb_api/watch_provider_diff, the detector.
  • Cost: $0.
  • Risks:
    • TMDB can tighten the rule again; scraping is against TMDB's terms.
    • One country per request, at 42 KB a page.
    • Links lag JustWatch by up to 32 h.
    • Price changes are invisible to the detector, so they wait for the sweep.

B. JustWatch GraphQL as the only source, batched

  • How it works.
    • Map TMDB ids to JustWatch ids. 278k titles come from the stored clickout context; the rest from a one-off search checked against externalIds.tmdbId.
    • Each request asks for about 10 titles × all their countries (aliases), with slim fields and bestOnly.
    • The full catalog is swept daily.
    • newTitles per country runs a few times a day for new offers.
    • A title a member opens costs one request, about 100 ms.
  • Throughput: about 36k requests and 2 GB or less a day, an average of 0.4 req/s. One path is plenty.
  • Time to full freshness: about 10 hours at 1 req/s, so a daily full refresh; new offers within hours.
  • Recovery: the same breaker and AIMD. Failover across our IPv4 hosts (JustWatch has no IPv6), with a capped residential path as the last resort.
  • Code changes:
    • New folder f/justwatch/: id map, a batched query builder, an offer parser into the existing StreamingLink shape, and the new-offers feed.
    • JustWatch packageId is the same id space as providerId in today's clickouts, so service mapping stays.
    • stream_url changes from click.justwatch.com to direct URLs, so provider_name_from_url needs a JustWatch-package branch.
    • The Crate copy is unchanged.
  • Cost: $0, or about $0.3/day if all of it went through a proxy on a weekly sweep.
  • Risks:
    • JustWatch's terms forbid scraping, commercial use and using proxies to get around blocks.
    • The API is unversioned; its schema can change any day.
    • There is no second source when it breaks.
    • Direct links drop JustWatch's click tracking, and some carry JustWatch's affiliate tags (Q3).

C. Hybrid: JustWatch for links, TMDB API for checks, TMDB page as fallback Recommended

  • How it works.
    • B is the main path.
    • The free TMDB API detector from A runs daily as an independent check. When JustWatch and TMDB disagree on a provider set for longer than 48 h, it flags that pair.
    • A's fixed page crawler runs at a low background pace (1 req/s) for pairs JustWatch can't map, and takes over automatically while JustWatch's circuit is open.
    • Egress is gw-worker1–3 and gw-cache1 (IPv4, plus IPv6 for TMDB). Optionally a $5 never-expiring residential credit, used only when every own path is open, with a hard cap of 0.3 GB/day ($0.30).
  • Throughput: JustWatch about 36k requests a day for all 9.3 M pairs, plus TMDB API 361k a day, plus TMDB pages up to 86k a day.
  • Time to full freshness: about 1 day for every pair; hours for new offers and for titles members open. If JustWatch is down, it falls back to A's pace.
  • Recovery: per-upstream breakers with canaries, AIMD per path, then failover first across paths and then across sources, with an alert after 2 hours. No manual unblocking.
  • Code changes: A and B together, plus a source field on each link (justwatch or tmdb_web) and a disagreement report. Build it in steps:
    1. Fingerprint fix and breaker. Hours of work, and it restarts today's crawler.
    2. Loop job and detector.
    3. JustWatch fetcher in shadow mode, comparing against TMDB pages for a week.
    4. Switch the main path to JustWatch.
  • Cost: $0/day normally, and at most $0.30/day while the emergency proxy runs.
  • Risks:
    • JustWatch's terms (the same as B), but any single source can fail without taking links down.
    • More moving parts than A.
    • Shadow mode needs a week of comparison before switching.

Why C:

  • It meets every goal. It is about 30 times fewer requests than today's 7-day target, refreshes daily instead of weekly, recovers on its own, keeps the links, and costs $0.
  • It doesn't bet everything on one undocumented API.
  • If the owner says no to JustWatch (Q2), A is the plan. Step 1 of C is the same as A's first step either way.

Questions for the owner

  1. Q1. May we apply the one-line client fix (honest User-Agent or HTTP/2) and the circuit breaker now? That restarts link crawling without any new source.
  2. Q2. Are you comfortable reading JustWatch's GraphQL API directly, given its terms forbid scraping and commercial use? Or should we stay on TMDB only (architecture A)?
  3. Q3. JustWatch returns direct service URLs, some carrying JustWatch's affiliate tags. Should we store them as they are, strip the tags, or keep sending clicks through click.justwatch.com?
  4. Q4. Which hosts may we use for outbound crawling: gw-worker1–3, gw-cache1, IPv6? Should the database hosts (pgnode, mongo, vector) stay out?
  5. Q5. May we buy a $5 never-expiring residential proxy credit (DataImpulse or Geonode) as an emergency path, hard-capped at 0.3 GB/day?
  6. Q6. What freshness do you want: daily for all 139 countries, or daily for popular and opened titles and weekly for the rest? Any countries we can drop?
  7. Q7. Is GoodWatch commercial today (ads, affiliate, subscriptions)? That decides whether we need TMDB's commercial license, and whether to ask JustWatch for a partner quote.
