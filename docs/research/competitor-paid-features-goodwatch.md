## Principal findings

GoodWatch already has substantial code for advanced discovery, personalized ordering and taste explanations, movie and episode watch logs, rewatches, show progress, a Wishlist, shareable top-five lists, several import formats, and an authenticated read/write MCP interface. Calling it only a discovery site would substantially understate current main. Conversely, calling it a complete replacement for paid tracking products would overstate flexible list management, historical statistics, calendar/alert delivery, portability, automatic synchronization, and native/offline experiences. See the feature-level evidence tables, not these broad family names, when comparing competitors.

The inspected score, Wishlist, tracking, import, and share-list entry points gate persistent personal data on membership, not a paid entitlement. The MCP connection page describes a free account. Those are positive, bounded observations about these code paths. They do **not** establish a permanent pricing promise, unlimited capacity, production flag settings, or whether a third-party assistant/provider requires payment. A payment-UI search alone would be inadequate evidence. Relevant gates and numerical limits are enumerated below. [C05] [C07] [C09] [C16] [C22] [C23]

Several important “planned” findings in older research have already changed: tracking and personal order have current implementations; account deletion still does not have a merged consumer journey; IMDb expansion and SIMKL/Netflix/TV Time history imports remain unfinished; and availability recheck work has code even though its execution issues remain open. These distinctions matter more than issue counts.

## Preserve the domain meanings

Use [CONTEXT.md][C00] and the tracking ADRs [C06], rather than importing another product's vocabulary:

- **Want to See** is an intention; **Wishlist** holds those intentions. Want to rewatch is Want to See on an already Seen title. It does not itself create a watch or reset a show.
- A **Watch** is an individual movie/episode occurrence, with its own date precision. A **Pass** is one run through a show's episodes. Earlier passes survive Watch again; current progress uses the current pass.
- **Seen** for a movie follows a watch or rating; rating a movie creates an undated watch. Marking it not seen removes the score and logged watches after confirmation. A show's rating does not change its stored show status, although a rated show is treated as seen by discovery's seen filtering.
- A show's five stored states are **Not started, Watching, On hold, Dropped, Seen**. Only a member action or import changes state. Finishing the last aired regular episode can make it Seen; later episodes airing do not automatically turn it back into Watching. “Caught up” is a presentation label, not a sixth stored state.
- **Next episode** and progress follow regular episodes in the current pass; specials do not define whole-show completion. Watch again needs at least one watched regular episode. Imports protect existing On hold, Dropped, and Seen choices.
- **My library** is the member's marked titles by status, not a chronological diary or physical media collection. **Everyone** in the taste comparison means the GoodWatch aggregate score, not the ratings of other GoodWatch members.

These rules differ from generic “watched”, “completed”, “watchlist”, and “sync” claims. Migration must preserve their consequences explicitly.

The general importer caps a submitted file at **20 MiB** and normalized observations at **50,000**. ZIP safety limits include 200 entries for general archives (a separate filtered Kodi allowance), 32 MiB per expanded entry and 64 MiB total expansion. MAL gzip has its own 32 MiB expansion guard. The persisted import history reader shows the latest 100 non-preview runs; this is a read-history bound, not “only 100 imports allowed”. Preview account-state snapshots use 100,000-row limits. Consequently, neither “unlimited imports” nor “lossless for any library size” is established. [C16] [C21]

Episode matching is also a migration feature. The resolver uses catalog identity/numbering and mapping evidence; ADR 0012 forbids silently changing stored watch identity to match a presentation order. Source shows, anime cours, specials, alternate episode orders, and missing catalog titles need real-file acceptance. No silent inference should turn a rating, aggregate playcount, or unverified source date into fictitious individual viewing history. [C06] [C18]

## Access, flags, and numerical limits

These are different kinds of constraints: membership gates, business rules, protective request quotas, parser bounds, and read/display truncation. They should not be collapsed into a single “free tier limit”. There is no evidence here of a paid upgrade removing them.

| Constraint | Actual code/configuration rule | Implication for parity claims |
|---|---|---|
| Guest ratings | 20 distinct scored titles; existing score edits permitted. Local per-title interaction is mutually replacing. [C05] | “Free unlimited ratings without an account” is false. Member ratings are a different path. |
| Guest persistence | Local storage, memory fallback; no server-backed episode/watch history or favorites. [C05] [C07] | A guest browser session is not a cloud-synced tracking account. Sign-up migration needs its own acceptance test. |
| Taste readiness | Five liked, fingerprint-bearing titles for taste match; separate five-rating guest For you threshold. [C01] [C03] | A newly created account cannot be promised immediate fully personalized recommendations. |
| Discovery/search | 40/page, max browse page 250; ranked web search 100 results, query 512 characters. [C01] [C02] | Result-window bounds, not a subscription tier or full-catalog export API. |
| Network search rate | 10/30 seconds and 60/600 seconds when trusted client-IP configuration is present; shared IPv6 /64 grouping. Without a trusted address the per-visitor limiter is not applied. [C02] | Shared household/network usage can hit a throttle. Current production header/configuration was not read. |
| Share list shape | Exactly five unique titles; title 80 characters; owner/public readers 200 lists. [C14] | No general variable-length list parity; creation without a cap does not prove unlimited retrievable lists. |
| Tracking reads | 200 movie occurrences per movie; 20,000 show occurrences across passes for one show; separate upcoming/aired queries also cap at 20,000 rows. [C07] | These are reader limits, not paid allowances; large-history fidelity must be tested. |
| Imports | General 20 MiB/50,000 observations; IMDb 10 MiB/50,000 rows; expansion guards and history/snapshot reader bounds described above. [C16] [C17] [C21] | No unlimited-size or universal-lossless-import claim. |
| Bulk rescore | At most 50 scores per request; larger selections are chunked by the UI; five concurrent server writes. [C08] | Batch sizing, not an account score-count cap. |
| MCP request/write rate | 60 requests/minute and 1,000/hour/member; additionally 300 write units/minute and 2,000/hour; heavyweight writes cost five units. Batch inputs max 50, with per-item results. [C23] | Read/write integration is useful but rate-limited. Batch success is not necessarily all-or-nothing. |
| MCP smarter ranked search | 20 uncached admitted attempts/member/UTC day; one in flight; normalized query cached 60 seconds, cursor retained 15 minutes; cached hits and paging do not spend another attempt. Failures after admission can consume an attempt. [C23] | The ordinary catalog tools and smarter ranking have different budgets. Never market unlimited AI search. |
| MCP response size | Standard search/discovery returns up to 40 titles per page. [C22] | Pagination is required; not a full-account backup contract. |
| Member storage quotas | No paid-entitlement check or explicit count limit found in score/Wishlist writes. Tracking and list readers still have bounds. [C07] [C09] [C14] | Safe internal statement: “No member count quota found in these writers.” Unsafe public promise: “Unlimited everything forever.” |

Current main's relevant switches are concrete:

- `BETTER_AUTH_ENABLED` must be exactly `true` to enable the new auth runtime. MCP resource/auth configuration is also required; browser cookies alone are not bearer authorization. Read/write consent scopes are distinct. [C24]
- `REC_MCP_READ`, `REC_MCP_WRITE`, and per-tool `REC_MCP_*` variables are evaluated for each member/tool. Unset means enabled; explicit off disables, and comma-separated member IDs can restrict access. These are rollout/operations switches, not a paid plan. [C23]
- `REC_CONNECTOR` defaults off in the remaining general feature registry, but it is not the MCP endpoint's master authorization switch. The current `/use-with-ai` page and MCP policies must be checked independently. [C22] [C26]
- Old tracking, taste, age, and personal-order preview flags in historical issues are not current gating evidence. Current main reader/UI paths and the narrowed feature registry supersede those references. Actual deployed environment values remain **unknown**. [C03] [C26]

## Initial gap hypothesis — provisional pending competitor research

The most likely high-value parity work concerns preserving a member's investment and helping them return regularly. These are audit hypotheses, not approved issues or a build sequence.

| Hypothesis | Why it may matter | Existing foundation / important boundary |
|---|---|---|
| Full export and reliable migration are an adoption prerequisite | A person with years of watch history needs a reversible move, not just an importer accepting a file. | Import receipts, source IDs, watches/passes and MCP reads exist; a portable complete export and round-trip contract do not. Account deletion remains unmerged. |
| Flexible lists are a major gap | Top-five sharing and a single Wishlist cannot represent large themed lists, priority queues, folders or jointly maintained lists. | Keep ordered share-card lists as a distinct product. Do not claim custom-list parity until length, privacy, ordering, import/export and collaboration are compared separately. |
| Historical watch statistics and annual summaries are a major gap | Rating taste charts answer a different question from what/how much/when someone watched. | Watch rows provide a basis, but date precision, missing runtime, repeats and episode mappings must be handled explicitly before aggregate promises. |
| Calendar/iCal and outbound release/availability alerts may drive return use | A member should not need to reopen the website to learn about a release if the competitor use case is external delivery. | Upcoming and arrival signals exist in-app. Freshness, preferences, delivery channels, time zones, and leaving-date evidence are still separate work. |
| Automatic tracking/sync may determine whether users switch | Manual updates and export files can be too much work for heavy TV/media-server users. | One-time Plex/TMDB imports and MCP writes are useful foundations; they do not constitute playback scrobbling or maintained bidirectional sync. |
| Native/offline/household features need demand validation | These can be substantial product work with platform and synchronization costs. | Responsive web UI, cloud member storage and content filters cover parts of the value, not native clients or household identities. Their priority depends on competitor evidence and user jobs. |
| Recommendation/discovery differentiation may already be stronger than historical roadmap notes suggest | Service-aware filtering, taste groups and personal ordering exist now. | Validate quality, cold start, coverage and real workflows rather than treating model/prototype names or percentages as parity proof. |

Separate useful consumer capability from presentation or patronage. Share-card themes already provide a cosmetic option; custom posters, profile styling, supporter badges and status flair should have their own comparison rows and lower default priority than keeping history or exporting data. Do not count “support the developer” as a missing functional capability. Conversely, list collaboration and privacy are functional even if a competitor bundles them with cosmetic perks.

Professional-only needs—commercial audience research, enterprise catalog licensing, bulk studio analytics, professional contact databases, or business API service levels—are outside this consumer audit. No commitment to implement them follows from “every major useful paid competitor feature”. Collection ownership is included only as a potentially relevant consumer job; catalog franchise collections are not an ownership substitute. The competitor reports must decide which products/features actually compete for GoodWatch's intended users.

## Adoption barriers and required marketing verification

1. **Freeze the claim's release snapshot.** Confirm the production build SHA against the source feature path, not just main or a merged issue. Test as a fresh guest and ordinary member outside owner/preview accounts. Capture deployed flag values safely, including MCP read/write/tool restrictions. This audit established no independently verified-live feature.
2. **Prove the proposed free-access wording.** Exercise each advertised feature without a subscription, including imports, share lists, tracking, rescoring and MCP. Publish meaningful numerical limits. Distinguish GoodWatch membership from third-party assistant/provider requirements. Do not promise unlimited storage, search, imports or lists on the basis of absent billing code.
3. **Run source-specific migration acceptance.** Use real member-approved exports for IMDb, full Letterboxd, Trakt, Kodi, MovieLens, Plex, MAL/Kitsu and each new adapter; test preview, confirm, receipt, refresh, replay/idempotency and Undo. Compare counts and individual rows, not just the HTTP status. Track unsupported reviews/lists/episode scores, unknown dates and unmatched titles. Test maximum sizes and catalog gaps.
4. **Establish a lossless-exit contract.** Define and verify export coverage for ratings, reviews, exact watch occurrences/precision, pass/status, intentions, favorites and list order/visibility. Demonstrate round-trip import. A failed-row CSV download or a hand-written MCP extraction script is not an adequate native backup claim. Verify deletion only after its actual merged/released journey exists.
5. **Test tracking semantics and concurrency.** Cover rewatch passes, specials, ongoing shows reaching Seen, later new episodes, alternate numbering, imported states, date/time-zone boundaries, and owner edits concurrent with import/Undo. Include the open #633/#634 cases and histories beyond current reader bounds. Explicitly explain migration differences to users.
6. **Measure availability honestly.** Sample countries/services and old/new titles, inspect timestamps and unknown/conflict cases, verify recheck schedules and provider-list removals, and distinguish catalog-wide rows from a member's saved-service arrivals. Verify deep links and episode availability. No “all services”, “always accurate”, “instant alerts”, or “leaving soon” claim follows from existing stay tables.
7. **Validate MCP in real supported clients.** Complete consent/read-only/write scopes, token refresh/revocation, app removal, mixed-success batches, quotas and rate-limit UX. A tool schema or local integration test is not proof of current ChatGPT/Claude or every other client's usable configuration. Resolve #572's acceptance and document any external client access requirements.
8. **Confirm product-level substitutes, not label matches.** Compare flexible lists, diary, calendar, summaries and social features by the user's task and actual limits. A top-five card, upcoming row, taste chart, or one-time import should not be advertised as a substitute for a general list manager, iCal feed, annual watch report, or continuous sync.
9. **Check the complete ad/offline/device experience.** Observe production including embedded/linked third-party media, mobile browsers, multiple devices and poor connectivity before claiming ad-free, native, offline, or seamless cloud sync. A web manifest and local guest storage do not prove those experiences.
10. **Use a narrow, evidence-backed launch matrix.** For each competitor feature record the competitor's current primary-source entitlement/limits, the GoodWatch released equivalent, remaining differences and a reproducible acceptance result. Resolve the high-value migration gaps before a broad replacement campaign; reserve cosmetic/supporter items and excluded professional features explicitly. This audit does not itself authorize publication or outreach.

Unresolved decisions for the orchestrator's consolidated comparison: which exact competitor entitlements are major consumer jobs; which migration data losses are acceptable; whether “free equivalents” means functional substitutes or exact parity; and which capacity/freshness commitments GoodWatch is willing to maintain. These are comparison/policy questions, not questions sent directly to the user by this research thread.
