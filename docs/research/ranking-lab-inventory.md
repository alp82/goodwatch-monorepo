# Ranking lab inventory and offline experiments

Investigated 2026-09-23 against the initial state at commit `c5398a5e` in the isolated ranking exploration worktree. The lab was subsequently expanded; “initial” and “original” below refer to that commit. This is a prototype evidence note, not a production ranking decision. Sources are the repository's captured candidates and executable scoring logic; no live service was called. The relevant domain outcome is **interest discovery**; the capture cannot establish a **worthwhile suggestion**, since it does not establish unfamiliarity or current availability. [Domain vocabulary](../../CONTEXT.md)

## What exists

The lab is a self-contained HTML ranking simulator generated by embedding `capture.json` into `template.html`. All ranking runs locally against fixed candidates. Its original question is which fingerprint ranking and vector/text combination orders D4 results best. The initial implementation has six presets, free controls, production-relative movement, and named watch titles. The README opening says nine queries/seven presets, but the inspected files have fourteen/six. [README](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/README.md), [template](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html), [builder](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/build.py)

The capture contains 28,000 vector rows (2,000 for every query) and 4,697 text rows. Used fingerprint dimensions range from 3 to 23. All candidate keys have title metadata and every row contains its selected dimensions. Three queries have no text pool: `tarkovsky`, `furious`, `craty`. The remaining text pools range from 54 (`like groundhog day`) to 1,082 (`slow burn space horror`). The capture supports rescoring and source membership experiments, but cannot establish recall outside the captured pools. [Capture](../prototypes/ranking-lab/capture.json)

## Important corrections to the earlier interpretation

The initial README attributes the Tarkovsky loss to a dimension scoring five. The actual capture shows Stalker (1979, `movie:1398`) has 21/23 threshold matches: `non_linear_narrative=1` and `psychedelic=3` miss. Begotten (`movie:1483`) also has 21/23, missing `character_depth=4` and `social_commentary=4`. Their weighted sums are 168.04 and 181.62; You Won't Be Alone (`movie:883083`) matches 23/23 but has weighted sum 148.72. Thus the question is whether all 23 inferred attributes should count equally toward an implied conjunction, not merely whether one borderline value deserves partial credit. [Capture](../prototypes/ranking-lab/capture.json), [original interpretation](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/README.md)

How to Train Your Dragon (2010, `movie:10191`) already matches all five dragon-query dimensions. Its text score is approximately 0.996927 and weighted sum is 46.42. The 2025 remake (`movie:1087192`) is a separate captured candidate. The original watch lookup picks the first matching title string, which can conceal remakes. In this query the loss is evidence strength relative to the sum among full fingerprint matches, not an in-range count failure. [Capture](../prototypes/ranking-lab/capture.json), [`rankRows` and watch rendering](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)

The `text` field is fractional accumulated evidence, not an integer number of phrase matches. For example Kung Fu Panda: The Dragon Knight has text=2.4421 for nonsense while Tim and Eric has text=0.8146. Per-phrase contributions are not captured. The evidence string array can be empty despite a positive score. Controls should say evidence score, and should not imply that changing its cap exactly limits the number of matched phrases. [Capture](../prototypes/ranking-lab/capture.json), [capture schema construction](../../goodwatch-webapp/scripts/ranking-lab-capture.ts)

## Capture and simulator limitations

There are 68 overlapping candidate rows whose selected fingerprint values disagree between the two sources: nonsense 2, cooking 2, space horror 18, heist 11, grief 9, lighthouse 2, sunglasses 3, dragons 9, groundhog 1, time travel 11. These are observed value differences; their cause is not established. For example Damsel (`movie:763215`) has spectacle 9/world_immersion 8 in the vector pool and 7/7 in the text pool. [Capture](../prototypes/ranking-lab/capture.json)

The existing `textfirst` path scores text fingerprints, while `union` preserves vector fingerprints for overlapping IDs. A union comparison therefore changes both candidate membership and, for some rows, the actual attributes. Surface this or choose one explicit canonical fingerprint policy before claiming a fusion strategy caused the ranking change. [compute](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)

Other limits visible in the source:

- The “Production (main)” preset is a local approximation over this capture, not a stored production response. Its sum primary is normalized using candidate-pool min/max. In text-first mode it assigns null cosine to every text candidate, so its cosine tiebreak contributes nothing for those rows. [rankRows/compute](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)
- Text-first suppresses vector-only candidates when text has at least 100 rows; otherwise it appends them. Thus “not in pool” can mean “captured but excluded by strategy.” [compute](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)
- Phrase concreteness uses only the first phrase to decide evidence treatment for every candidate, including those matching a second mood phrase. Query flags and language readings are fixed; no control genuinely reinterprets the query. [compute](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)
- The capture has no schema version, timestamp, commit hash, recorded production result order, or per-phrase numeric score breakdown. Capture construction substitutes zero for missing vector payload attributes, so later readers cannot distinguish a real zero from an originally missing value. [capture script](../../goodwatch-webapp/scripts/ranking-lab-capture.ts)
- Watch titles include plausible positives and obvious counterexamples but are not graded relevance labels. Rank movement alone is not measured search quality. Exact creator intent, concrete relation matching, availability, and unseen titles need additional evidence. [WATCH](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html)

## Offline experiments

The following table comes from executing the original `compute`/`rankRows` functions in Node against the fixed JSON. Experimental formulas replace the fingerprint primary only; all use “Concrete phrase leads” evidence and the original 0.25 theoretical-normalized weighted-sum tiebreak, and retain text-first membership/source behavior. Results are ranks, not quality labels.

Definitions, with `n` selected dimensions, original weighted sum `s`, theoretical lower/upper bounds `lo`/`hi`, and `u=(s-lo)/(hi-lo)`:

- **Saturation:** sum `min(v/6,1)` for wanted dimensions and `min((10-v)/6,1)` for avoided dimensions, clamped below at zero.
- **Weighted saturation:** the same terms weighted by `abs(query weight)`, normalized so the sum of weights is `n`.
- **Dimension sum:** `n*u`.
- **50/50 blend:** `0.5*hardMatchCount + 0.5*n*u`.

## Recommended next prototype

Keep saturation as an explicitly unsettled experiment: it demonstrates that making threshold satisfaction continuous can make Stalker substantially worse. Add the count/sum blend as a distinct experiment about whether strength can compensate for incomplete attribute coverage. Neither is a winner: the blend restores some Tarkovsky/dragon positions but weakens cooking and space horror.

Make each of those tradeoffs visible across all queries before adding further tuning. Use stable media keys plus year, separate captured-but-excluded from absent candidates, show score decomposition and phrase evidence, and inspect fingerprint source disagreements. A small set of guided walkthroughs should cover nonsense versus evidence, Tarkovsky versus inferred conjunction, dragons versus equal full-match counts, and text-first versus mood union.

The next validation question is which titles people consider relevant for each query and why. Then expand beyond this hand-picked capture with held-out queries and explicit relation/creator examples. No production ranking or new domain decision is validated by the present experiments. The existing accepted fingerprint ADR excludes Jev for title fingerprint scoring; this prototype only evaluates ranking of existing fingerprints and does not alter that decision.
