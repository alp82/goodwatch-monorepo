## What main currently does

Sources: [pinned main D4 implementation](https://github.com/alp82/goodwatch-monorepo/blob/055824a282ef22cd77f852ff111a83e77a2c47e7/goodwatch-webapp/app/server/combined-search/d4.server.ts), [combined orchestration](../../goodwatch-webapp/app/server/combined-search/search.server.ts), [balanced blend](../../goodwatch-webapp/app/ui/search/search-model.tsx).

1. Run TMDB multi-search for title/person candidates alongside language handling and interpreted discovery. Native exact titles bypass optional translation; translation is default-off, and disabled non-English discovery uses native/vector-only retrieval.
2. Interpret attribute flags, concrete words and a selected phrase, alongside want/avoid readings for 74 fingerprint dimensions. Current source uses `2 * (want - avoid)`, wanted threshold `0.5`, avoided threshold `-1.2`, and up to all 74 dimensions. This differs from the older map's historical `0.6` summary; current source wins for replay fidelity.
3. Search Crate essence/synopsis for selected phrases. A second phrase qualifies at probability `0.15`; a single non-concrete mood word gates text search. Thin pools may expand to later phrases, keywords and trope names. The current result limit is 100, text pool limit 300 per search; old notes referring to 20 describe an earlier baseline.
4. Rank text candidates by weighted sum normalized with lower bound at most zero and upper bound at least one, plus `0.5 * min(text evidence, 4)`. Text comes first; vector retrieval fills a short list. Vector retrieval prefetches up to 2,000 by cosine then ranks that bounded pool by weighted sum.
5. Apply authoritative metadata eligibility, blend title and discovery ranks, then collapse reliable duplicate identities. Exact normalized titles get a protected score; other title hits mix with `10 / (9 + discovery rank)` rather than raw D4 scores. The result is bounded at 100.

Explicit filters are shared across Crate/Qdrant: media type, all selected genres, year range and optional service/country. Title matching has separate eligibility treatment. Default discovery requires 2,000 votes, while title lookup is not subject to that discovery floor. Public adult opt-in was removed by a later user amendment; adult-flagged results are excluded, unknown classification remains allowed. [Filter implementation](../../goodwatch-webapp/app/server/combined-search/search-filters.ts), [catalog eligibility](../../goodwatch-webapp/app/server/combined-search/catalog.server.ts), [latest implementation amendments](https://github.com/alp82/goodwatch-monorepo/issues/122).

Runtime pins `jev-1.13.0` and a 1,500 ms deadline with basic-search fallback; Crate retains encrypted interpretations/history and spending events, Redis provides cache/coordination. The latest deployment comment reports successful production search and zero-charge cache reuse after the Crate/Redis correction; it does not close overall quality/journey acceptance. [Runtime](../../goodwatch-webapp/app/server/search-runtime/runtime.server.ts), [deployment report](https://github.com/alp82/goodwatch-monorepo/issues/122#issuecomment-5758636388).

## What the prototype branch adds

The branch replaces main's sum ranking inside the production-shaped D4 module with count-based scoring: wanted scores at least 6 and avoided scores at most 4 each earn one hit, a weighted-sum tiebreak spans 0.25, and evidence is capped at one unit. Qdrant executes the equivalent formula over the same 2,000-candidate cosine prefetch. It exports internals and raw text candidates for offline capture. These are branch changes, not adopted main behavior. Its opening “locked/no experiments” comment is stale. [Branch implementation](../../goodwatch-webapp/app/server/combined-search/d4.server.ts), [capture script](../../goodwatch-webapp/scripts/ranking-lab-capture.ts).

The static lab holds 14 query captures, vector/text candidate pools, used fingerprint values, phrase/concreteness readings, evidence and display titles. Six surviving presets compare main-like sum ranking, flat count, concrete-aware cap, stronger concrete evidence, mood union and text-only. Controls already support near-miss credit, weights, bands, tie scales and pool combinations. The README opening “nine queries/seven presets” is stale relative to the artifact. [Initial lab and findings](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/README.md), [initial template](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html), [initial capture](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/capture.json).

Recorded findings: count ranking suppresses Kung Fu Panda for “complete nonsense”; stronger concrete evidence partly restores cooking-show candidates. But Stalker drops for “tarkovsky”, and How to Train Your Dragon drops from 7 to 31 under the concrete-leads experiment. These are diagnostic watched-title ranks, not human relevance grades. Hard hit thresholds discard score strength within each band; counting dimensions equally also removes weight strength from the primary score. These are formula properties, not demonstrated quality defects. The initial README attributed the Tarkovsky loss to a score-5 cliff; inspection during the next iteration found Stalker also misses non-linear narrative (1) and psychedelic (3), so that earlier causal explanation must not be repeated as established evidence. How to Train Your Dragon (2010) already matches all five selected attributes; its trade-off concerns strength and evidence, not an incomplete hit count. [Initial recorded sweep](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/README.md).

## Gaps the next lab should make visible

- **Reference fidelity.** The starting lab's “Production (main)” is only a model: it normalizes text against observed min/max without main's zero/one anchors, adds a small cosine term on the text path that main does not use, and normalizes vector fill after removing text overlaps rather than over the full vector pool. Correct the model and label it “main formula replay over captured pools”; do not imply a newly captured production response. [Starting template](https://github.com/alp82/goodwatch-monorepo/blob/c5398a5e/docs/prototypes/ranking-lab/template.html), [pinned main](https://github.com/alp82/goodwatch-monorepo/blob/055824a282ef22cd77f852ff111a83e77a2c47e7/goodwatch-webapp/app/server/combined-search/d4.server.ts).
- **Recall versus ranking.** No formula can rescue an absent candidate. The lab should distinguish missing from vector pool, missing from text pool, and present but ranked low. The capture does not contain whole-catalog candidates, so even a perfect offline ranking does not prove recall. [Capture script](../../goodwatch-webapp/scripts/ranking-lab-capture.ts).
- **Description versus final search.** The lab does not include TMDB title matches, final blend, authoritative metadata recheck, identity collapse, basic fallback or pagination. “Tarkovsky” may have person/title intent the isolated discovery model does not represent. The accepted 30-query fixture includes exact/misspelled titles, exclusions, long requests and languages absent from this 14-case experiment. [Fixtures](../prototypes/search-evaluation/fixtures.json), [combined orchestration](../../goodwatch-webapp/app/server/combined-search/search.server.ts).
- **Meaning of evidence.** Evidence counts matching search clauses, including overlapping phrases, not independent confirmations of relevance. Show exact evidence strings alongside score components to expose repeated lexical credit. [D4 pool construction](../../goodwatch-webapp/app/server/combined-search/d4.server.ts).
- **Missing values.** The starting capture converts missing vector fingerprint dimensions to zero. Offline code can then reward an avoided missing dimension as if its known score were zero; Qdrant's range condition for a missing payload does not necessarily match that arithmetic default. The capture cannot reconstruct missingness after coalescing. Display the limitation, and retain null/missing values in future captures. [Capture script](../../goodwatch-webapp/scripts/ranking-lab-capture.ts), [branch formula/defaults](../../goodwatch-webapp/app/server/combined-search/d4.server.ts).
- **Latency accounting.** `vectorMs` is a raw cosine call; `textMs` wraps full branch retrieval and can include vector fill and metadata reads. Their sum is not combined-search end-to-end latency. Cached readings happened to make original captures free; the script can call paid inference or write runtime state on a cache miss. Existing HTML reranking alone is offline and free. [Capture script](../../goodwatch-webapp/scripts/ranking-lab-capture.ts).

## Concrete next iteration

Keep this a single-file logic prototype: the design question is “Which scoring/pool rule improves the whole request without the observed count cliffs or concrete-evidence regressions?” No new application route is necessary.

1. Add a concise goal/inventory panel and guided cases for nonsense, threshold cliffs, concrete evidence, sparse-pool fill and missing candidates.
2. Show reference versus experiment side by side, top-10 entrants/exits, all watched-title ranks and per-query change summaries. Clearly separate observed ordering from assistant assessment and user verdict.
3. Explain each selected row with weighted sum, in-range hits, evidence strings, pool membership, final arithmetic and cutoff-sensitive dimensions. Make score-5 cliffs visible.
4. Compare bounded hypotheses that preserve useful weighted-score distinctions: main sum with concrete-aware evidence; confidence-weighted hits; a smooth threshold transition; and existing concrete-leads count. Reject configurations that buy a single watched-title improvement by visibly damaging other requests. These are suggested experiments, not accepted decisions.
5. Keep full configuration visible and shareable/exportable in memory. Annotate “new results need review” rather than manufacturing a numeric quality pass. Preserve the existing 14 captures as the experiment source and link the 30-request acceptance baseline separately.

Before any adoption, the integrated 30-request path still needs per-request comparisons, user review of new results, exact/misspelled lookup and eligibility verification. [Acceptance #121](https://github.com/alp82/goodwatch-monorepo/issues/121) retains the historical Incepton and vote-floor failures; current code includes eligibility fixes but issue status alone does not establish that every case now passes. [Implementation #122](https://github.com/alp82/goodwatch-monorepo/issues/122) remains open for broader verification. A local ranking winner does not resolve those tickets.
