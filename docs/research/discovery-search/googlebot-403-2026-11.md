# Googlebot 403 incident — November 2026

**Cause confirmed; one scoped Cloudflare exception applied November 27 at 05:58:17 UTC. Fresh verified Google homepage success and recrawl remain pending.** No application, Worker, DNS, SSL, proxy or Coolify changes.

## Cause and timeline

Cloudflare's **Block AI training crawlers** managed rule blocked real Googlebot and Bingbot, including the exact homepage crawl Search Console reports as forbidden. The global `ai_training: "block"` policy was applied to these search crawlers; their verified status did not exempt these requests. The events establish the policy responsible, but not Cloudflare’s internal reason for applying it to search crawlers. The existing exception covered only Applebot and PetalBot.

The event API does not expose the raw `cf.client.bot` boolean. Its verified category plus independent range verification establish identity; the bot score field is unavailable on this zone. The ruleset read response identifies its `http_request_sbfm` phase even though direct access to that managed ruleset is denied. Do not confuse the event source label `firewallManaged` with the execution phase.

- November 13: AI training blocking enabled, per the [cutover record](../../cloudflare-proxy-cutover.md). The custom fake-engine rule was last modified November 13; the Applebot/PetalBot exception November 14. No November 17–18 edit appears in these rule timestamps.

## Exact single change and rollback

Added **Allow verified Googlebot and Bingbot past AI training block** to **goodwatch.app → Security → WAF → Custom rules** (new dashboard: **Security → Security rules**), after the three existing custom rules. Before: this rule did not exist (`null`). After: enabled Skip, **All Super Bot Fight Mode rules only**, with **Log matching requests** enabled. No remaining-custom-rule, rate-limit or managed-WAF skip is selected. The exact expression and API rule are below.

This exception requires Cloudflare verification as well as the named Googlebot/Bingbot identity and one of the three site hosts. It is not a user-agent-only bypass. The bot phase must be skipped because that is where this training rule executes; global AI training blocking remains enabled. The existing Applebot/PetalBot exception is untouched. Cloudflare documents this phase-specific [Skip behavior](https://developers.cloudflare.com/waf/custom-rules/skip/options/).

```json
{
  "action": "skip",
  "action_parameters": {
    "phases": [
      "http_request_sbfm"
    ]
  },
  "description": "Allow verified Googlebot and Bingbot past AI training block",
  "enabled": true,
  "expression": "(http.host in {\"goodwatch.app\" \"www.goodwatch.app\" \"static.goodwatch.app\"} and cf.client.bot and (http.user_agent contains \"Googlebot\" or http.user_agent contains \"bingbot\"))",
  "id": "1311174ee84b4bffb55e1c8f3be1693a",
  "last_updated": "2026-11-27T05:58:17.090536Z",
  "logging": {
    "enabled": true
  },
  "ref": "gw_verified_google_bing_training_exception",
  "version": "1"
}
```

Read-back verification: all three pre-existing custom-rule objects match the snapshot exactly; bot settings match exactly; exactly one rule was added. `fight_mode` and `enable_js` remain false, `ai_training` remains `block`, AI search/user policies remain disabled, and managed robots remains off. The API does not return separate SBFM verified/likely/definitely-automated settings for this zone; no such setting was changed.

Private rollback snapshot: `~/goodwatch-private/cloudflare/googlebot-403-before-2026-11-27.json`, directory mode 0700, file mode 0600. Applied configuration: sibling `googlebot-403-after-2026-11-27.json`. Both were kept outside the repository. **Rollback:** delete only custom rule `1311174ee84b4bffb55e1c8f3be1693a` in the above dashboard page. This restores the previous three-rule list; it also restores the known crawler block.
