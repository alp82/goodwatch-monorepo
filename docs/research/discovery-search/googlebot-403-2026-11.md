# Googlebot 403 incident — November 2026

Investigation: November 27, 2026. **Open: edge rejection suspected; specific rule and recovery not yet proven.** No production setting or application code was changed. This note records an investigation, not a deployed fix.

## Timeline and attribution

- November 14, 19:17 UTC: apex proxy enabled, per [cutover record](../../cloudflare-proxy-cutover.md). That record explicitly warns that the verified-bot export becomes blind behind Cloudflare. Bot Fight Mode was documented off; AI training blocking was on. The “Fake search engines” rule is a **custom WAF rule**, not a managed rule.
- November 17–18: supplied Search Console performance evidence drops from roughly 100–117 daily impressions to 9, then about 5; zero from November 22. This bounds the symptom, not the configuration-change time.
- November 27, 04:45:25 UTC: independently repeated URL Inspection reports homepage `Blocked due to access forbidden (403)`, `ACCESS_FORBIDDEN`, mobile crawler, robots allowed.
- Origin access logs for 04:44–04:47 UTC contain eight homepage requests, all 200, and no Google-agent request on the apex. This supports rejection before the origin, but is not a Cloudflare event identifying the responsible rule.
- Ordinary public homepage request during investigation: 200. No spoofed Googlebot request is treated as verification.

The running origin proxy's apex middleware is in-flight limiting and retry; named crawler limiting is separate. The browser gate excludes the homepage and the person policy applies only to person routes. No changes to the edge/proxy folders or the three named bot-gate modules appear on main during November 17–18. The five cited Worker commits are November 25; the documented deployed canary targets `/shows/moods/sad`, not `/`. Live Worker routes could not be read, so repository configuration alone cannot exclude an undocumented edge deployment.

## Access blocker and owner remediation

The existing credential can list the zone but gets HTTP 403 reading the custom WAF ruleset, Bot Management settings and Worker routes. GraphQL rejects Security Events access for missing Analytics Read. A private request for a scoped read-only credential was opened. No documented scoped API procedure for the exact necessary security change has been established; no dashboard writes were attempted.

In the [Cloudflare dashboard](https://dash.cloudflare.com/), select **goodwatch.app**:

1. Open **Security → Events** (in the newer layout, Security Analytics → Events). Filter hostname `goodwatch.app`, path `/`, UTC November 27 04:44–04:47, and Google crawler user agents. Inspect action, service/source, rule ID, verified-bot classification and source address. Verify that address with Google's published ranges or forward-confirmed reverse DNS. If historical events are unavailable, run Search Console's homepage **Test live URL** and inspect that new event immediately. Repeat for Bingbot and the other Google crawler families; do not infer their outcome from Googlebot.
2. If the matching event names **Fake search engines**, open **Security → WAF → Custom rules** (new layout: **Security → Security rules**) and inspect that exact rule. The documented expression requires `not cf.client.bot`. Restore that condition if missing. If an authentic Google address is misclassified despite it, retain the Ray ID and verified evidence for Cloudflare support; do not exempt arbitrary Googlebot user agents.
3. If the event names **Bot Fight Mode**, open **Security → Settings**, filter **Bot traffic**, and switch **Bot fight mode** off, restoring the recorded baseline. WAF Skip cannot bypass this product.
4. If the event names **Super Bot Fight Mode**, on that same settings page set **Verified bots → Allow** if it is blocking them. If the AI training policy is the matching source, use a narrowly scoped verified search-crawler exception for the identified phase; do not disable all AI training protections or add a blanket verified-bot skip. The existing Applebot/PetalBot exception is not evidence that Google is exempt.
5. If a different custom or managed rule is named, change only that rule's verified search-crawler exclusion. If no security event exists, check **Workers & Pages → Worker → Settings → Domains & Routes** for any route covering the apex homepage and inspect its logs. The actual rule/toggle remains unknown until this evidence is available.

Cloudflare references: [bot protection settings](https://developers.cloudflare.com/use-cases/solutions/stop-malicious-bots/), [custom rule ordering and verified-bot skips](https://developers.cloudflare.com/waf/custom-rules/use-cases/challenge-bad-bots/). These are conditional remediation paths, not a claim that any listed setting is currently enabled.
