# Align availability timestamp verification with the actual publication path

Research date: 2026-09-18 (Europe/Berlin). Inspected working tree at `ef163b0ac13be83069fa042a192d274f35c85acf`. Source and recorded operational evidence only; no live database inventory, deployments, scraping, or tracker changes.

## Recommendation

Keep [Verify availability timestamps for the 30-day watchability rule](https://github.com/alp82/goodwatch-monorepo/issues/91) open, but sharpen it around **source-specific title/country check evidence propagated to offers and negative results**, rather than assuming a per-service last-check field exists. The source pipeline already records useful successful scrape times. The main known gap is loss of their scope and provenance before the webapp reads availability.

[Decide when suggestions are useful and watchable](https://github.com/alp82/goodwatch-monorepo/issues/85#issuecomment-5720596749) requires availability at least 30 days old or otherwise unestablished to be unknown, excludes it from confirmed watchability, and distinguishes a current no-matching-offer check. It does not require changing the crawler's existing refresh schedule or building an availability service from scratch.

## Proposed ticket edits

Replace the question's assumption of service-level checks with:

> Which existing source snapshots can establish a trustworthy availability check for a media identity and country, and how must that evidence accompany each selected-service/offer-type match and a no-matching-offer result to apply the thirty-day rule?

Append bounded acceptance requirements:

1. Identify the actual deployed scheduled/priority publication path and inspect representative Mongo source snapshots, reconciled Crate records and webapp responses read-only; use both movies and shows and more than one country on a title.
2. Document separate scrape and API source check semantics, including omitted API data, mixed contributions, successful empty snapshots, failures preserving old links, unresolved provider mapping, identity-repair pending/quarantined countries and unattributed legacy rows. Do not treat missing child rows as a verified negative.
3. Explicitly reject title-wide `tmdb_providers_updated_at`, generic publication timestamps, retry deadlines and vector membership as sufficient freshness proof. Verify a fresh country cannot rejuvenate a stale country or contribution.
4. Return a minimal propagation contract for source check time, covered country/scope, usable/unknown state and verified-empty evidence. This contract may use country-level source snapshots; it need not introduce a separate fetch per service. Decide how conflicting sources affect positive and negative confidence before claiming either.
5. Verify age just below, exactly at and above thirty days, missing/invalid evidence, an empty success, a current snapshot lacking a selected service, and mixed fresh/stale countries. Include timestamp units, UTC interpretation and cached responses. Preserve title discovery when watchability is unknown.
6. If current publication cannot supply the contract, create one scoped implementation follow-up to propagate it through publication and the watchability read boundary, owned alongside [Implement interest discovery and explicit watchability checks](https://github.com/alp82/goodwatch-monorepo/issues/92). Do not absorb a global rescrape, identity-backlog cleanup or infrastructure program into this verification ticket.

A conservative per-source/per-country check record that survives zero offers is a plausible small correction, not a settled schema decision. The research ticket should establish the contract and evidence; implementation belongs to its follow-up or the watchability delivery slice.

## Confidence and limits

High confidence that existing source scrape timestamps have useful semantics and the current published/read shapes lose the necessary scope. No claim that any particular live title is stale, that the historical backlog persists at its reported size, or that deployed scripts match this checkout. The next step is a bounded read-only sample and deployed-definition check, not changing crawler capacity.
