Research date: 2026-09-17. Source revision: `ef163b0ac13be83069fa042a192d274f35c85acf`. This is a read-only source/intent investigation of [Verify authenticated guest handoff and import recovery](https://github.com/alp82/goodwatch-monorepo/issues/88), not its account-backed execution or resolution. No account, browser session, database, or tracker was changed.

## Recommendation

Keep the ticket, but explicitly scope it as **current-behavior evidence and reusable controlled-account fixtures**; implementation verification belongs to [Implement confirmed account transfer and recovery](https://github.com/alp82/goodwatch-monorepo/issues/90), with the final production repeat in [Deploy and verify the completed recommendation journey](https://github.com/alp82/goodwatch-monorepo/issues/94). The existing evidence question remains valid, but its instruction to compare with human decisions “if already resolved” is outdated: the [guest-progress resolution](https://github.com/alp82/goodwatch-monorepo/issues/84#issuecomment-5705214162) now supplies the mandatory expected behavior.

## Current code and implications

- Existing accounts are split by onboarding completion, not by actual account age: completed onboarding exits before checking guest storage; incomplete onboarding triggers automatic import without a review. Exercise **new**, **existing incomplete**, and **existing complete** accounts separately, including an existing incomplete account with conflicting data. Sources: [step selection](../../../goodwatch-webapp/app/ui/onboarding/hooks/useOnboardingStep.ts#L23) (lines 23–75), [automatic import](../../../goodwatch-webapp/app/ui/onboarding/SmartOnboardingBanner.tsx#L34) (34–45). These code paths contradict the agreed existing-account review but are not new runtime observations.
- Import writes scores, Wishlist and skips, but no watched-state write. The generic upsert overwrites conflicting score values, and writes happen concurrently across tables and individually within each table. Therefore the current failure/retry scenario must distinguish a request failing before writes, a partially completed write set, and a successful write whose response is lost; only exercising a generic HTTP failure cannot establish partial-write recovery. Sources: [import endpoint](../../../goodwatch-webapp/app/routes/api.import-guest-interactions.ts#L26) (26–99), [upsert](../../../goodwatch-webapp/app/utils/crate.ts#L177) (177–242). Keep watched-state checks as existing-member regression evidence, not a new guest interaction type or an assumption that importing a rating marks it watched.
- Guest storage is removed only on a successful import response; dismissal stores a session flag, while the import effect does not check that dismissal flag. Check reload after dismissal and whether a hidden banner still permits auto-import; do not infer that “Skip” means declining guest changes. Sources: [import response](../../../goodwatch-webapp/app/ui/onboarding/hooks/useGuestRatingImport.ts#L18) (18–47), [dismissal](../../../goodwatch-webapp/app/ui/onboarding/hooks/useOnboardingActions.ts#L60) (60–63), [banner effect and rendering](../../../goodwatch-webapp/app/ui/onboarding/SmartOnboardingBanner.tsx#L34) (34–60).
- Country continuation uses guessed country or US; provider selection prefers member settings then browser storage. These are separate writes from interaction import. Include preference-only guest progress and a settings failure after successful interaction import, so “transfer success” cannot mean ratings alone. Sources: [onboarding actions](../../../goodwatch-webapp/app/ui/onboarding/hooks/useOnboardingActions.ts#L17) (17–51), [provider preselection](../../../goodwatch-webapp/app/ui/onboarding/StreamingSelector.tsx#L19) (19–25), and the canonical guest-progress resolution.
- Auth form switching drops return context, while email and OAuth redirects use the supplied return path. Sources: [auth form](../../../goodwatch-webapp/app/ui/auth/CustomAuthForm.tsx#L27) (27–82, 212–231). The [earlier walkthrough](walkthrough.md#L26) already observed unauthenticated context loss; authenticated return remains unverified ([limits](walkthrough.md#L45)). Include signup-to-signin switching and return to original browser after cross-browser confirmation.
- Logout clears query caches and the dismissal flag, but does not itself clear guest interactions; Taste keeps its own in-memory interactions and persists them when unauthenticated. Verify completed-transfer/logout without resurrecting old guest state, and pending-transfer/logout without silently destroying recoverable progress. Sources: [logout](../../../goodwatch-webapp/app/ui/auth/SignOutLink.tsx#L19) (19–33), [Taste storage effects](../../../goodwatch-webapp/app/ui/taste/hooks/useTasteScoring.ts#L15) (15–44). The resurrection possibility is a hypothesis, not an observed defect.

2. Require a small table of scenario, agreed outcome, observed outcome, source revision, and unexercised limit. Record missing review/decline/selection behavior as a baseline gap; do not hold this evidence ticket open waiting for its implementation before the implementation ticket can use the evidence.
3. Add explicit baseline cases for logout, preferences-only transfer, settings failure after interaction success, auth-mode switching, and the three failure boundaries above. For the future review, carry forward selection, default-unselected conflicts/preferences, explicit decline versus close, and unselected-change disposal to the implementation acceptance checklist; they are already agreed, not new decisions.
4. Replace “second browser/device if available” with “attempt with controlled second-browser access; if unavailable, record the gap and its owner.” The evidence ticket may document a limit, but the accepted release gate cannot silently waive cross-browser confirmation/original-browser recovery.
5. Retain account access as a prerequisite and coordinate the shared fixture/runbook with [Verify journey deployment access and recovery procedure](https://github.com/alp82/goodwatch-monorepo/issues/93). Specify disposable mailbox/account ownership, new and existing onboarding states, safe fixture reset/cleanup, and a failure exercise confined to controlled accounts. No production infrastructure fault injection is implied.

## Dependencies, design boundary, and limits

The implementation ticket consumes this baseline and performs post-change checks; release preparation shares access/tooling, and final release repeats acceptance against production. This avoids three independent fixture efforts without moving implementation into an evidence ticket. Shared guest storage and discovery context remain owned by [Implement shared guest progress and discovery continuity](https://github.com/alp82/goodwatch-monorepo/issues/89). The [accepted design](https://github.com/alp82/goodwatch-monorepo/issues/86#issuecomment-5721529691) retained only incremental explore-bar changes and explicitly did not approve signup/import-review presentation; this evidence ticket should not select a redesign.

Confidence is high for source behavior and scope alignment, limited for actual authenticated runtime. Searches of tracked docs and webapp source found no documented disposable-account provisioning mechanism; this is not proof no established access exists elsewhere. The earlier walkthrough explicitly lacked such access. No Chrome DevTools tool was exposed in this research agent's available tool list; no browser or account-backed checks were attempted. [Webapp instructions](../../../goodwatch-webapp/AGENTS.md#L14) require the existing localhost:3003 server and Chrome DevTools, and prohibit automated tests. This report changes no release gates and resolves no ticket.
