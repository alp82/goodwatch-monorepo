# Interest discovery and watchability: ticket alignment

2026-09-18. Research for [Implement interest discovery and explicit watchability checks](https://github.com/alp82/goodwatch-monorepo/issues/92), within [Deliver a continuous recommendation journey](https://github.com/alp82/goodwatch-monorepo/issues/82). Inspected source checkout `ef163b0ac13be83069fa042a192d274f35c85acf` and current tracker decisions. This is source research, not runtime verification or implementation. Only this report was written.

## Recommendation

Retain this delivery ticket, but clarify its concrete work and prototype reference. The [watchability resolution](https://github.com/alp82/goodwatch-monorepo/issues/85#issuecomment-5720596749) remains the behavior contract. The [accepted experience resolution](https://github.com/alp82/goodwatch-monorepo/issues/86#issuecomment-5721529691) accepted only the incremental details explore bar and Taste-card links, not a complete discovery/watchability presentation. Replace “using the reviewed connected-experience prototype” with an explicit link to that final resolution; do not revive its rejected layouts, dialogs, signup UI, or preview state. Any additional presentation that requires a user decision should receive live review while routine delivery remains AFK.

Add these implementation/acceptance obligations:

- Provide a real zero-rating general-suggestion path for guests and members without usable positive history. Remove the initial recommendation gate without pretending the existing personalized endpoint supports empty input. Distinguish general suggestions from personalized ones, and preserve optional rating/refinement.
- Use the shared guest/member interaction contract for exclusions and interest signals. Preserve `(media_type, tmdb_id)` identity, exclude rated/skipped titles from fresh discovery, retain existing watched-history exclusions, keep Wishlist separate, and use Want to See as interest rather than only an exclusion. Cover cross-media numeric-ID collisions and users with only low ratings or Wishlist history.
- Implement explicit discovery versus watchability modes. Saved services must not silently constrain initial discovery. Apply country, selected provider, offer type, and verified freshness together only for the watchability check. A provider match alone does not prove an included or fresh offer.
- Consume verified country/source-aware availability evidence from the timestamp investigation. If its findings require publishing new evidence, name and wire that scoped delivery prerequisite rather than treating an investigation's closure as implementation. Distinguish unknown from a verified current no-match, including countries with zero offers.
- Make recommendation result cards open real details and retain origin context, coordinating with shared continuity delivery. The accepted links on the large rating card do not implement links on the recommendation-result cards.
- Deliver close-enough directions with actual initial suggestions and explicit relaxed constraints. Keep previews separate from current matching results and leave active filters unchanged until selection. Unknown/unavailable previews must never be labeled confirmed watchable.

A new broad recommendation-engine ticket is not justified: useful existing generation/filtering primitives exist. A separate scoped availability-publication delivery task is justified if the timestamp investigation confirms the consumer lacks the necessary evidence; it should block the watchability part of this work. Initial general discovery and exclusions can proceed independently of that data delivery. There is no evidence here requiring a further design-map split for the whole ticket.

## Availability and delivery ownership

The [timestamp investigation](https://github.com/alp82/goodwatch-monorepo/issues/91) is already a blocker. Its answer must establish what evidence downstream consumers can use, including fresh zero-offer outcomes and failed/frozen contributions. The [parallel availability report](ticket-alignment-availability.md) traces existing country-level successful check evidence and its loss at publication, recommending a minimal propagation contract and scoped delivery follow-up rather than broad rescraping. This discovery report does not independently verify Mongo publication semantics. The current discovery SQL and streaming component inspected here are sufficient to show that the UI/query path does not itself implement the agreed freshness distinctions.

Shared progress and navigation state belong to [Implement shared guest progress and discovery continuity](https://github.com/alp82/goodwatch-monorepo/issues/89); account transfer belongs to its separate delivery task. This ticket should consume those contracts and implement result/action behavior, not create another guest store. [Production release](https://github.com/alp82/goodwatch-monorepo/issues/94) owns deployment and final cross-entry-point verification; this task still needs its own local runtime evidence before handoff.

## Verification limits

No recommendation endpoint, browser journey, ranking-quality evaluation, or production database was exercised. The findings establish reusable code and gaps to verify, not observed production defect rates or recommendation quality. Preserve all seven scenarios in the canonical watchability resolution, particularly immediate discovery despite saved services, paid-offer opt-in, unknown at 30 or more days, retained interest in unavailable titles, and previews that do not mutate active constraints. Follow [webapp AGENTS.md](../../../goodwatch-webapp/AGENTS.md), lines 6–16: existing localhost:3003, Chrome DevTools, Lighthouse for significant changes, and no automated webapp tests.
