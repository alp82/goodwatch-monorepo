# YepWatch store assets

- Google icon: `icon-512.png` (512×512 RGB PNG).
- Apple marketing icon: `icon-1024.png` (1024×1024 RGB PNG, no alpha channel).
- Google feature graphic: `feature-graphic-1024x500.png` (1024×500 RGB PNG).
- Android phone gallery: the eight `android/gallery-*.png` files (1080×2400), in filename order. They show the real voting deck, four reaction looks, a match, shared matches and the final decision. The reaction images are full-resolution frames extracted from native screen recordings. The older `01`–`04` captures remain as alternatives; upload the new eight, rather than all twelve.
- Apple native galleries: `ios-iphone-medium/gallery-*.png` (1206×2622), `ios-iphone/gallery-*.png` (1320×2868), and `ios-ipad/gallery-*.png` (2064×2752). There are eight medium iPhone images, six large iPhone images and six iPad images. Each display has its own native captures. The original `01-choose-together.png` home screens remain as alternatives.

Artwork comes from the existing YepWatch SVG mark and Gabarito typeface. Run `node --import tsx scripts/build-store-assets.ts` from `yepwatch-app` after installing app/webapp dependencies. It also regenerates the crawlable policy pages from the same content used by the app. It does not generate screenshots.

Apple capture uses the native simulator artifact from EAS build `7f5a5b83-0a97-4efe-b1f1-1ae2d6ec53ec`, with `com.yepwatch.app`, version 1.0.0 (17). `scripts/capture-apple-store.py` records home screens without creating rooms or signing in. The `store-capture-gallery` profile records complete group flows and their real animation frames using two owned, disposable guest identities. It uses the live public API, with fixtures disabled, and never signs into or changes a GoodWatch account. `store-simulator` builds a fresh simulator artifact and captures it; `store-capture-existing` captures the pinned artifact. Update that archive URL before reusing a different build. Download only the named screenshot PNGs for store use; private debug artifacts must not be committed or uploaded to the store.

The current galleries are documented in `gallery-manifest.json`: source recording hashes, selected timestamps, output hashes and native dimensions. No image is a web page resized to look like a phone or tablet; no screenshot is retouched or given a fabricated app interface. Native video frames retain the recorder's original dimensions.

Use `node scripts/export-store-copy.cjs <destination>` for individual paste-ready listing fields. The canonical source is `store/en-US.json`. Google uses the short and full descriptions; Apple additionally has subtitle, promo text and keywords.

For Apple staging, set `YEPWATCH_EAS_CLI_ROOT` to an installed `eas-cli` directory, then run `node scripts/upload-apple-gallery.cjs --apply --output <private-result.json>` from the app directory. The helper checks app/version identity, PNG dimensions, file checksums and processing, retains earlier uploads at the end, and reads the sets back. Without `--apply`, it only inspects. It never submits review. Use `scripts/sync-apple-listing.cjs` separately for the complete text records; partial updates through the underlying Apple helper clear omitted fields.

Capture inputs (`YEPWATCH_GALLERY_ROOMS`) and downloaded diagnostics contain guest credentials or invitation links. Keep them outside source control and the handoff bundle. Prepare only rooms you own with `scripts/store-gallery-room.py --prepare <private-state.json> --families iphone-medium iphone-large ipad`; the state file persists the exact admission request before sending it. Supply those admissions to one private EAS job, restore any temporary profile environment before committing, and download only the selected PNGs for publishing. Private debug/video archives remain separate.
