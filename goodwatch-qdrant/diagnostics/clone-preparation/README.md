This prepared helper can request cache reclamation only from the existing task-owned Qdrant clone. It is uninstalled. Default invocation reports preparation without imports from the staged runtime, host inspection or mutation. Execution requires the exact script, staged controller and policy hashes. It does not start/stop Qdrant, change resource limits, read the archive, advise files, pin pages or issue search queries. It performs bounded collection metadata GETs to verify green/optimizer-ok/244,262 points/12 segments/six shards.

The [actual initial-cap refusal](../../../docs/implementation/search-ranking/clone-pin-cap-refusal-20261012.json) measured 6,346,526,720 current bytes + 895,873,024 missing selected bytes + 268,435,456 reserve, exceeding the unchanged 6,442,450,944 cap. No pin child was started. A later [ten-second passive observation](../../../docs/implementation/search-ranking/clone-cache-passive-20261012.json) found file/current/anonymous bytes stable and no physical read/write growth. The earlier 2.69 GB file-cache observation used the pre-zero-gate Qdrant process; the later 4.04 GB used the restarted process. Those records do not establish the cache-populating mechanism. Current cache is mostly mapped; dirty/writeback/tmpfs/locked/swap counts were zero during the sample.

Linux [6.8 cgroup-v2 documentation](https://www.kernel.org/doc/html/v6.8/admin-guide/cgroup-v2.html#memory-interface-files) defines `memory.reclaim` as a target-cgroup proactive reclaim request accepting bytes without nested keys. Reclaim can exceed or fall below the requested amount; `EAGAIN` means under-reclaim. It is not ordinary memory pressure, and it does not guarantee a file-only result. This experiment would establish clone preparation, not production-backup equivalence.

The helper takes the existing control lock and optional empty instance lock. Before and immediately before its single write, it verifies exact image/mounts/resources/process identity, no descendant cgroups, the expected Qdrant and entrypoint processes only, zero swap/dirty/writeback/locked pages, outside helper placement, and unchanged source-process/ancestor limit fingerprints. It opens only that guarded cgroup's `memory.reclaim` with a held directory FD and inode fence. An outside-cgroup child repeats the source and FD checks, then attempts one bare 3 GiB write. The parent waits at most 60 seconds, sends TERM with five seconds grace, then KILL with five seconds grace. A kernel-blocked surviving writer is reported; it is not implicitly joined or retried. Inherited task locks remain held while such a writer survives, and no further control is safe until its exit is confirmed.

Both accepted and under-reclaimed requests require fresh numeric cache/accounting/process counters, no new cap/OOM/throttle events, unchanged process/limit/range-selection fences, metadata health and the original strict `current + actual missing selected pages + reserve <= cap` test. Host floors and disk budgets remain unchanged. Failed/incomplete evidence is a refusal, not a reason to relax the cap. The final range digest does not freeze file contents, and cache/accounting can change after measurement. Pinning needs its own fresh guards and proof.

Readonly inventory uses the separately explicit own-process soft-NOFILE option; the hard limit, source and ancestor limits remain unchanged. No MEMLOCK adjustment or cgroup join occurs. Recorded source write-byte deltas expose background activity; zero dirty pages at a guard cannot exclude concurrent background writes. Output contains fixed reasons, hashes and numeric evidence, never raw paths, process arguments, queries or exception text.

Run local fixtures with `python3 -B -m unittest discover -s goodwatch-qdrant/diagnostics/clone-preparation -p 'test_*.py'`. They use temporary files and owned children only: one bounded write, EAGAIN without retry, real timeout/reaping, child source rejection before write, limit/resource fences and cap refusal despite reduced current memory. They do not execute cgroup reclamation.
