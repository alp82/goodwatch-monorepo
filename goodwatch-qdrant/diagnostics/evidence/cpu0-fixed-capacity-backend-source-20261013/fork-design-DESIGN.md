# Prepared PinChild fork refinement

This is a local design proposal after the immutable backend08ea static BLOCK. No host action or source mutation is authorized by this document.

Replace only controller_cpu0.PinChild's multiprocessing spawn context with explicit fork. ZeroChild behavior, source4, runtime, daemon, CPU guards and f831 reclaim helper remain byte-identical. Keep the existing parent scope `with lifecycle.helper_fork_scope(lock_fd): manager=PinChild(...)`; its registered at-fork child hook closes only that held control FD in the child, while parent retains and rechecks its same FD/flock. CLOEXEC alone is not a fork guarantee.

Before Process.start, require the controller has exactly one thread using bounded actual `/proc/self/task` enumeration. Refuse if any second thread exists. Do not create a tracker: fork Process+Pipe uses neither multiprocessing shared-memory nor synchronization objects, and no spawn preparation calls resource_tracker.getfd. A real isolated child-census fixture must assert the only live direct child is the actual helper and no new tracker exists. Existing exact source-member census remains strict; no generic Python exemption or extra PID roster.

The child receives only the existing pipe/spec/policy/config/own-limit flags. Close the parent's pipe endpoint explicitly in the fork child, and child endpoint in parent. Verify the child has no control-lock FD via real inherited-FD fixtures while parent still blocks an independent contender. Other inherited FD inventory must be measured in fixture, and unrelated owned sensitive descriptors explicitly closed in child; do not falsely claim fork is exec or drops all FDs. No private query packet is read by the Python controller; Node owns private HTTP.

Unchanged pin_child prepares its own memlock/nofile, joins the exact source cgroup, uses fresh parent-inspection RPC and local process/exe/startTicks/source-cgroup validation, and holds read-only mappings. Child PID/startTicks/exe/parent/cgroup/VmLck must be independently measured in source_helper_context; before join it is not admitted as a held helper. Parent outside ledger charges controller full new role and source anon/kernel growth; joined helper is report-only and not double-charged. Pre-join attribution remains explicitly unknown, peaks null. Parent-only inspector counters must not aggregate fork-child inherited memory; child calls delegate unchanged.

Actual helper after joining must be exactly the third physical source member (wrapper,Qdrant,helper), while controller's direct children must be exactly the helper. Existing baseline/query limits, 256 MiB cap reserve, 512 MiB measured growth allowance, full selected working-set debit, 100% residency and query floors are unchanged. Any identity/source/extra-child/thread refusal remains terminal, no retry.

Fixture requirements: actual launched isolated Python PinChild using test-only target; real /proc thread census, child census, PID/birth, retained parent control lock, child absence of that FD and parent's pipe FD; helper join/source/accounting authority may be explicit stand-in and cannot prove host placement. Add a real background-thread refusal before Process.start and a parent-only inspector count fixture. Validate all backend14 source files unchanged except the intentional controller/tests/docs successor, with new prepared hashes after review. This design does not prove real clone readiness, pin capacity or latency.

Review question: is this narrow fork context safe and complete for this single-threaded stdlib controller, or is an explicit subprocess/pipe successor required? Identify any missing inherited-descriptor or lifecycle closure. Do not request broader schema changes unless necessary. Do not execute tools.
