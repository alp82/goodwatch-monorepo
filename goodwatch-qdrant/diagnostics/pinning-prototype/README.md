# Uninstalled mapped-data pin prototype

This backend prototype tests preventive file-page locking. It has not been installed or used to pin production or the diagnostic clone. A successful pin state is not application latency acceptance. The frozen three-cycle production backup observation continues independently.

`pin.py` opens regular single-link files read-only, discovers current `SEEK_DATA`/`SEEK_HOLE` ranges, rounds and merges pages, and uses `PROT_READ | MAP_SHARED` mappings. Only selected data pages receive `mlock`; full sparse holes are excluded. Partial data-page boundaries necessarily include the rest of that page. `mincore` checks residency without reading mapped bytes. Selection hashes cover file identities and complete raw extent ranges; they do not freeze contents or eliminate concurrent truncation races.

`queries: 0` and `storageWrites: 0` are declarations of the helper contract, not measured system-wide counters. The helper makes no application query calls or file-content writes; ordinary reads and mappings can update access-time metadata because files are not opened with `O_NOATIME`. Own-process cgroup, OOM-preference and limit changes are explicit setup operations. Future archive reads have the same access-time caveat.

`runtime.py` verifies the fixed source image, exact mounts/resources, actual Qdrant executable, PID and process start ticks before and after a pass. Docker inspection uses the absolute `/usr/bin/docker` executable. Pin setup and reconciliation require an explicit `source_check` callback: the separate controller must inspect outside the capped pin child's cgroup and supply current source proofs through its owned IPC channel. The child independently checks actual process executable, start ticks and cgroup. A missing outside inspector fails before setup. The standalone daemon therefore supports preparation and readonly measurement; its `pin` action refuses rather than spawning inspection processes inside the clone cap. Clone mode additionally requires the task labels and exact loopback publication. Deleted mappings are excluded and retired while unchanged healthy locks remain held. Replaced files or changed ranges reconcile individually. A source restart releases previous locks and verifies that only the helper process joins the current Qdrant cgroup. The helper uses its own instance lock, independently of the backup job lock.

Four classes are selected by the proposed rule: vector, graph, sparse and other. Payload files are measured but excluded unless an explicit reviewed policy includes them. These classes infer roles from filenames; they are not proof of which component a particular query accesses. Payload index/storage coverage must therefore remain visible in held-out results. Inventories fail above 20,000 distinct mapped files or 65,536 extents in one file rather than silently truncating coverage.

Each class reports file count, raw extent count, merged page-range count and data-page count. Before locking, the helper measures missing selected pages with readonly mappings and `mincore`. Initial locks, additional locks or missing selected pages require current cgroup bytes plus those nonresident bytes plus the explicit `capReserveBytes` to fit under a finite cgroup cap; failure is `initial_cap_headroom_inconclusive`, with no new `mlock` calls. An unchanged, fully resident pass needing zero new locks may retain pins near that cap without this additional reserve. It still requires the emergency floor, identity/residency checks and resource-event fences; it does not establish clean promotion. The selected-data-plus-anonymous/kernel guard remains separate. Current accounting precedes new readonly mappings: the reviewed reserve must cover mapping/page-table and helper setup overhead as well as concurrent growth. Existing residency can change between measurements, and existing file-page charges can belong elsewhere, so this preflight does not prove future cap-clean execution. Capture and compare actual resource counters around each phase and across passes. Clean experiment promotion requires zero pressure max events; the optional exploratory steady-pressure allowance is never cap-clean proof.

Extent reconciliation releases obsolete ranges across all selected files before adding any new range. A file gaining an extent before another file loses one cannot transiently exceed the Python locked-byte budget. A real two-file fixed-size extent-transfer fixture records kernel `VmLck`; restoring per-file trim/add ordering makes it exceed its 12,288-byte cap with a 16,384-byte peak, while the corrected ordering stays within the cap.

The mapping guard reads current helper VMAs and the kernel's `vm.max_map_count`. Its conservative projection adds one mapping and up to two VMA splits per merged selected page range, plus an explicit `mappingReserveCount`; it must stay below the kernel limit. It conservatively counts existing held mappings again during a steady pass. Rejection is preferable to exhausting mappings during a fragmented-file lock. Readonly measurement reports its VMA count and kernel limit without claiming that pinning would fit.

Production policy requires an additional-lock reserve of the archive size plus 2 GiB and an emergency floor of 1.5 GiB. Existing locks may remain when the archive consumes the reserve only if a pass needs zero new lock bytes. Segment turnover or extent growth requiring new bytes below the reserve fails and releases the entire pin set; crossing the emergency floor also releases it. The Python locked-byte budget, declared `RLIMIT_MEMLOCK` preflight, and mapped-data plus actual anonymous/kernel memory are checked before additions. Raising the helper's own memlock limit requires an explicit option. Kernel enforcement of `RLIMIT_MEMLOCK` depends on capability: `CAP_IPC_LOCK` bypasses that kernel limit, so root UID alone does not establish a kernel-enforced lock cap. The current Python budget remains an application guard, and cgroup accounting has the placement limitations below. This arithmetic is a necessary guard, not proof that every existing cached page is charged to the target cgroup: earlier restore/archive processes can retain different memory charges.

Initial and additional locking require unchanged OOM, memory-max and CPU-throttle counters. Runtime exposes a narrowly scoped capability for a separately reviewed clone-pressure controller: only an explicit clone pressure pass with zero newly locked bytes and unchanged selection may report a memory-max increment without dropping the pins. OOM and throttling still fail. The normal runner does not enable this capability, and held-out query windows must remain strict. Pressure success must never be labeled initial pin success.

At the authorized read-only clone inventory on 2026-10-11, the four selected classes covered 1,725,227,008 page-rounded bytes; anonymous memory was 2,262,941,696 bytes and kernel memory 41,725,952 bytes. Their sum was 4,029,894,656 bytes under the unchanged 6 GiB clone cap. Current cgroup memory was 5,123,055,616 bytes; the measured missing selected pages represented 466,190,336 bytes. This snapshot was not already at its cap, although it does not establish current or future headroom. Fresh preflight plus the reviewed cap reserve must decide whether a run can proceed. Including payload would increase selected pages to 4,068,966,400 bytes, leaving insufficient reliable cap margin. Host available memory was 4,468,654,080 bytes, below the production archive-plus-2-GiB reserve. These measurements do not authorize relaxing the production policy or increasing the clone cap.

The experiment plan remains pending review. It must use the existing task-owned archive for bounded read-only pressure or a separately reviewed smaller scratch budget. An additional archive-sized file would exceed the existing disk allocation guard. No global cache flush, production warming, Qdrant restart, resource change, search-history write, or paid lookup is part of this prototype. Freeze the helper and selection-rule hashes before selecting held-out requests; report missing coverage dimensions truthfully. Capture initial locking, pressure and held-out query resource windows separately, with source continuity, complete residency, exact result-set/per-ID score parity and ordering parity recorded independently.

Run local fixtures from the repository root:

```sh
python3 -m unittest discover -s goodwatch-qdrant/diagnostics/pinning-prototype
```

`daemon.py` with no arguments prints a prepared-only record and performs no inspection. Its explicit `measure` action calls the readonly inventory without creating a pin manager or moving the helper into a cgroup. Its standalone `pin` action refuses because it has no outside inspector. The measurement runner exits after the configured lifetime or a termination signal. Runtime pin ownership, alive checks across query windows, cross-pass event comparison and final cleanup belong to the separate controller and remain pending integration validation. Actual cgroup joining and container turnover with the pin child have not been exercised; patched local fixtures are not that proof.

There is no reviewed frozen configuration yet. Review an exact `mapped-data-pin-config.v1` JSON file containing `source`, `policy`, `intervalSeconds`, `lifetimeSeconds` and allowed `actions`. Source fields must pin the current task-owned clone image, exact three binds including the renamed restore fixture, loopback port, 6 GiB memory/swap values and two-CPU limit. The four-class policy explicitly supplies maximum locked bytes, archive size, reserve, emergency floor, `capReserveBytes` and `mappingReserveCount`; payload inclusion is disabled. No cap or mapping reserve is selected by a CLI default. The daemon hashes the exact JSON bytes as `policySha256`, and hashes the filenames and bytes of `pin.py`, `runtime.py` and `daemon.py` as `codeSha256`. Any source/helper/config change invalidates those reviewed digests. These digests cover reviewed files, not the interpreter or loaded-module provenance. Stage reviewed modules in a fresh private directory without preexisting bytecode caches. Use `daemon.code_hash()` to compute its canonical code digest; use SHA-256 of the exact configuration bytes for the policy digest.

After exact configuration review and validation, the invocation template is:

```sh
python3 -I -B goodwatch-qdrant/diagnostics/pinning-prototype/daemon.py \
  --config REVIEWED_CONFIG --policy-sha256 REVIEWED_POLICY_HEX \
  --code-sha256 REVIEWED_CODE_HEX --action measure
```

The standalone `--action pin` option refuses before inspection or setup. The separate controller must own the capped pin child and outside inspection callback; its explicit memlock-raise option can affect only that child. Measure mode rejects a memlock raise. These examples are templates, not executed deployment commands. The daemon has no pressure-window activation mechanism; a separate reviewed controller is still required before experiments.

`pin.safe_reason` returns only a fixed allowlisted code; unknown provider, filesystem and exception text becomes `guard_or_runtime_failure`. The no-lock measurement runner's failure record explicitly states `released: true`. Pin owners must report `PinSet.release_state()` after cleanup; a failed unmap keeps `released: false` and its held mapping count until successful cleanup or proven process exit. A declared failed event alone does not prove the pin child exited or that locks were released. Guard failures preserve their original exception and fixed reason even if cleanup also fails. Both core and runtime attempt cleanup through `pin.release_preserving_error`; `pin.failure_details(error)` separately exposes fixed `cleanupFailureReasons` and the latest tracked `releaseState`. The controller must retain both fields with the causal reason. A later successful retry may update the state to released while earlier cleanup failures remain visible; these historical attempts are not current locked-state claims.

The fixtures use owned temporary files and real small readonly mappings to verify sparse-page accounting, no file writes, partial lock failures, residency failures, successful release, retry after failed unmap, segment replacement without dropping healthy locks, PID/start-time turnover, headroom and limit rejection. Runtime boundaries use local fixtures; they do not issue Qdrant requests or change services. Stop/exit releases the helper's mappings and their locks. A failed `munmap` retains tracking and the instance lock until cleanup succeeds or the helper exits; continuing with untracked locks is forbidden.

Linux documents file-backed locked mappings on the [unevictable LRU](https://cdn.kernel.org/doc/html/latest/mm/unevictable-lru.html), and [mlock/munlock](https://man7.org/linux/man-pages/man2/munlock.2.html) specifies page-rounded locking, limits and release behavior. Those paging guarantees do not promise fixed file contents.
