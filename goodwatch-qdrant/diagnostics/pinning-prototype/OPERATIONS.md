# Prepared production operations

These local drafts are unpublished, uninstalled and unlaunched. They do not start a seven-day acceptance window. `production.py` is the supervisor under review; the operations below require separate review and live permission/release gates.

`production_service.py` validates the frozen helper, raw policy and service/journal hashes before execution. It redirects fixed numeric helper events to `production_journal.py`, which permits one writer, strips unknown fields, fsyncs each complete event and rejects partial tails. The journal must live in a dedicated canonical private directory. Collector-start events and sequences distinguish restart and missing frames. No automatic journal rotation or truncation is provided: retain the closed interval and its hashes before any later rotation.

`production_coverage.py` checks a closed explicit UTC interval against frozen helper, policy and service hashes. A passing interval needs at least seven days, an initial locked proof, healthy fences around both endpoints, renewed lock proofs and heartbeats no more than 45 seconds apart, continuous collector sequences, no restart, release, failure, replay, turnover or source change, and exact locked/resident class accounting. This is supplemental helper evidence: application acceptance is always false. Search lifecycle/history acknowledgements, first usable result latency, full completion time and both ingress collectors remain independently required.

The owned unit template preserves the runtime directory, runs a dedicated parent outside Qdrant and does not restart automatically. It does not install or enable itself. Its capability set and moved-child cleanup need an authorized production live join/release test. Never stop or restart Qdrant to test the production helper.

`publish_production.py` contains a tested owned-file publication and rollback library. Before the first target change, it retains all originals and a prepared receipt under a new private directory and fsyncs them. Each target is replaced atomically after checking the expected current hash. Rollback validates all retained originals and refuses concurrent target edits; it removes only originally absent owned targets. A process dying after publication can recover from the prepared receipt. The CLI intentionally refuses execution pending review. The separate `publication_guard.py` holds inode-fenced exclusive supervisor and holder locks for the entire publication/rollback, repeats unit inactivity checks and performs a bounded process executable/argv census. An existing installation requires a complete private retained journal; every registered holder-start PID/start tick is checked against live proc identity even after a release acknowledgement. First installation refuses unknown existing code/runtime files. `guarded_publish` and `guarded_rollback` wire this guard around the tested library; local fixtures are not proof of production permissions. All earlier supervisor review bundles remain unchanged. The v6 durable birth registration is required before a reconcile command; publication rejects legacy lock records lacking birth identity. Coverage treats a new birth or retry claim inside the interval as discontinuity. No service activation, git pull, cron change, firewall change or Qdrant allocation change is included.

Promotion requires separately frozen source and policy, resolved archive/headroom bounds, a reviewed holder-release publisher guard, actual child VmLck/placement/limits and release proof, plus bounded PR446 memory/pressure collection during the authorized backup trial. Preserve source identity throughout each comparison and classify any emergency release, source turnover or coverage loss as inconclusive rather than successful pinning.
