## Implementation

`utils/account-transfer.ts` captures interactions, country/services and discovery context before password or Google authentication. Browser records bind to the authenticated account, and selections/confirmed payload survive reload. A signup response with a real identity created during that request establishes a newly created account; it binds immediately, even before delayed email confirmation. A later password sign-in retains this proof. OAuth entry records its start before redirect and compares the authenticated user's actual creation time. Neither an empty account nor incomplete onboarding proves newness. Absent proof, existing-account review is used.

`AccountTransfer.tsx` sits ahead of ordinary onboarding, including completed onboarding. It loads uncached account state and real title/provider names, shows account/browser differences, and persists all initially selected changes. Only confirmation starts an existing-account transfer. New-account transfers start automatically. A confirmed selection becomes fixed during retry. Browser storage must work before writes start; errors retain progress. Completion/decline invokes shared-store cleanup; logout clears completed in-memory progress and isolates account query caches. Browser preferences and discovery remain. Auth forms preserve safe local return paths and explain that confirmation on another device requires returning to the original browser.

`api.import-guest-interactions.ts` validates account identity and the entire selection before writing. A durable `user_setting` journal under `browser_transfer:<uuid>` records the confirmed payload, completed parts and final completion. Unknown internal keys are ignored by normal settings readers and excluded from the review response. Journal compare-and-swap updates only advance completion, including overlapping retries. No cross-table transaction is assumed.

Writes are additive for Wishlist/skips and change only the selected score column, preserving written reviews, watched/favorite flags and canonical movie/show identity. Selected preferences and their onboarding completion flags are verified together. Each part is read back before journal acknowledgement; browser cleanup requires every selected part to have persisted. Lost responses retry the same journal, including after server completion, without rewriting later account edits. A selected score/preference changed after review is rejected rather than silently replacing that newer value; the current recovery message requires restoring the reviewed value before retry. This is a deliberate concurrency protection, not an automatic merge or rollback. Already completed writes are not rolled back.
